# 공통 지침

> 영어 원본: [common.md](common.md)
> 이 문서는 사람을 위한 비권위 한국어 번역본이다. 에이전트 실행 시 읽거나 사용하지 않는다.

- 계획, 아키텍처, 장단점, 문제 정의, 복잡한 디버깅, 검토와 주요 결정은 메인 세션에서 처리한다.
  높은 수준의 추론을 위임하지 않는다.
- 대상이 알려진 심볼, 파일 경로, glob 또는 리터럴 문자열이면 메인 세션에서 직접 검색한다.
- 사용자가 요청했든 작업에 필요하든 새 커밋은 모두 `suggest-commit` 스킬의 커밋 모드로 만든다.
  amend, merge, revert, cherry-pick은 이 규칙에 해당하지 않는다.

## 위임

본격적인 작업 전에 담당자를 정하고, 범위·의존성·사용 가능한 기능이 달라질 때만 다시 판단한다.

- 짧은 답변, 알려진 경로 조회, 의존성이 긴밀한 작업, 변경 파일이 두 개 이하인 구현, 통합 수정은 메인 세션에서
  처리한다.
- 여러 파일이 필요하거나 많은 로그를 만드는 제한된 조사를 위임하고, 간결한 결과와 원본 위치를 받는다.
  메인 세션에서 같은 조사를 반복하지 않고 주요 주장만 확인한다.
- 변경 파일이 두 개를 넘는 구현은 범위와 수용 검사가 명확하며 독립 실행이 가능하거나 많은 중간 정보를 메인 문맥
  밖에 둘 수 있을 때 구현 worker에게 위임한다. 자원이 독립적인 작업만 병렬 실행한다.
- 메인 세션의 문맥이나 경과 시간을 줄이면서 품질 저하가 거의 없거나 없을 때는 요청을 기다리지 말고 병렬
  서브에이전트를 적극적으로 사용한다. 각 작업에 필요한 맥락만 전달한다. 인사, 상태 확인, 작은 수정 한 건에는
  에이전트를 만들지 않는다. 사용자와 스킬의 명시적 할당은 계속 우선한다.
- UI 코드, 시각 디자인, 다이어그램 작업은 호스트의 designer 경로로 보낸다. 다만 호스트 세션 파일이 메인 세션에
  맡긴 종류는 예외다. 레이아웃이나 컴포넌트 구조를 바꾸지 않고 문구나 스타일 값만 바꾸는 수정은 구현 worker에게
  맡길 수 있다. 설계 문서와 RFC는 메인 세션에 둔다.
- 호스트의 위임 허용이 필요하다. 위임, 고정 역할·모델·사고 강도 또는 믿을 수 있는 설정 근거를 사용할 수 없으면
  호스트 규칙이 정한 대체 경로를 쓰고, 그런 경로가 없으면 승인된 작업을 메인 세션에서 계속한다. 제한 사항은 한 번
  알린다. 권한과 검사를 유지하고 사용자 설정을 바꾸거나
  다른 작업자 모델로 몰래 대체하지 않는다.

독립적인 읽기 전용 검토는 메인 세션의 검토 책임에 대한 예외다. 중요한 변경을 마치기 전에 한 번 추천한다. 사용자
승인 없이 검토자를 호출하거나 같은 결과에 대해 이미 거절한 제안을 반복하지 않는다. Claude가 작성한 결과라면 세션 줄
"Review model"의 검토자를 밝히고, 승인한 뒤에만 아래의 독립 모델 검증 규칙을 읽는다. 그렇지 않으면 묻기 전에
읽는다.

## 확인 질문

요구가 모호하거나 충돌해서 결과가 달라질 수 있으면 수정과 외부 변경을 멈추고, 필요한 것만 읽은 뒤 간결한
질문 하나를 한다. 호스트 규칙이 필수 질문의 blocking을 허용할 때만 도구를 사용한다. 그렇지 않으면 최종
답변으로 묻고 턴을 끝낸다. 필수 결정에는 비동기 질문을 사용하지 않는다. 사용자의 명시적인 답변을 받은
후에만 재개한다. 무응답, 시간 경과, 빈 답변, 자동 응답, 기본값은 답변이 아니다. 호스트의 출력 형식과
스킬이 따로 정한 질문·중단 규칙을 따른다. 임시 조치와 근본 해결이 둘 다 있으면 비용과 영향을 함께 제시하고
사용자가 고르게 한다. 로그인 같은 대기 중인 사용자 조치는 한 번만 알린다.

## 조건부 지침

- 본격적인 구현, 반복 모델 평가, 플러그인 관리, 반복 실행 실패 진단 전에
  [작업 효율](../work-efficiency.ko.md)을 읽는다.
- 첫 구현 변경 전에 [구현 실행 규칙](../implementation-execution.ko.md)을 읽는다.

## 계획과 설계 작업

- 구현 계획은 실행자가 설계를 추가하지 않고 진행할 수 있어야 한다. 설계 문서는 목표 설계를 공유하며, 기존 문제는
  목표 설계를 설명하는 데 필요한 만큼만 다룬다.
- 사용자가 구현 계획, 설계 문서 또는 RFC를 명시적으로 요청하거나 스킬을 직접 호출했을 때만 관련 스킬을 실행한다.
  일반 구현, 진단, 코드 리뷰, 요약 또는 단순 언급만으로 실행하거나 다른 스킬을 연쇄 호출하지 않는다.
  구현 실행 규칙에 따른 작업 준비는 이런 요청에 해당하지 않는다.
- `document-to-confluence`, `suggest-commit`, `technical-design-writer`는 스킬 설명이 사용자 의도와 일치하면 자동으로
  실행할 수 있다. 이 항목은 앞의 실행 조건에 대한 예외다.
- 사용자가 요청한 구현 계획을 작성하거나 수정하기 전에 [구현 계획](../implementation-planning.ko.md)을 읽는다.
  그 계획, 설계 문서, RFC를 작성하거나 수정하기 전에는 [독립 모델 검증](../independent-model-validation.ko.md)을
  읽는다. 설계 문서 전용 절차와 템플릿은 설계 작성 스킬에서 관리한다.

## 답변

- 용어는 사용자 또는 프로젝트 용어집, 구현과 계약의 리터럴 이름, 공식 제품명이나 정립된 분야 용어,
  정립된 쉬운 표현, 가장 일반적인 기존 표현 순으로 선택한다. 한 의미에는 한 용어를 사용하고 한 용어에는
  한 의미만 부여한다. 낯선 용어와 유용한 약어는 한 번 정의한다. 정확한 용어를 더 쉽지만 다른 뜻의 용어로
  바꾸지 않고 반복되는 용어를 일관되게 쓴다.
- 답변에 Mermaid나 렌더링되지 않는 다른 다이어그램 소스를 넣지 않는다.
  단순한 관계에는 표, 목록 또는 인라인 표기를 사용하고 공간 관계에는 ASCII 그림을 사용한다.
- 도구 호출 사이의 진행 상황 안내를 포함해 사용자에게 쓰는 모든 메시지를, 주변 맥락이 다른 언어를 쓰더라도
  응답 언어로 작성한다. 사용자가 다른 언어로 요청한 텍스트는 코드 블록이나 인용 블록에 넣는다.
