# 공유 글

> 영어 원본: [shared-text.md](../../../instructions/shared-text.md)
> 이 문서는 사람을 위한 비권위 한국어 번역본이다. 에이전트 실행 시 읽거나 사용하지 않는다.

사람들이 작업을 파악하려고 읽는 글을 작성하거나 다시 쓰기 전에, 그리고 원본의 줄바꿈이 화면에도 줄바꿈으로
표시되는 Markdown을 쓰기 전에 이 문서를 읽는다. 각 절은 적용 시점을 밝힌다.

## 줄이기 점검과 빠진 내용 점검

사람이 작업을 파악하려고 읽는 모든 글에 이 절을 적용한다. 사용자에게 주는 답변이나 최종 보고, 저장소 문서, 이슈나
티켓 본문, 댓글, 리뷰 답글, 커밋 메시지, 채팅 메시지, 풀 리퀘스트 설명이 여기에 든다. 이런 글을 쓰거나 고칠 때는 바뀐
부분만이 아니라 글 전체에 두 점검을 모두 한다. 기존 글의 일부만 고쳤다면, 고친 부분 밖에서 찾은 문제는 내 변경
때문에 틀리거나 중복이 된 곳만 고친다.

1. 줄이기 점검: 지워도 독자가 판단하거나 행동하는 데 필요한 사실을 잃지 않는 문장이나 링크는 모두 지운다. 링크한
   원본, 바로 옆의 표나 그림, 다른 절, 독자가 글과 함께 보는 diff를 되풀이하는 문장, 그런 diff가 보여 주는 이름 목록,
   나열한 확인 항목을 요구하는 규칙(필요한 확인을 하지 않았다면 그 이유는 남긴다), 무엇이 바뀌지 않는다는
   문장(독자가 그 문장 없이는 잘못 행동할 때는 제외), 이미 나열한 다른 링크가 대상을 다루는 링크가 여기에 든다.
   같은 종류의 항목은 한 줄로 합친다.
   최종 보고에서는 변경을 동작으로 설명하고, 새 테스트는 그 테스트가 잡는 회귀로 한 문장에 설명한다. 파일, 함수,
   테스트 이름은 사용자가 직접 열어 보거나 조치해야 할 때만 적고, 앞선 실패나 재시도, 누가 어느 부분을 했는지 같은
   작업 과정과 사용자가 묻지 않은 개수는 뺀다.
2. 빠진 내용 점검: 글을 요청과 그 원본에 비추어 본다. 독자에게 필요한 결정, 조건, 선행 조건, 순서, 완료 기준을
   모두 되살리고, 두 가지로 읽히는 문장은 모두 고쳐 쓴다.
3. 게시할 곳에 길이 예산이 있고 글이 그것을 넘으면 먼저 첫 번째 점검으로 줄인다. 줄이면 잃게 될 사실 하나하나를
   아래 독립 검토가 확인할 때만 예산을 넘긴 채로 둔다.
4. 게시할 곳의 글쓰기 규칙이 팀이 함께 쓰는 문서나 저장소에 있으면, 플러그인에서 덮어쓰지 말고 그곳의 규칙을
   바꾸고 그 변경을 공유한다.

## 독립 글 검토

외부 시스템에 글을 올리거나, 다른 사람이 읽는 파일을 쓰거나, 최종 보고를 보내기 전에, 위의 두 점검을 마친 뒤 이
검토를 실행한다. 최종 보고는 작업을 끝내며 그 결과를 알리는 답변이고, 짧은 답이나 질문은 여기에 들지 않는다.
자기 초안에 대해 스스로 기록한 점검은 이 검토로 치지 않는다.

```text
python3 <Source directory>/scripts/text_review.py review --kind <kind> --draft <file> --rules <file>... --source <file>...
```

- `--kind`는 `pr-description`, `review-reply`, `issue-body`, `ticket-comment`, `commit-message`, `chat-message`,
  `shared-document`, `final-report`, `other` 중 하나다. 게시할 곳의 글쓰기 규칙은 `--rules`로, 글이 다루는 요청,
  diff, 티켓은 `--source`로, 길이 예산은 `--budget <글자 수>`로 넘기고, 게시할 곳의 규칙이 티켓 키를 금지하면
  `--no-ticket-keys`를 넘긴다. 최종 보고에는 사용자의 요청과 변경 전체의 diff를 `--source`로 넘기고, `--rules`는
  사용자나 프로젝트가 보고에 대해 정한 규칙이 있을 때만 넘긴다. 기존 글의 일부만 고쳤다면 그 글의 diff도
  `--source`로 넘긴다.
- 이 명령은 먼저 글만 보고 판단할 수 있는 패턴을 검사하고, 걸린 것이 있으면 거기서 멈춘다. 지적마다 고친다. 그다음
  대화 맥락이 없는 검토자가 넘긴 규칙과 원본만으로 초안을 검토한다.
- 종료 코드 0이면 검토한 글을 그대로 올린다. 1이면 지적마다 글 전체에 반영하고 다시 실행한다. 지적받은 문장을
  남기려면 그 이유를 `--note`로 넘겨 다음 실행이 판단하게 한다. 지적이 없는 실행이 나온 뒤에만 올린다.
- 검토자까지 간 실행만 센다. 그런 실행을 세 번 해도 지적이 남으면 아무것도 올리지 말고, 남은 지적을 사용자에게
  보여 주고 묻는다. 최종 보고는 대신 고친 그대로 보내되, `text_review.py check --kind final-report <file>`가 지적을
  내지 않을 때 보내고, 검토에 관한 줄은 넣지 않는다.
- 종료 코드 3은 검토자가 판정을 내지 못했다는 뜻이다. 검토가 실행되지 않았다고 말하고, 외부에 올리기 전에 묻는다.

## 줄바꿈

- GitHub 이슈, 풀 리퀘스트, 댓글 본문과 그 밖에 원본의 줄바꿈이 화면에도 줄바꿈으로 표시되는 대상에서는 일정
  너비로 줄을 나누지 않고 각 문단과 각 목록 항목을 원본 한 줄에 쓴다. 에이전트를 위한 글에도 적용한다.
- Confluence에 게시할 Markdown 문서 또는 렌더링된 한 줄마다 원본 한 줄을 요구하는 프로젝트의 Markdown 문서에서는
  다음을 따른다.
  - 한 주제의 연속된 문장들은 한 문단에 두고 주제가 바뀌는 곳에만 빈 줄을 넣는다. 같은 주제의 한 문장짜리 문단을
    연달아 두지 않는다.
  - 문단에 여러 줄이 필요하면 의미가 끊기는 문장 끝에서 문단 안의 각 줄을 `<br>`로 끝낸다. 한 줄에 한 문장 또는
    밀접하게 연결된 두 문장을 둔다. 문장 중간에서는 줄을 나누지 않는다.
  - 같은 종류의 항목이 세 개 이상이면 도입 문장과 목록으로 쓴다.
  - 다음 표나 그림만 소개하면서 앞 문단의 주제를 이어 가는 한 문장짜리 문단은 앞 문단의 마지막 줄로 넣는다.
- 이런 글을 게시하거나 마무리하기 전에 `python3 <Source directory>/scripts/markdown_line_breaks.py FILE`을 실행한다.
  GitHub 본문에는 `--max-chars 0`을 추가한다. 작업 흐름에서 로컬 파일을 쓰지 않으면 FILE에 `-`를 지정하고 텍스트를
  표준 입력으로 전달한다. 모든 지적 사항을 고친다.

## 읽기 쉬운 공유 글

이 절은 답변으로 요청받은 요약을 포함한 요약, 동료와 공유하는 문서, Jira 이슈 본문과 댓글, 풀 리퀘스트 설명에
적용한다. `skill-issue-creator`가 쓰는 이슈 본문처럼 코딩 에이전트를 위한 글은 대신 자체 규칙을 따른다.

- 한국어에서는 에이전트 지침의 영어 용어를 직역하지 않고 문맥에 맞는 뜻으로 쓴다. 예를 들어 "contract"는 계약
  대신 규칙, 응답 형식, 정해 둔 동작으로 쓴다. 영어 용어는 문자 그대로의 식별자일 때만 유지한다.
- 독자가 결정이나 규칙을 이해하는 데 영향을 주지 않는 숫자는 뺀다. 필요한 숫자는 대응하는 값과 비교하거나 합계를
  세부 항목으로 나누는 표에 제시하고, 문장 안에 숫자를 나열하지 않는다. 임계값 같은 규칙 상수와 예시에 필요한
  값은 본문에 둔다. 검사에 대해서는 실행한 테스트 수 대신 동작과 조건 등 무엇을 확인했는지 밝힌다.
- 곁의 그림이나 표가 이미 보여 주는 사실은 그림이나 표를 남기고 되풀이하는 문장을 지운다. 앞에는 무엇을 보여
  주는지 한 문장만 남기고, 뒤에는 그 안에 없는 사실만 덧붙인다.
- 더 상세한 원본을 요약할 때는 결정, 이유, 절마다 대표 예시 하나를 남긴다. 전체 목록, 항목별 표, 구현 세부 사항은
  상세 원본에 둔다. 표의 셀에는 요약에서 다루는 항목만 적고 목록 대신 구분자로 연결한다.
- 기존 글을 줄이거나 다시 쓴 뒤에는 이전 글과 대조해 독자에게 필요한 조건, 예외, 범위, 결정 시점 중 빠진 내용을
  모두 복원한다. 이 대조를 맡은 독립 검토자에게는 변경 요약이 아니라 두 버전을 모두 제공한다.
