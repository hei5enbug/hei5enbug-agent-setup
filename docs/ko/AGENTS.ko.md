# 저장소 개발 지침

> 영어 원본: [AGENTS.md](../../AGENTS.md)
> 이 문서는 사람을 위한 비권위 한국어 번역본이다. 에이전트 실행 시 읽거나 사용하지 않는다.

> 이 지침은 이 저장소를 개발할 때만 적용한다.
> 플러그인 훅은 `instructions/session/`만 불러오며 이 파일은 불러오지 않는다.
> `instructions/` 아래 내용은 사용자에게 배포되는 플러그인 실행 동작이며 저장소 개발 규칙이 아니다.
> 그 실행 규칙은 이 저장소 작업에도 적용한다. 호스트가 불러오지 않았다면
> `instructions/session/core.md`, `instructions/session/common.md`, 현재 호스트용 파일을 먼저 읽는다.

- 구현 전에 요구사항을 검토한다. 잘못되었거나 정의되지 않은 용어, 여러 가지 가능한 해석,
  모순 또는 누락된 결정 때문에 결과, 범위, 계약 또는 완료 조건이 실질적으로 달라질 수 있으면
  가능한 해석과 영향을 설명하고 사용자에게 질문한다. 코드, 스키마, 용어집 또는 기존 합의로
  해석이 하나로 확정되면 그 근거를 밝히고 적용한다. 사용자만 내릴 수 있는 결정이 확정될 때까지
  파일을 수정하거나 외부 상태를 변경하지 않는다. 답변을 미리 전제하지 않는 읽기 전용 조사만
  계속할 수 있다.
- 훅, 에이전트, 스킬, 설정 또는 플러그인 구조를 변경하기 전에 변경하는 영역에 해당하는 Claude Code와 Codex의
  최신 공식 문서 페이지를 확인한다. mod, 훅 이벤트, 설정, 에이전트 옵션 같은 기능도 확인 대상에 포함한다.
  필요를 충족하는 지원 기능이 있으면 직접 만든 코드보다 그 기능을 우선하고, 확인한 기능과 그 방안을 고른
  이유를 밝힌다.
- 이 저장소의 모든 변경은 일반 사용 시 반복해서 드는 토큰과 컨텍스트 비용, 그리고 출력 품질을 둘 다
  개선하거나 최소한 유지해야 한다. 둘이 충돌하면 품질이 우선한다(소유자 결정, 2026-10-27). 측정한 품질이 더
  높은 선택지를 고르고, 토큰을 아끼려고 품질을 낮추는 선택지는 채택하지 않으며, 늘어난 비용은 측정값과 함께 변경
  보고에 기록한다.
  정확성과 필수 검증을 유지하면서 불필요한 지침 로딩, 중복 읽기, 도구 호출과 내용 중복을 줄인다.
  불러온 지침과 검증 결과는 관련 입력이 바뀌지 않은 동안에만 재사용한다.
  로컬 작업에서는 변경의 영향을 받는 검사를 실행하고, 해결되지 않은 위험이 있으면 범위를 넓힌다.
- 항상 로드되는 표면, 즉 스킬 description, `SKILL.md` 본문, 세션 지침 파일에는 그 표면을 쓰는 모든 실행에 필요한
  규칙만 둔다. 특정 조건에서만 필요한 규칙은 참조 파일로 옮기고, 표면에는 "<동작> 전에 <참조>를 읽는다." 형태의
  한 줄 항목만 남긴다. 그 참조를 읽는 일과 참조가 없을 때 멈추는 일은 세션 코어의 조건부 지침 규칙을 따른다.
  이슈를 구현하는 변경은 품질 평가 결과와, 바뀐 항상 로드 텍스트의 변경 전후 크기를 줄 수나 토큰으로 보고한다.
- 사람이 읽는 모든 영어 Markdown 파일에는 의미가 완전히 같은 한국어 번역본을
  `docs/ko/<저장소 루트 기준 원본 경로의 마지막 .md를 .ko.md로 바꾼 경로>`에 유지한다.
  원본과 번역본을 함께 수정, 이동 또는 삭제한다. 각 번역본은 제목으로 시작하고, 그다음 인용 블록에서
  상대 경로로 영어 원본을 링크하며 비권위 문서이고 실행 중에는 절대 읽지 않는다고 밝힌다.
  `skills/`, `agents/`, `instructions/` 안에는 `.ko.md` 파일을 두지 않으며, 이 폴더 아래의 파일에서
  `.ko.md` 파일로 링크하지 않는다. `README.md`처럼 루트에 있는 독자용 문서만 한국어 번역본을 링크할 수 있다.
  코드, 스키마, 테스트 자료, 생성 아티팩트 또는 영어가 아닌 문서는 복제하지 않는다.
- 스킬을 변경하기 전에 `skills/skill-builder/SKILL.md`의 현재 내용이 이미 로드되어 있지 않으면 읽는다.
  직접 수정할 때는 "Portability contract", "Core loop", "Translated mirrors" 절만 읽고, 스킬을 새로 만들거나 평가
  절차를 탈 때는 파일 전체를 읽는다. 변경에 맞는 직접 수정 또는 평가 절차를 따른다. 플러그인 구조, 매니페스트 또는 훅을
  변경할 때는 호스트가 `plugin-creator`를 제공하면 사용하고 기존 플러그인 계약을 보존한다.
- 공통 동작은 하나의 기준 원본에 두고 실제 호스트 차이만 분리한다. 세션 지침이 이미 규정한 규칙은
  그곳에만 두고, 다시 쓰지 말고 참조한다.
- [규칙 집행](docs/rule-enforcement.ko.md)은 글로 쓴 규칙마다 그 규칙을 집행하는 검사를 짝지어 둔다. 사용자 교정이 검사로
  집행되지 않는 기존 규칙을 되풀이하면 같은 변경에서 그 파일이 설명하는 대로 한 단계 올리고 해당 행을 갱신한다.
  검사가 실수를 불가능하게 만들면 그 글로 쓴 규칙을 지운다.
- 이슈를 만들기 전에 기존 이슈를 검색한다. 이슈, 풀 리퀘스트, 댓글, 커밋 메시지는 영어로 쓰고 기존 이슈의
  관례를 따른다. 파일, 커밋 또는 메시지에 담을 수 있는 내용은 이 파일 끝의 "공개 경계" 절을 따른다.
- 저장소 구현에는 Claude Code 플러그인 작업자 서브에이전트를 기본으로 사용한다. 나머지 경로는
  `.codex/agents/`의 Codex 프로젝트 역할을 사용한다.

  | 역할 | 기본 이름 | 모델 / 추론 강도 | fallback 이름 | 모델 / 추론 강도 |
  |---|---|---|---|---|
  | 범위가 정해진 구현 및 디버깅(쉬운 작업) | `haiku_worker` | `claude-haiku-5-5` / `xhigh` | `worker` | `gpt-6.1-sol` / `high` |
  | 범위가 정해진 로컬 읽기 전용 근거 조사 | `scout` | `gpt-5.6-luna` / `xhigh` | `haiku_scout` | `claude-haiku-5-5` / `xhigh` |
  | 승인된 내용을 반영하는 기계적인 문서 편집 | `writer` | `gpt-6.1-sol` / `high` | `haiku_writer` | `claude-haiku-5-5` / `xhigh` |
  | 완료된 범위 한정 변경을 한 번 읽기 전용으로 최종 검토 | `code_reviewer` | `gpt-6.1-sol` / `high` | `opus_code_reviewer` | `claude-opus-5-5` / `high` |

  `haiku_worker`와 `sonnet_worker`는 플러그인의 `hei5enbug-agent-setup:worker`와
  `hei5enbug-agent-setup:sonnet-worker` 서브에이전트를 가리킨다. 나머지 `haiku_*` 이름과 `opus_code_reviewer`는
  별도 Claude Code CLI 프로세스에 붙이는 과제 이름이며, 등록된 `--agent` 이름이 아니다. `worker`, `scout`, `writer`, `code_reviewer`는 Codex 프로젝트 역할이다.
  각 역할에는 Claude에서 GPT로, GPT에서 Claude로 전환하는 다른 모델 계열의 fallback 하나만 둔다.
  기본 실행 파일, 인증, 할당량, 역할, 요청한 설정 또는
  신뢰할 수 있는 설정 근거를 사용할 수 없을 때만 지정된 fallback을 사전 승인된 경로로 사용한다. 전환 이유와
  선택한 경로를 알린다. 기본 작업자가 이미 시작됐다면 먼저 중지하고 부분 결과를 확인한 뒤, 확인된 미완료
  작업만 같은 범위, 권한, 검사와 함께 넘긴다. 과제마다 표에 지정된 fallback 하나를 최대 한 번 시도한다.
  그것도 사용할 수 없으면 메인 세션에서 진행한다. 기본 경로와 같은 인증, 할당량 또는 기능 문제에 막힌 것이
  확인된 fallback은 시도하지 않는다. fallback으로 사용자 결정 누락을 해결하거나 권한 제한이나
  실패한 완료 검사를 우회하지 않는다.

  이 저장소의 라우팅은 이 역할에 대한 플러그인의 모델 및 추론 강도 경로를 덮어쓰고,
  기계적인 문서 작업을 `writer`에, 범위가 정해진 최종 검토를 `code_reviewer`에 배정한다.
  플러그인의 나머지 작업 소유권, 권한, 검증 규칙은
  계속 적용한다. 호스트가 지원하면 표에 나온 모델과 추론 강도를 명시적으로 요청하고, 역할 결과를
  사용하기 전에 기본 역할과 fallback 역할 모두 실제 호스트 실행 기록에서 모델과 추론 강도를 확인한다.
  기본 역할에 고정된 모델을 덮어써 fallback을 호출하지 말고, 지정된 경로를 해당 호스트에서 실행한다.
  Codex 프로젝트 역할은 새 Codex 세션부터 적용된다.

  Claude fallback에는 대응하는 기본 Codex 역할의 `developer_instructions`와 범위가 정해진 과제를
  stdin으로 전달한다. 각 역할의 범위는 이 원본 하나에서 유지한다. `claude -p`에 표의 전체 모델 ID와
  추론 강도, `--output-format json --permission-mode dontAsk --strict-mcp-config`를 지정한다.
  `haiku_scout`과 `opus_code_reviewer`에는 `--tools Read Grep Glob --allowedTools Read Grep Glob`를 추가한다.
  `haiku_writer`에는 `--tools Read Grep Glob Edit Write --allowedTools Read Grep Glob`와 함께 배정된 각
  Markdown 파일과 미러에 대한 `Edit(//<absolute allowed path>)`를 추가한다. Edit 규칙은 Write에도 적용되고,
  `//`는 절대 경로를 뜻한다. 배정된 검사는
  메인 세션이 실행한다. 이 fallback에는 셸, 네트워크, 위임 도구를 제공하지 않는다.
  JSON `modelUsage`가 요청한 모델을 나타내고 기존 실제 설정 검사에서 추론 강도를 확인했을 때만 결과를
  사용한다. CLI로 재개할 때 모델, 추론 강도, 도구 제한, 과제 범위를 다시 적용한다. 이 선택은 복구 정책이며
  fallback의 품질이나 비용 우위를 측정해 입증한 주장이 아니다.

  선택한 구현 경로의 대안을 명시적으로 비교할 때는 완전히 해결한 과제 수를 먼저 보고,
  완료율이 비슷하면 성공 건당 비용과 추가로 얻는
  코드 품질을 비교한다. 실패한 시도의 비용도 포함한다. 품질과 비용을 임의의 비율로 합치거나
  보고서의 측정 한계를 무시하지 않는다.
  쉬운 작업은 범위가 정해진 로컬 읽기 전용 근거 조사에 `scout`을, 코디네이터가 승인한 기계적인
  Markdown 및 미러 편집에 `writer`를 사용한다. `scout`의 `gpt-5.6-luna`/`xhigh` 고정값은 사용자가 명시적으로
  선택한 값이며, 이전 로컬 비교가 그 품질을 입증하는 것은 아니다. `writer`는 2026-10-17 미러 편집 과제 세 개를
  블라인드로 비교한 뒤 `gpt-6.1-sol`/`high`로 바꿨다. Sol은 기대 항목 18개 중 17개를 통과하고 고칠 곳이 한 곳이며
  토큰도 적었고, Luna는 9개를 통과하고 고칠 곳이 19곳이었다. Claude Code에서는 `writer`를 역할 정의를
  `--instructions`로 넘긴 `role_runner.py language`로 실행한다. 메인 세션은 구현을
  배정하기 전에 원인, 수정 가능한 경로, 변경 요구사항, 실행 가능한 완료 검사를 정한다.

  메인 세션은 난이도와 사용량에 따라 구현 작업자를 고른다.

  | 작업 | 작업자 |
  |---|---|
  | 쉬움: 편집 내용이 정해져 있고 검사가 모두 확인하는 응집된 변경 하나 | `haiku_worker`: 세션 줄 "Worker agent model"이 `claude-haiku-5-5`의 `xhigh`를 보일 때 `hei5enbug-agent-setup:worker` 서브에이전트, 그렇지 않으면 `sonnet_worker` |
  | 보통 또는 어려움: 동작 변경, 여러 파일, 파싱, 보안, 동시성 | `sonnet_worker`: `hei5enbug-agent-setup:sonnet-worker` 서브에이전트(`claude-sonnet-5-5` / `high`) |
  | Claude 사용 한도에 걸리거나 Claude worker를 사용할 수 없음 | `worker`(`gpt-6.1-sol` / `high`): Claude Code에서는 허용 경로가 든 폴더에서 `role_runner.py implementation --fallback --instructions <worker 역할 정의>`를 실행하고, Codex에서는 `worker` 역할을 쓴다 |

  `claude -p` 프로세스 대신 이 플러그인 서브에이전트를 띄운다. 2026-10-22에 auto 모드 분류기는 승인 가드를 고치는
  `claude -p` 작업자를 자기 수정으로 막았고, `dontAsk`는 가드가 묻는 명령에서 작업자를 멈췄다. 반면
  `sonnet-worker` 서브에이전트는 같은 종류의 변경을 막힘 없이 했고, 서브에이전트 기록에 `claude-sonnet-5-5`의
  `high`가 남았다.

  2026-10-17에 실제 승인 가드 과제 세 개(분류, 세션 상태, 모드)를 Sonnet `high`와 Sol `high`로 한 번씩
  돌렸다. 여섯 실행 모두 코디네이터의 검사를 통과했다. 블라인드 검토에서 고칠 곳은 Sol이 모두 5곳,
  Sonnet이 10곳이었고, Sol은 Sonnet의 출력 토큰 30~54%를 쓰고 더 빨리 끝났다. 이어서 쉬운 작업 두 개를
  Haiku, Sonnet, Sol `high`로 한 번씩 돌렸다. 설정 편집은 어느 모델도 고칠 곳이 없었고 Haiku의 API 비용은
  Sonnet의 약 9분의 1이었다($0.018 대 $0.159). 파일·파싱 경계 처리가 있는 사용량 기록 읽기 스크립트는 고칠 곳이
  Sol 1곳, Haiku 4곳, Sonnet 6곳이었다. 모델과 과제마다 한 번씩만 돌린 근거는 얇고 Sol의 비용은 금액으로
  재지 못했다. 플러그인의 `implementation_worker` `auto` 경로가 같은 규칙을 런타임에 적용한다.
  2026-10-20에 사용자는 구현은 Claude에, 조사와 최종 검토는 GPT에 유지하도록 보통·어려운 작업을 Sonnet으로 옮겼으며,
  Sol은 대체 경로가 되었다.

  플러그인 에이전트의 정의를 덮어쓰거나 Anthropic 모델을 Codex 역할에 넣지 않는다. CLI로 재개할 때
  모델과 추론 강도를 다시 지정하고, 작업자의 결과를 사용하기 전에 기존 준비 확인과 실제 호스트 기록
  검사를 따른다. 작업자는 범위를 넓히는 대신 새 원인이나 누락된 결정을 메인 세션에 보고한다.

  합쳐진 최종 diff에 대해 변경 크기와 작성 모델 계열에 맞춰 읽기 전용 최종 검토를 한 번 실행한다.

  | 변경 | 최종 검토 |
  |---|---|
  | 사소함: 오타, 문구, 버전, 메타데이터 수정, 번역, 또는 검사가 모두 확인하는 기계적 수정 | 없음 |
  | 범위 한정, Claude 작성: 완료 검사가 분명한 구성 요소 하나이고, 공개 계약, 보안, 동시성, 훅, 가드 변경이 없음 | `role_runner.py reviewer --model gpt-6.1-sol`이며, runner 기본값인 `high`로 실행된다 |
  | 복잡함, Claude 작성: 여러 구성 요소, 공개 계약, 보안, 동시성, 훅이나 가드 | `role_runner.py reviewer --model gpt-6-astra --effort xhigh` |
  | GPT 작성(`gpt-6.1-sol`로 작성한 작업 포함) | `role_runner.py reviewer --model claude-opus-5-5`, 복잡하면 `--effort xhigh`와 함께 `claude-fable-5-1` |

  이 검토는 요청의 모든 작업이 끝나고 검사를 통과한 뒤 합쳐진 최종 diff를 대상으로 질문 없이 자동으로 한 번 실행한다.
  더 이른 검토에는 사용자의 승인이 필요하다. 검토자에게 최종 diff, 요구사항, 검사 근거를
  전달한다. Claude가 작성한 변경에서 `gpt-6-astra` 검토자를 사용할 수 없으면 `code_reviewer` 경로를 대신 쓴다. 메인 세션이
  지적 사항을 검증하고 완료 여부를 결정하며, 두 번째 검토는 시작하지 않는다.
  이 검토의 정확도는 Frontier v4에서 측정하지 않았다.

  Frontier v4는 모델과 추론 강도별로 23개의 까다로운 동작 재현 과제를 한 번씩 수행한다. 쉬움/보통/어려움
  등급을 정의하지 않으며 문서 작업도 평가하지 않는다. 위 라우팅은 이 저장소의 정책이며 벤치마크
  결과나 일반적인 모델 우위 주장에 근거한 구분이 아니다.

  사용자는 범위가 정해진 구현에 Haiku xhigh를, 범위 한정 최종 검토에 Sol high를 선택했다. 이는 역할
  선호이며 Haiku가 Frontier v4의 완료율이나 비용 효율에서 앞선다거나 구현 점수가 리뷰 정확도를
  입증한다는 주장이 아니다. 보고서마다 하네스 버전과 비용 기준이 다르므로 비용은
  구독 요금이 아닌 API/목록 가격 추정치다. [Haiku 비교](https://vulcanbench.com/benchmarks/swe-v4-haiku55-vs-frontier.html),
  [Luna 비교](https://vulcanbench.com/benchmarks/swe-v4-gpt55-luna-v35.html),
  [VulcanBench 방법론](https://vulcanbench.com/methodology.html)을 참조한다. 문제 정의, 복잡한 근본 원인
  분석, 계획, 설계와 RFC, 승인 결정은 메인 세션에서 처리한다. `designer`, `reviewer` 역할은
  기존 호스트 경로를 그대로 사용한다.
- 이 저장소를 변경하기 전에, `tests/test_model_pins.py`의 `PINS_VERIFIED_ON`이 14일보다 오래됐으면
  `config/model-registry.json`의 `pins`에 있는 GPT Luna를 제외한 모든 모델 계열의 가장 새로운 정식 모델을
  확인하고 `PINS_VERIFIED_ON`을 그 날짜로 바꾼다. GPT Luna는 사용자가 명시적으로 선택을 바꿀 때까지
  사용자가 고른 `gpt-5.6-luna`를 유지하며, 기본 사고 강도는 `high`이고 사고 강도 규칙에 따라 `xhigh`를 쓴다
  (사용자 선택일 2026-10-20). 공식 [Claude 모델 개요](https://platform.claude.com/docs/en/about-claude/models/overview),
  [OpenAI 모델 카탈로그](https://developers.openai.com/api/docs/models), 각 호스트의 모델 카탈로그를 사용하고 미리보기
  모델은 제외한다. 계열에 더 새로운 릴리스가 있으면 같은 변경에서 `config/model-registry.json`의 `pins`와 모든 참조를
  갱신하고 `tests/test_model_pins.py`가 통과할 때까지 맞춘다. 실행 파일은 모델을 이 전체 ID로만 적는다. 별칭이나 실행 시점의
  최신 릴리스 조회는 추가하지 않는다.
- Orca CLI가 설치되어 있지 않아 테스트를 건너뛰면, 검사가 통과했다고 보고하기 전에 Orca를 설치하고 다시 실행할지
  사용자에게 묻는다.
- `HEAD`에서 닿는 가장 새로운 `v<major>.<minor>.<patch>` 태그가 릴리스 기준이다. 매니페스트에만 있는 버전은 이미
  `main`에 있거나 로컬에 설치돼 있어도 계획한 다음 버전이지 기준이 아니다. 배포되지 않은 작업 전체를 그 계획한 버전
  하나에 유지한다. 기준 이후 첫 변경이 같은 커밋에서 그 버전을 정하고, 이후 변경은 다시 올리지 말고 그 버전에 합친 뒤
  자기 커밋 안에서 아래 표로 자리를 다시 정한다. 로컬 반복 작업마다 의미 버전을 올리지 않는다. 태그를 단 릴리스만
  설치한다. 사용자가 아직 릴리스하지 않은 작업의 설치를 요청하면 먼저 태그를 달아, 다음 변경이 다음 계획 버전에서
  시작하게 하고 재설치에 cachebuster가 필요 없게 한다. 버전을 바꾸기 전에 기준 태그와 계획한 버전을 사용자에게 밝힌다. 두 플러그인 매니페스트,
  `pyproject.toml`, `uv.lock`의 버전을 일치시킨다. 릴리스는 태그만 단다. 릴리스하거나 버전만 바꾸는 별도 커밋은 만들지
  않는다. 사용자가 릴리스를 배포하면 `HEAD`에서 `README.md`의 모든 개발 검사를 실행하고 `HEAD`에 `v<version>` 태그를 단
  뒤 태그를 푸시한다. `tests/test_release_version.py`는 기준보다 낮은 버전, 기준 이후 두 개 이상의 계획 버전(더 낮은 단계의
  다음 버전을 나중에 더 높은 단계로 다시 고른 경우는 제외), 기준 이후
  변경이 있는데도 계획 버전이 기준과 같은 경우, 기준 이후 버전 파일만 바꾸는 커밋을 거부한다.
  배포되지 않은 변경 중 영향도가 가장 높은 항목을 기준으로 다음 의미 버전을 정한다.

  | 자리 | 적용 기준 |
  |---|---|
  | 첫 번째 | 하네스 아키텍처나 핵심 제어 로직이 기존 실행 계약을 대체할 정도로 바뀐다. |
  | 두 번째 | 스킬을 추가, 제거 또는 통합하거나 목표, 요구사항 또는 외부 동작 계약을 바꾼다. |
  | 세 번째 | 기존 스킬의 목표와 요구사항을 유지한 채 성능, 신뢰성, 평가 품질 또는 출력 품질을 개선한다. 이런 변경이 여러 개여도 한 번만 올린다. |

## 공개 경계 (보호됨)

이 저장소, 그 이력의 모든 커밋, 그리고 이 저장소의 모든 태그, 브랜치, 이슈, 풀 리퀘스트, 리뷰, 댓글은 공개된다.
어느 것에도 다음 내용을 담아서는 안 된다.

- 실제 기기의 로컬 절대 경로 또는 실제 사용자 이름, 호스트 이름, 홈 폴더
- 비밀값, 자격 증명, 토큰, 비공개 키, 계정 식별자, 내부 URL 또는 그 밖의 보안상 민감한 내용
- 비공개 조직이나 공개되지 않은 플러그인에만 해당하는 내용: 이름, 제품, 서비스, 저장소, 인프라, 스키마,
  티켓 키, 사람 또는 채널

예제, 테스트 자료, 평가 데이터에는 `example.com`, `/home/test`, `/tmp/work`, `<plugin-root>`, `ABC-123`,
`demo` 스키마처럼 명백히 가상의 값만 쓴다. 이 저장소는 범용으로 유지하며, 이 저장소에 의존하는 플러그인의
이름을 쓰거나 그 플러그인을 설명하지 않는다.

매번 커밋하기 전에 `python3 -m pytest tests/test_public_boundary.py`를 실행하고 스테이징된 diff와 커밋 메시지에
위 값이 있는지 살핀다. 발견한 내용은 모두 고친 뒤 커밋한다. 공개된 이력에서 이런 값을 발견하면 작업을 멈추고
소유자에게 보고하며, 소유자의 명시적 승인이 있을 때만 이력을 다시 쓴다.

소유자가 현재 대화에서 이 절을 이름으로 지목하고 변경을 명시적으로 요청한 경우에만 이 절을 변경, 완화, 이동
또는 삭제한다. 그 변경은 다른 변경 없이 단독 커밋으로 만들고, 같은 커밋에서 `tests/test_public_boundary.py`의
절 해시도 갱신한다. 다른 작업을 요청받았다는 이유로 이 절을 바꿀 권한이 생기지는 않는다.
이 절은 이 파일의 마지막에 둔다.
