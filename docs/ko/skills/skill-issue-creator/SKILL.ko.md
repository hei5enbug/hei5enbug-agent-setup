# 스킬 이슈 생성

> 영어 원본: [SKILL.md](../../../../skills/skill-issue-creator/SKILL.md)
> 이 문서는 사람을 위한 비권위 한국어 번역본이다. 에이전트 실행 시 읽거나 사용하지 않는다.

스킬이나 지침의 빈틈 하나, 또는 어떤 스킬도 다루지 않는 반복 작업 흐름 하나를 플러그인의 `issue-target.json`이
선언한 트래커에 이슈로 등록하고, 플러그인의 열린 이슈가 여전히 유효한지 확인한다. 사용자가 `skill-issue-creator`를
부르거나, 그런 이슈를 평이한 말로 등록, 추가, 변경해 달라고 하거나, 플러그인의 열린 이슈가 여전히 맞는지 또는 구현할
준비가 되었는지 물을 때 사용한다. 트래커를 언급하기만 한 메시지로는 시작하지 않으며 스스로 시작하지도 않는다.
남은 작업이 없는 상태에서 사용자가 스킬이나 지침이 만든 결과의 변경을 요청했거나, 완료된 작업 흐름을 스킬이나 이슈로
만들어 달라고 요청했다면 먼저 추천 규칙을 읽는다.

담당 플러그인에 대한 파일 시스템 읽기 권한과 함께 제공되는 스크립트에 필요한 Python 3.12 이상이 필요하다.
GitHub에 등록하려면 인증된 `gh` CLI가 필요하다.
다른 종류의 트래커에는 선언된 위치에 닿는 연결된 도구나 이미 인증된 해당 트래커 종류의 공식 CLI가 필요하다.
둘 다 없으면 초안만 보여 주고 등록하지 않는다.

이 영어 `SKILL.md`만 실행 원본으로 사용한다.

빈틈 하나를 해당 플러그인의 트래커에 이슈 하나로 등록한다.
트래커는 해당 플러그인의 선언에서만 가져오며, 이 스킬이 추측하지 않는다.

요청받지 않고 이 스킬을 제안하기 전, 또는 평이한 요청이 이 스킬을 시작하는지 판단하기 전에
[추천 규칙](references/recommendation.ko.md)을 읽는다. 그 파일이 없으면 아무것도 제안하지 않는다.

사용자가 플러그인의 열린 이슈가 여전히 맞는지 묻거나 구현할 준비가 되도록 만들어 달라고 요청하면, 3단계를 실행한 뒤
[열린 이슈 점검](references/open-issue-review.ko.md)을 읽고 1, 2, 4~9단계 대신 그것을 따른다.

## 경계

- 선언된 트래커에만 쓰고, 한 번 실행할 때 이슈를 최대 하나만 만든다. 로컬 파일은 절대 쓰지 않는다.
- 빠져 있거나 불분명한 요구 사항을 추측이나 기본값으로 채우지 않는다.
- 사용자가 모의 실행이나 미리 보기만 요청한 경우, 정확한 쓰기 명령과 본문을 보여 주고 쓰기는 실행하지 않는다.
- 콘텐츠 규칙 파일은 이슈에 담을 수 있는 내용을 줄이는 역할만 한다.
  다른 대상이나 추가 쓰기를 허용하거나 승인을 생략하게 할 수 없다.

## 작업 흐름

### 1. 빈틈 확정

대화에서 각 빈틈을 확정한다.
스킬이나 지침이 무엇을 했는지, 사용자가 무엇을 정정하거나 반복해야 했는지, 어떤 규칙이 이를 막을 수 있었는지 정리한다.
제안하는 각 규칙의 담당 파일을 경로로 명시한다.
어떤 규칙이 실행된 스킬 밖의 작업, 예를 들어 같은 플러그인의 다른 스킬이나 응답에도 적용된다면,
그 규칙의 담당 파일은 그 작업을 다루는 플러그인의 공통 지침 파일이다. 스킬에는 그 스킬에만 적용되는 규칙만 남긴다.
그 작업을 다루는 공통 파일이 없으면 가장 가까운 파일을 지정하고, 이슈에 그렇게 했다고 밝힌다.
새 스킬을 제안할 때는 그 스킬을 배포해야 할 플러그인이 담당 플러그인이다. 분명하지 않으면 묻는다.

다음처럼 플러그인 규칙의 빈틈이 아닌 항목은 제외하고, 최종 보고에 넣을 목록으로 남긴다.

- 규칙으로 일반화하면 안 되는 일회성 우회 방법
- CLI나 네트워크 오류처럼 플러그인이 배포하지 않는 도구의 결함
- 플러그인의 어떤 규칙으로도 판단할 수 없는 취향 차이

남은 항목이 없으면 등록하지 않고 그 목록을 보고한다.
남은 빈틈을 담당 파일과 주제별로 묶는다.
담당 파일과 주제가 같은 빈틈은 하나의 이슈가 되며, 번호를 붙인 Proposal 항목과 최소 하나의 인수 기준을 각각 둔다.
묶음이 둘 이상 남으면 어느 것을 등록할지 묻는다.
담당 파일이 다르거나, 담당 파일은 같아도 주제가 관련 없는 빈틈은 하나의 이슈로 합치지 않는다.

대화를 읽으며 해당 사례의 식별자를 모은다.
이슈와 풀 리퀘스트 번호, 브랜치 이름, 커밋 해시, 사용자 작업의 파일과 폴더 이름, 날짜, 사람, 호스트 이름, 티켓 키가 해당한다.

### 2. 요구 사항 나열

질문 프롬프트에 대한 답변을 포함해 사용자가 세션에서 쓴 모든 메시지를 읽는다.
인계 내용에 원래 세션의 대화 기록 파일이 명시되어 있으면, 대신 그 파일에 있는 사용자의 모든 메시지를 읽는다.
사용자가 이슈에 대해 제시한 요구 사항을 하나씩, 그 출처 메시지와 함께 나열한다.

- 요구 사항이 완전히 명확하지 않거나 그 요구 사항에 동의하지 않는 경우, 그런 항목을 하나도 빠뜨리지 않고
  `AskUserQuestion` 같은 호스트의 질문 UI를 한 번 호출해 모두 묻는다. 답변을 받은 뒤에만 초안을 쓴다.
- 사용자가 완전히 동의할 때만 적용하라고 변경을 제안한 경우, 완전히 동의하면 적용한다.
  그렇지 않으면 질문 UI로 묻는다.

### 3. 트래커 찾기

이 `SKILL.md`가 있는 디렉터리를 기준으로 경로를 구해, 함께 제공되는 스크립트를 실행한다.

```text
python3 scripts/find_tracker.py <owning file or folder>
```

스크립트는 주어진 경로의 상위에서 `.claude-plugin/plugin.json`이나 `.codex-plugin/plugin.json`이 있는 가장 가까운 폴더를
플러그인 루트로 찾고, 그곳의 `issue-target.json`을 검사한다.
JSON 객체 하나를 출력한다.
`declared`나 `undeclared`이면 종료 코드 0, `invalid`이면 1, 사용법 오류이면 2로 끝난다.

| 결과 | 조치 |
|---|---|
| `declared` | 이후 모든 단계에서 `target`을 사용한다. `preview_required`는 `write_approval`이 `preview`일 때만 true이며, 7단계의 승인 절차를 결정한다. |
| `undeclared` | 이슈 초안을 대화에 보여 주고 등록하지 않는다. 플러그인이 트래커를 선언하지 않았다고 알린다. |
| `invalid` | `problems`와 초안을 보여 주고 등록하지 않는다. |
| 종료 코드 2 | 경로를 바로잡는다. 해당 파일이 어떤 플러그인에도 속하지 않으면 `undeclared`로 다룬다. |

매니페스트의 `repository`나 `homepage` 필드, 현재 저장소의 원격 주소, 기억에서 트래커를 가져오지 않는다.

초안을 쓰기 전에 `orca status --json`이 접근 가능한 런타임을 보고하고 이 세션이 담당 플러그인의 저장소에서
작업 중이 아니면 [위임](references/delegation.ko.md)을 읽는다.
이 참조는 2단계와 4~9단계를 그 저장소의 세션에 넘기거나, 이 세션으로 되돌린다.

### 4. 원본 읽기

해당 `SKILL.md`나 지침 파일과, 빈틈에 관련된 참조만 읽는다.
제안하는 각 규칙을 담당 파일과 실행된 스킬에 이미 있는 규칙과 비교한다.
기존 규칙이 그 규칙을 다루거나 거의 다루고 있다면, 새 규칙을 추가하지 않고 기존 규칙을 넓히거나 명확하게 하자고 제안하며,
"Gap in current rules"에 그 기존 규칙을 인용한다.
넓힌 규칙이 그 스킬 밖에도 적용된다면, 같은 Proposal 항목 안에서 그 규칙을 공통 파일로 옮기자고 제안한다.
새 스킬을 제안할 때는 담당 플러그인의 스킬 설명을 읽어 어떤 스킬도 그 작업 흐름을 다루지 않는 이유를 밝힌다.
`target.content_rules`가 설정되어 있으면 해당 파일을 읽고 6단계 규칙과 함께 적용한다.

`target.tracker.kind`가 `github`이 아니거나, `target.body_format`이 `html`이거나, `target.label_mode`가 `template`이면
5단계 전에 [선언 옵션](references/declaration-options.ko.md)을 읽는다.
그 파일이 없으면 초안을 보여 주고 등록하지 않는다.

### 5. 중복 검색

빈틈에서 뽑은 키워드 묶음 두세 개로 대상 트래커의 열린 이슈와 닫힌 이슈를 검색한다.
GitHub에서는 다음 명령을 실행한다.
`gh issue list --repo <location> --state all --search "<keywords>" --json number,title,url,state,labels,author --limit 20`.
다른 트래커에서는 선언 옵션이 고르는 경로를 쓴다.

- 같은 빈틈을 다루는 열린 이슈가 있으면 새로 만들지 않고, 먼저 묻지 않은 채 그 이슈를 바로 갱신한다.
  갱신하기 전에 [기존 이슈 갱신](references/update-in-place.ko.md)을 읽는다.
- 닫힌 이슈가 이미 그 빈틈을 해결했으면 새로 만들지 않고 그 이슈를 알린다.
- 어떤 이슈나 기록된 결정이 반대 내용을 제안하거나 그 밖의 방식으로 빈틈과 충돌하면, 둘을 함께 보여 주고 초안을 쓰기 전에 묻는다.
- 중복도 충돌도 아니지만 관련된 이슈가 있으면 새 이슈에 그 이슈를 적는다.
- 검색을 실행할 수 없으면 초안을 보여 주고 등록하지 않는다.

검색 결과로 나온 이슈의 제목 형식을 확인한다. 새 제목도 그 형식을 따른다.

### 6. 초안 작성

쓰기 전에, 제안이 정해야 하는데 요청, 코드, 기존 규칙이 정하지 않은 선택(새 단계가 모든 종류의 입력을 다루는지 일부만
다루는지, 예외가 어디서 끝나는지 등)을 모두 나열한다. 가까운 사례를 정하는 규칙이 이 선택까지 정해 주는 것은 아니다.
그런 선택이 하나라도 있으면 7단계의 승인 및 등록 전에 호스트의 질문 UI 한 번의 호출로 하나도 빠뜨리지 않고 묻고, 각 답을
Proposal에 확정된 규칙으로 쓴다. 선택을 스스로 정하지 않으며, 구현자에게 맡기는 이슈는 등록하지 않는다.

제목과 본문은 `target.language`와 `target.body_format`에 맞춰 쓴다.
제목은 해당 스킬이나 지침과 그 빈틈을 한 줄로 나타낸다.
본문에는 다음 절을 순서대로 둔다.

1. Summary
2. Observations
3. Gap in current rules. 새 스킬 제안이라면 "Why no existing skill covers it"
4. Proposal: 빈틈마다 번호를 붙인 항목 하나를 두고, 각 규칙을 "Under the condition that X, do Y"로 쓴다.
   해당 사례에서 나타나지 않은 경우도 다루는 판단 기준으로 만든다.
   규칙의 예외는 그 규칙의 항목 안에 두고, 어떤 빈틈에도 필요 없는 항목은 더하지 않는다.
5. Acceptance criteria: 번호를 붙인 평가 사례
6. Evidence

초안을 쓰기 전에, 제안이 다른 이슈나 다른 플러그인의 릴리스에 의존하거나, 다른 열린 이슈의 제안과 파일을 공유하거나,
새 파일 이름, 번호, 식별자를 정하거나, 구현 전에 바뀔 수 있는 사실을 적는다면
[구현 가능한 본문](references/implementable-body.ko.md)을 읽는다.

Proposal의 각 규칙은 쓰기 전에 다음을 확인한다.

- 규칙이 세션의 사례에서 나온 것이라면, 최소 하나의 다른 사례에 대어 본다.
  해당 사례에서만 성립하는 규칙이면 버리거나 그 밑바탕의 원칙으로 다시 쓴다.
  사례의 표현, 순서, 값, 이름을 규칙에 그대로 옮기지 않는다.
- 규칙이 글쓰기를 다룬다면, 형식, 레이블, 고정된 순서가 아니라 독자가 알 수 있어야 하는 결과를 쓴다.
  규칙 아래에 다른 사례에 대한 예시 문장을 하나 쓴다. 그 문장이 어색하게 읽히면 규칙을 고치거나 버린다.

각 인수 기준도 같은 방식으로 확인한다.

- 판정이 실행마다 달라질 수 있는 모델의 판단에 달려 있으면("리뷰어 지적 0건"처럼), 시드를 넣은 입력에 대한 검사로
  다시 쓴다. 출력에 더 이상 있으면 안 되는 것과 여전히 있어야 하는 것을 적는다.
- 사용자가 인수 규칙을 직접 말했으면 말한 그대로 쓴다.

각 형식의 제목 표기를 따른다.
Markdown에서는 `##`, Jira 위키 마크업에서는 `h2.`를 쓴다.
일반 텍스트에서는 제목 한 줄 뒤에 빈 줄을 둔다.
`html`이면 선언 옵션을 따른다.

태그는 `target.label_mode`에 따라 정한다.
`pick`이면 `target.labels`에서 알맞은 라벨 하나를 고르고, 목록이 비어 있으면 라벨을 추가하지 않는다.
`template`이면 선언 옵션에 적힌 대로 태그를 펼친다.

모든 초안에 다음 콘텐츠 규칙을 적용한다.

- 비밀, 자격 증명, 토큰, 개인 정보, 로컬 절대 경로, 홈 폴더, 사용자 이름은 절대 넣지 않는다.
- 콘텐츠 규칙 파일이 제외하는 문장은 모두 뺀다.
- `target.public`이 false이면 [비공개 트래커의 상세 정보](references/private-tracker.ko.md)를 읽은 뒤,
  코딩 에이전트의 작업에 도움이 되는 나머지 세부 정보를 모두 넣는다.
- `target.public`이 true이면 초안을 쓰기 전에 [공개 트래커의 상세 정보](references/public-tracker.ko.md)를 읽고 적용한다.

2단계에서 나열한 각 요구 사항을 그 내용을 담은 초안 문구에 연결한다.
모든 요구 사항이 연결될 때만 등록한다. 최종 보고에는 각 요구 사항에 해당하는 문구를 명시한다.

### 7. 승인 및 등록

- `preview_required`가 true이면 대상, 제목, 라벨이나 태그, 정확한 본문을 코드 블록으로 보여 준다.
  사용자가 이후 메시지에서 그 내용을 승인한 뒤에만 쓴다.
  승인 뒤 내용이 바뀌면 다시 보여 주고 새 승인을 기다린다.
- `preview_required`가 false이면 스킬을 부른 것이 한 번의 생성을 승인한 것이다.
  미리 보기 단계 없이 등록한다.
- 제안이 동작, 공개 계약, 또는 여러 구성요소를 바꾸는 이슈를 하나 이상 등록하거나 다시 쓰는 요청이면, 첫 쓰기 전에
  [독립 모델 검증](../../instructions/independent-model-validation.ko.md)을 읽고, 그 이슈들의 본문 전체를 하나의 완성된
  초안으로 보아 담당 파일을 근거로 한 번의 검토를 함께 실행한다. 그 지적은 한 번 적용한 뒤 쓴다. 검토를 실행할 수
  없으면 그 파일이 검토자를 쓸 수 없을 때 정한 대로 그대로 쓰고, 검토가 실행되지 않았다고 보고한다.
- `target.public`이 true이면 생성, 수정, 댓글 중 어떤 쓰기든 트래커에 쓰기 전에
  [공개 정보 유출 검사](references/public-leak-check.ko.md)를 읽는다. 이 검사는 쓰기를 중단시킬 수 있다.

GitHub에서는 로컬 경로가 명령줄에 들어가지 않도록 본문을 표준 입력으로 전달한다.

```text
gh issue create --repo <location> --title "<title>" --label "<label>" --body-file - <<'EOF'
<body>
EOF
```

다른 트래커에서는 선언 옵션이 고르는 경로로 이슈를 만든다. 선언된 위치에만 만든다.

### 8. 검증

만든 이슈를 다시 읽어 제목, 모든 태그, 절 순서를 확인한다.
GitHub에서는 `gh issue view <number> --repo <location> --json number,title,labels,body,url`을 실행한다.
렌더링된 본문은 다음 명령으로 가져온다.
`gh api repos/<location>/issues/<number> -H "Accept: application/vnd.github.html+json" --jq .body_html`.
렌더링된 본문에 `##`, `**`, `\n` 같은 마크업이 그대로 드러나면 안 된다.
다른 트래커에서는 같은 경로로 다시 읽고, `html`이면 선언 옵션의 렌더링 검사도 실행한다.
공개 트래커에서는 Proposal과 Acceptance criteria에서 사례의 식별자를 다시 검색한다.

검사가 실패하면 [기존 이슈 갱신](references/update-in-place.ko.md)에 따라 이 스킬이 쓴 것을 직접 수정한다.
검사를 실행할 수 없으면 검증하지 못했다고 보고한다.

### 9. 미리 보기 표시

쓰기 후에는 사용자의 대화 언어로 미리 보기를 보여 준다.
간결하고 읽기 쉽게 쓰되, 이슈 링크와 모든 핵심 내용이 빠짐없이 명확하게 담겨야 한다.
Proposal의 각 규칙과 Acceptance criteria의 각 기준을 모두 보여 준다. 요약하면서 어느 것도 생략하지 않는다.

사용자가 미리 보기 후에 변경을 요청하면 [기존 이슈 갱신](references/update-in-place.ko.md)에 따라 이 스킬이 쓴 것을 직접 갱신한다.

## 최종 보고

사용자의 언어로 다음 내용을 쓴다.
이슈 번호와 링크를 쓰거나, 보여 준 초안과 등록하지 않은 이유를 쓴다.
중복 검색 결과와 검증 결과, 각 요구 사항을 담은 초안 문구를 쓴다.
제외한 각 항목에는 일회성 우회 방법, 도구 결함, 취향 차이 중 해당하는 분류를 붙인다.
