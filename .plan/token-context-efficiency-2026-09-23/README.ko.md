# 스킬 결과를 유지하면서 실행 비용 줄이기

이 문서는 최초 개선안이다. 이후 구현과 시험 결과는 [실행 기록](execution-results.ko.md)에 있다.

> 영어 원본: [README.md](README.md)
> 이 문서는 사람이 읽기 위한 비권위 한국어 미러다. 실행 지침으로 사용하지 않는다.

각 개선안이 Sonnet(high)과 Luna(xhigh)에서 모든 요구사항을 지키고, 완료 시간을 늘리지 않으면서
실행 비용을 줄인다는 근거를 확보할 때까지 현재 동작을 기본값으로 유지한다.
짧은 프롬프트를 평가하기 전에 설명 최적화 코드의 정확도 희생 지시부터 바로잡는다.

## 목적과 범위

사용자는 저장소 전체를 조사하고 `.plan/`에 개선안을 작성하도록 요청했다.
이 문서는 변경을 제안하며, 실제 개선을 구현하거나 토큰 절감이 측정되었다고 주장하지 않는다.

| 항목 | 확정 범위 |
|---|---|
| 목표 | 불필요한 지침 로딩, 반복 읽기, 모델 입력, 도구 출력, 중복 작업을 줄인다. |
| 조사 대상 | 플러그인 스킬 10개, 독립 배포 `omo-model-config` 스킬, 세션 지침, 에이전트, 훅, 지원 스크립트, 평가 자료, 탐색 설정. |
| 품질 | 목적, 실행 조건, 요구사항, 예외, 승인, 실패 처리, 사용 가능한 결과물을 보존한다. |
| 모델 | 저장소의 필수 평가 어댑터에 따라 실제 Claude Code와 Codex 환경에서 검증한다. |
| 성능 | 읽기, 도구, 작업 에이전트, 재시도, 복구를 포함해 사용 가능한 결과물까지 걸리는 시간을 측정한다. |
| 보호 대상 | 스킬 이름, 탐색 경로, 호스트 간 동작, 공개 출력 형식, 모델·사고 강도 계약, 잠금, 최신 상태 확인, 미러, 릴리스 정책. |
| 제외 대상 | 모델 등급 하향, 필수 검토 횟수 축소, 승인 정책 변경, 스킬 목적 추가, 외부 게시, 플러그인 설치. |
| 최초 계획 작성 시 변경 | 이 단계에서는 계획 디렉터리만 작성했다. 당시 실행 지침, 코드, 매니페스트, 버전은 변경하지 않았다. |

“저하 없음”은 채택 기준이다. 정적 조사만으로 앞으로의 모든 실행을 보장한다는 뜻은 아니다.
필요한 측정값이 없거나 품질 저하가 해결되지 않은 후보는 채택하지 않는다.
유한한 시험의 통과 근거는 시험한 모델, 작업, 조건에만 적용된다.

## 구현 전략

### 판단 절차 보존

각 스킬 진입 문서에는 실행 조건, 필수 결과, 순서가 있는 필수 절차, 중요한 예외,
중단 조건, 짧은 완료 점검을 남긴다.
특정 모드, 렌더러, 호스트, 복구 상태에서만 필요한 상당한 분량의 상세 설명을 참조로 옮긴다.
옮기는 절마다 최초 사용 전에 읽도록 하는 명시적인 조건을 둔다.
경로가 불분명하면 필요한 후보 지침을 읽거나 불확실성을 해소한다. 추측으로 지침을 생략하지 않는다.

조건은 해당 동작 옆에, 정확한 임계값은 비교식 옆에 둔다.
실수하기 쉬운 차이를 보여 주는 구체적인 예시는 남긴다.
절차와 마지막 점검의 반복이 누락을 잡아 준다면 보존한다.
순서가 있는 규칙을 “알아서 판단”, 약어 나열, 높은 추론 능력을 전제한 요약으로 바꾸지 않는다.

작은 파일을 여러 개 만드는 대신 선택한 모드마다 참조 하나를 추가하는 구성을 우선한다.
범용 지침 레지스트리, 전처리 프레임워크, 새로운 스킬 간 의존성은 추가하지 않는다.
기존의 독립 패키징과 명시된 형제 스킬 참조 계약을 유지한다.
영어 문서를 수정할 때 완전한 한국어 미러도 함께 수정한다.

### 실제로 달라지는 비용 최적화

논리적 토큰, 활성 문맥, 금전 비용, 완료 시간을 구분한다.
F25는 저장소가 소유한 프롬프트 조립의 접두부를 안정화하고, F26은 기존 호스트의 도구 탐색을 사용한다.
이 플러그인에 캐시 옵션이나 도구 레지스트리를 추가하지 않는다.
F27은 기존 상태 유지 절차의 복원 검사를 강화하며 자동 세션 초기화를 도입하지 않는다.
열 가지 제안의 상세 연결과 공식 근거는 [방안별 검토](strategy-assessment.ko.md)에 둔다.

가중 순위보다 품질·승인의 필수 관문이 우선한다.
제시된 점수 계산은 맞지만 Q/V/S/A 값이 이 저장소의 측정 결과를 입증하지는 않는다.
캐시만 개선하면 논리적 입력은 같을 수 있다. 이를 문맥 감소가 아니라 캐시 비용 개선으로 기록한다.
캐시 접두부가 깨지더라도 정확한 소스와 지침을 유지한다.

### 유효한 근거만 재사용

파일 리비전, 관련 런타임·도구 스키마, 현재 문맥이 유효하면 이미 읽은 지침을 재사용한다.
필요한 단계마다 규칙을 다시 적용하되 동일한 텍스트를 다시 가져오지는 않는다.
파일 변경, 관련 기능 변경, 새로운 독립 문맥, 규칙을 잃은 문맥 압축 뒤에는 다시 읽는다.
소스·페이지 버전 확인, 잠금 획득 후 티켓 재읽기, 레지스트리 확인, 저장 결과 검증은 유지한다.

인터뷰 질문은 실제 문맥에 있는 지침에서 필수 요청 형식 규칙을 찾아 확인한다.
점수화도 공식, 집계 방식, 임계값, 전이 규칙을 같은 방법으로 확인한다.
규칙을 찾을 수 없으면 작업 전에 해당 참조를 다시 읽는다. “이미 읽음” 표시만으로는 부족하다.
재개나 문맥 압축이 관측되면 다음 관련 동작 전에 현재 UI·점수 참조를 다시 읽는다.

원래 작업 흐름이 파일 자료를 지원한다면 전체 원시 근거는 프롬프트 밖에 보관한다.
짧은 색인과 필요한 부분 읽기로 근거를 찾되, 필요한 내용을 조용히 잘라내지 않는다.
상태 파일에 사용자 승인이 필요한 스킬에는 승인 없이 영속화를 추가하지 않는다.

### 개선 측정과 일반 실행 분리

구현 전에 기존 스킬과 필요한 참조 전체를 고정한다.
서로 격리된 평가 위치에 동등한 구버전·신버전 설치본을 준비한다.
각 비교 쌍에서 모델 설정, 도구, 권한, 입력, 기대 결과를 동일하게 유지한다.
개발 중 개선을 측정하며 일반 스킬 실행에는 벤치마크 의존성을 넣지 않는다.

조사한 스냅샷은 `B0`로 보존한다. S1 뒤에는 F01을 바로잡은 별도의 실험 스냅샷 `B1`을 기록한다.
S2는 `B1`과 비교해 F11의 프롬프트 중복 제거와 F01의 품질 정책 수정을 섞지 않는다.
이후 후보마다 앞서 통과한 실험 스냅샷을 고정하고 해당 후보만 바꾼다.
실험 기준 버전은 설치된 기본값을 변경하지 않는다.
채택 전에는 조합한 버전을 `B0`와도 비교해 S1에서 생긴 비용 증가를 숨기지 않는다.

기존 계약이 맞는 곳에는 `timing.json`, `grading.json`, 벤치마크 도구를 재사용한다.
추가 로딩 기록, 실제 모델·사고 강도 확인 자료, 채택 결정은 평가 작업 디렉터리에 둔다.
이번 조사 메타데이터를 저장하려고 배포되는 벤치마크 스키마를 확장하지 않는다.

실패한 후보 때문에 무관한 개선을 막을 필요는 없지만, 실패한 후보를 배포 기본값에 넣어서는 안 된다.
보류 후보나 검증하지 못한 모델 경로가 남아 있다면 저장소 전체 최적화가 끝났다고 표시하지 않는다.

## 통합 검증

변경한 요구사항을 모두 [검증 계획](validation.ko.md)의 사례에 연결한다.
전체 설치 플러그인과 현재 지원되는 독립 스킬 사용을 함께 확인한다.
최초 선택, 반복 실행, 긴 입력, 기능 부재, 문맥 복원을 시험한다.
중요한 조건은 모두 필수다. 평균 점수 상승으로 요구사항 하나의 누락을 상쇄하지 않는다.

영향받는 시나리오와 실제 모델 경로마다 구버전·신버전 비교를 세 번 수행한다.
검증 문서의 보수적인 품질, 시간, 토큰, 문맥 기준을 적용한다.
추가 반복은 별도로 한도를 정한 후속 조사에서만 한다. 결론이 불분명하면 기존 동작을 유지한다.
설명 최적화는 기존 반복 실행 조건 시험을 유지하고 실제 호스트의 라우팅 근거도 확보한다.

구현 후에는 README에 설명된 환경을 준비하고 다음 저장소 검사를 수행한다.

```bash
for skill in skills/*/ standalone-skills/*/; do
  python3 skills/skill-builder/scripts/quick_validate.py "$skill"
done
python3 -m pytest
node --test skills/document-to-confluence/tests/test_render_diagrams.mjs
```

이번 문서 작업에서는 로컬 링크, 소스 측정값, 미러 존재, 변경 범위를 확인한다.
이 검사를 Sonnet·Luna의 동작이나 실행 비용 절감의 근거로 해석하지 않는다.

## 적용과 종료 조건

후보마다 완전한 근거가 통과한 뒤 개별 채택하고, 조합한 버전도 확인한다.
통합 시 저하가 생기면 원인이 된 후보와 미러를 함께 되돌린다.
영향받는 비교와 공통 통합 검사만 다시 수행한다.
채택한 변경이 통과하고 추가 작업이 필요한 미해결 항목이 없으면 종료한다.

소스 스냅샷과 시험 자료는 일반 실행 로딩 대상 밖에 둔다.
임의의 토큰 절감률을 맞추려고 품질 검사, 필수 독립 관점, 사고 강도, 소스 범위, 승인을 줄이지 않는다.

이 계획은 현재 버전 `0.6.0`을 바꾸지 않으며, 이를 최신 배포 버전이라고 주장하지 않는다.
향후 릴리스 전에 배포 기준 버전과 나머지 미출시 변경을 확인한다.
동작을 보존하는 효율·신뢰성 개선은 통상 하나의 패치 릴리스에 포함된다.
구현이 목적, 요구사항, 외부 계약을 바꾼다면 범위를 다시 정하고 저장소의 마이너·메이저 정책을 적용한다.
두 매니페스트, `pyproject.toml`, `uv.lock` 버전을 일치시킨다.
로컬 재설치에는 캐시버스터를 사용한다. 게시와 세션 갱신은 각각 별도 승인이 필요하다.
