# 품질 보존을 입증한 뒤 최적화 채택

> 영어 원본: [validation.md](validation.md)
> 이 문서는 사람이 읽기 위한 비권위 한국어 미러다. 실행 지침으로 사용하지 않는다.

[발견 사항](findings.ko.md)의 후보를 구현할 때 이 절차를 적용한다.
계획을 작성할 당시에는 실제 모델 시험 결과가 없었다. 이후 측정값과 한계는
[실행 기록](execution-results.ko.md)에 있다.
정적 파일 측정은 조사할 위치를 보여 줄 뿐 모델의 지침 준수나 토큰 절감을 증명하지 않는다.

## 모델과 실행 계약

사용자가 요구한 Sonnet(high), Luna(xhigh)는 저장소의
[평가 모델 어댑터](../../skills/skill-builder/references/execution-methods.md)에 따라 아래와 같이 구체화한다.
더 최신인 모델, 더 강한 모델, 낮은 사고 강도, 정체를 확인하지 않은 별칭으로 조용히 대체하지 않는다.

| 검증 경로 | 실제 실행 환경 | 필수 실행 설정 | 사용할 수 없을 때 |
|---|---|---|---|
| Claude | Claude Code | Sonnet 5, `high`. 해석된 전체 모델 ID를 기록한다. | 해당 경로를 미검증으로 표시하고 관련 기존 동작을 유지한다. |
| Codex | Codex | `gpt-5.6-luna`, `xhigh`. 실제 모델과 사고 강도를 확인한다. | 해당 경로를 미검증으로 표시하고 관련 기존 동작을 유지한다. |

사용자가 이후 정확한 Sonnet·Luna 버전을 다르게 지정하면 비교 전에 새 검증 표로 고정한다.
Markdown에 이름이 적혀 있다는 이유로 모델 사용 가능 여부를 판단하지 않는다.
작성 세션의 모델은 바꾸지 않는다. Skill Builder의 작업자, 채점자, 실행기는 해당 호스트 어댑터를 따른다.
Tiki-taka 상대와 계획·설계 독립 검토자는 각자의 기존 모델 계약을 유지한다.
이들은 필요한 협업자이며, 주 실행기를 대상 모델로 검증하는 일을 대신하지 않는다.

Codex 실행은 실제 Claude 실행을 대체하지 못한다.
Claude 경로는 Claude Code에서 수행한다. Codex의 Skill Builder 호출에서 Sonnet 작업자를 띄우지 않는다.
두 호스트에 같은 입력과 기준을 사용하되 실제 도구·훅 차이는 보존한다.

주 세션 전용 질문과 사람 참여 작업은 시험마다 해당 모델·사고 강도의 별도 실제 주 세션을 시작한다.
개선안 작성 세션의 모델은 유지한다.
기존 스킬 계약에 따라 Claude Code의 질문 UI와 Codex Plan 모드를 사용한다.
사람 시험 담당자가 고정된 답변을 UI에 입력하며 종료 확인과 실행 선택도 각각 답한다.
실행 작업자가 사용자를 대신 답하거나 일반 텍스트 대안을 실제 질문 UI 검증으로 집계해서는 안 된다.
비대화형 사례는 허용된 격리 작업자를 쓸 수 있다. 채점 작업자도 해당 호스트 어댑터를 따른다.
실제 주 세션이나 시험 담당자가 없으면 해당 사례를 미검증으로 표시한다.
사람의 답변 대기 시간을 따로 기록하고 정해진 응답 시점이 동등한 비교 쌍만 사용한다.
전체 경과 시간 원본을 보존하며 완료 시간에서 지연을 조용히 빼지 않는다.

## 기준 버전과 자료

수정 전에 조사한 커밋이나 새로 기록한 현재 커밋에서 플러그인·독립 스킬,
필요한 참조, 스크립트, 매니페스트, 활성 세션 지침을 고정한다.
구버전 `SKILL.md`가 작업 중인 디렉터리의 신버전 참조를 읽지 않게 한다.
구버전·신버전의 작업 디렉터리와 출력 디렉터리를 격리한다.

개선안의 `B0`/`B1` 순서를 따른다. S2는 S1 뒤의 실험 스냅샷에서 시작한다.
이후 후보마다 구·신 해시를 기록하고 최종 조합은 원래 `B0`와도 시험한다.
F01의 해당 회귀 검사만으로 실제 품질, 지연 시간, 토큰 절감을 입증할 수는 없다.

일반 스킬 로딩 밖의 개발 평가 디렉터리에 다음 자료를 보관한다.

| 기록 | 필수 내용 |
|---|---|
| 고정 요구사항 | 안정적인 기준 ID, 권위 있는 파일·제목, 필수 동작, 해당 모드, 사례 ID. |
| 사례 정의 | 정확한 요청, 소스 파일·리비전, 사용자 응답 순서, 도구·서비스 입력, 권한, 기대 결과물. |
| 실행 명세 | 호스트 버전, 실제 모델 ID, 사고 강도, 소스 해시, 도구 버전, 환경 조건, 시험 순서, 기능 한계. |
| 원시 실행 | 프롬프트, 대화 기록, 도구 결과, 오류, 최종 결과물, 요청된 부수 효과 또는 모의 처리임을 표시한 확인 자료. |
| 로딩 기록 | 순서가 있는 지침·참조 읽기, 리비전, 반환 바이트, 반복 읽기, 문맥 손실·재로딩 사건. |
| 기존 채점·시간 자료 | 현재 형식의 `grading.json`, `timing.json`. 기존 스킬 비교에는 `new_skill`, `old_skill` 디렉터리를 쓴다. |
| 비교 | 사례별 품질, 시간, 사용량, 문맥 측정 범위, 재시도 수, 채택 판단, 근거 경로. |

기존 스키마와 집계를 사용한다. 추가 필드는 별도 실행 명세에 두며 `benchmark.json`을 조용히 바꾸지 않는다.
평균 통과율은 설명용 수치일 뿐 채택 근거를 대신하지 않는다.
설명 평가는 학습·보류 질문을 분리하고 이식 가능한 결과가 모의 라우팅임을 표시한다.

## 사례와 보존 검사

F03의 기대 결과 결함을 바로잡은 뒤 기존 동작 사례 48개와 실행 조건 사례 20개를 보존한다.
입력이 포함된 텍스트 사례는 그대로 실행할 수 있다.
없는 문서·저장소·서비스를 참조하는 사례에는 실제 시험 입력이 필요하다.
실행기는 기대하는 접근법을 설명하는 데 그치지 않고 결과물을 만들어야 한다.

다음 네 위치에 누락된 동작 평가를 만든다.

- `skills/deep-interview/evals/evals.json`
- `skills/flowchart-design/evals/evals.json`
- `skills/tiki-taka/evals/evals.json`
- `standalone-skills/omo-model-config/evals/evals.json`

나머지 시나리오는 기존 평가에 추가한다. 필요한 입력은 각 평가의 `evals/files/`에 둔다.
기존 사례의 실제 입력과 검증 조건이 해당 행을 충족하면 중복으로 만들지 않는다.

상향한 모델이 수정에 성공해도 대상 모델 시험의 통과로 집계하지 않는다. 대상 실패와 전체 수정 비용을 기록한다.
이 사례는 필수 평가 모델, 사고 강도, 기존 대안 정책의 변경을 승인하지 않는다.

## 시험 한도와 순서

먼저 후보를 선택하고 검증 표와 기존 평가에서 영향받는 구체적인 사례를 열거한다.
어느 쪽 결과도 생성하기 전에 입력과 채택 기준을 고정한다.
일반 성공, 가장 중요한 예외, 최소·무변경 동작의 세 사례로 시작한다.
무변경이 적용되지 않으면 기능 부재나 잘못된 입력 사례를 쓴다.

사례와 실제 모델 경로마다 대응하는 비교를 세 번 수행한다.
순서는 `구/신`, `신/구`, `구/신`으로 번갈아 실행한다.
사례가 `K`개라면 실행기 한도는 `K × 2버전 × 2호스트 × 3회 = 12K`회다.
초기 사례도 총한도에 포함하며 입력·설정이 그대로인 유효한 실행 결과를 재사용한다.
채점과 필수 상대·검토자 호출은 별도로 기록하고 실행기 수에 숨기지 않는다.

중요한 실패가 확인되면 해당 후보를 중단하고 수정하거나 기존 동작을 유지한다.
수정 뒤에는 영향받는 사례만 새로운 한도를 정해 비교하고 이전 버전을 구분해 둔다.
평균이 우연히 통과할 때까지 실행을 늘리지 않는다.
정한 한도 안에서 결론이 나지 않으면 기존 동작을 유지한다.
선별 사례가 통과하면 채택 전에 영향받는 모든 분기와 플러그인 조합을 시험한다.

바뀐 설명마다 긍정·부정이 균형을 이루는 사례 20개로 시작한다.
같은 구·신 조건에서 사례·설명·호스트마다 세 번 판단한다. 적용 가능한 기존 실행 조건 자료는 재사용한다.
실제 라우팅과 모의 라우팅은 서로 다른 질문에 답하므로 이름과 근거를 구분한다.
최적화 도구의 기존 학습·보류 분리와 독립 표본을 유지한다.

시간 비교는 비슷한 부하에서 수행하고 자원을 다투는 동시 실행을 피한다.
지연 시간 비교에 실행기의 기본 `--num-workers 10`을 그대로 적용하지 않는다.
측정 비교는 작업자 수를 1로 고정하고 별도 처리량 실험은 따로 기록한다.
이는 평가 설정이며 호스트 전체의 작업자 제한이나 배포 CLI 기본값을 바꾸는 것이 아니다.

V24는 요청 한 번과 정확히 세 번의 연속 요청이라는 구체적 사례 두 개로 구성한다.
연속 요청 사례에서 `12K` 실행 한 번은 세 요청 전체를 뜻한다. API·모델 호출 수도 기록한다.
캐시 준비도 연속 실행 비용에 포함하며 무료 준비 작업으로 빼지 않는다. 적중을 만들려고 유지 호출을 보내지 않는다.
각 연속 실행 안에서는 후보 내용을 고정하고 구·신 실행 순서를 번갈아 적용하며 실행 간 캐시 재사용을 기록한다.
제공자 캐시에 접두부가 남아 있을 수 있으므로 새 호스트 세션이라고 콜드로 가정하지 않는다.
제공되는 사용량으로 콜드·웜·불명을 분류한다. 확인할 수 없으면 불명으로 남긴다.
캐시 미적중을 강제하려고 무작위 접두부를 넣거나 권한을 바꾸거나 사용자의 활성 세션을 초기화하지 않는다.

F25는 F11 뒤의 스냅샷을 고정하고 블록 순서만 바꾼다.
F26·F27도 통합 전에 따로 비교해 탐색·복구 비용을 캐시 개선 효과로 잘못 계산하지 않는다.

## 측정값과 채택 기준

요청부터 사용 가능한 결과물까지 필수 검토와 수정을 포함한 전체 경로를 측정한다.
개발·준비·채점 비용은 별도로 측정한다. 다만 그 작업 자체가 스킬의 요청 결과라면 실행 비용에 포함한다.

| 관문 | 통과 조건 |
|---|---|
| 절대 품질 | 모든 후보 시험에서 중요 기준 전체를 결과물·행동 근거로 통과한다. 기존 버전의 실패가 후보의 실패를 허용하지 않는다. |
| 상대 품질 | 기존에 만족한 요구사항이나 중요한 의미·시각 품질을 잃는 사례가 없다. 이견은 소스·결과물로 해결하며, 불분명하면 기존 동작을 유지한다. |
| 라우팅 | 긍정 사례 누락과 새 부정 사례 오판이 없고, 명시 호출·유사 요청의 경계가 약해지지 않는다. 전체 정확도 외에 범주별 결과를 보고한다. |
| 완료 시간 | 각 사례·모델·동등한 문맥 및 캐시 조건에서 후보 세 번의 중앙값과 관측 최댓값이 모두 기존 버전 이하이다. |
| 전체 모델 사용량 | 제공되는 입력·출력·추론 사용량 전체에 같은 비교를 적용한다. 겹치지 않는 상위·작업자·재시도 기록만 합한다. |
| 금전 비용을 주장할 때 | 적용되는 실제 요금 또는 검증된 단가 추정치라는 표시를 사용해 사례별 중앙값·관측 최댓값을 같은 방식으로 비교한다. 캐시 쓰기·읽기, 모든 참여자, 재시도·복구를 포함한다. 정가 추정을 구독 지출로 표시하지 않는다. |
| 문맥 | 최초·반복 지침과 도구 입력량을 집계하고 새 문맥 손실·압축이 없는지 확인한다. 최대 유지 문맥은 호스트가 제공할 때만 비교한다. |
| 실제 효과 | 의도한 전체 경로 비용 중 적어도 하나가 개선된다. 소스가 짧아진 것만으로는 부족하며 다른 필수 성능 기준은 나빠지지 않는다. |
| 완전성 | 두 실제 호스트 경로와 영향받는 모든 모드·예외의 근거가 충분하다. 측정값·기능 부재를 비용 0이나 성공으로 취급하지 않는다. |
| 통합 | 채택한 조합이 공통 문맥, 패키징, 참조 부재, 스킬 간 라우팅 검사를 통과한다. |

시간·사용량 기준은 의도적으로 보수적이다. 세 번의 실행이 전체 모집단의 지연 상한을 증명하지는 않는다.
잡음이 겹친 결과를 개선 증거로 해석하거나 결과를 본 뒤 기준을 완화하지 않는다.
불분명하면 현재 기본값을 유지하고 시험의 한계를 기록한다.

제공되는 입력, 출력, 캐시 읽기·쓰기, 추론 항목을 따로 보고한다.
캐시·추론 수치가 호스트 총량에 이미 포함되었다면 다시 더하지 않는다.
바이트, 단어, 출력 토큰만의 값, 다른 제공자의 집계 방식으로 대체하지 않는다.
같은 모델 경로 안에서 구·신을 비교하며 Sonnet·Luna 사용량을 섞어 절감처럼 보이게 하지 않는다.
토큰 감소만으로 금전 비용 절감을 입증할 수 없다.
반대로 캐시 비용만 개선하면 논리적 입력과 활성 문맥은 같을 수 있다.
다른 필수 기준이 나빠지지 않으면서 적용되는 실제 비용이나 완료 시간이 개선되면 효과 관문을 통과할 수 있다.
이를 논리적 토큰 감소나 문맥 창 확장이 아니라 캐시 재사용으로 표시한다.

처음 읽는 실행과 문맥을 재사용하는 실행은 별도 조건이다. 비교 쌍의 시작 상태를 동일하게 복원한다.
문맥 압축 사례는 필요한 지침이 사라지면 다시 읽는 것을 보여 줘야 한다.
최대 문맥을 알 수 없어도 읽기 감소는 유효한 근거지만, 최대 문맥 감소를 측정했다고 보고하지 않는다.
완전한 사용량이 없으면 전체 토큰 절감을 주장하는 채택은 허용하지 않는다.

## 캐시·도구·체크포인트 근거

배포 벤치마크 스키마 대신 평가용 별도 실행 명세에 아래 관련 필드를 추가한다.

| 영역 | 추가 근거 |
|---|---|
| 캐시 | 제공자·호스트 버전, 실제 모델·사고 강도, 불변 접두부 해시 또는 관측된 식별 정보, 전체 논리적 입력, 캐시 읽기·쓰기 항목, 캐시 상태, 요청 순서·재사용 간격. |
| 요금 | 적용 과금 기준, 통화, 검증한 단가 출처·날짜 또는 실제 요금, 겹치지 않는 각 사용량 항목. 단가·집계 범위가 없으면 비용도 미상. |
| 도구 로딩 | 목록에 나온 이름·설명과 실제 로딩한 스키마 구분, 선택 도구·스키마 리비전, 탐색 시도·시간·실패·대안 경로. |
| 위임 | 상위·작업자 사용량, 시작, 중복 읽기, 반환 근거, 결과 통합, 재시도, 소유권 경계. 이미 포함된 총량을 이중 집계하지 않음. |
| 복원 | 체크포인트 소스·리비전, 필수 상태 점검, 복원 읽기, 오래된 근거 처리, 요약·재구성 비용, 미완료 동작 대조, 이어서 완성한 결과물. |

캐시 생성과 읽기의 과금 규칙은 제공자·모델마다 다르다.
해당하는 최신 스키마·요금표를 사용하며 이미 포함된 입력 총량에 캐시 수치를 다시 더하지 않는다.
호환되는 수치를 제공하면 대응하는 논리적 입력 대비 캐시 읽기 비중과 분모를 함께 기록한다.
그렇지 않으면 적중률을 지어내지 않고 원시 항목만 기록한다.
API 캐시 제어와 내부를 볼 수 없는 압축 상태는 호스트 공통 저장소 설정이 아니다.
공식 근거와 한계는 [방안별 검토](strategy-assessment.ko.md)에 정리했다.

F27은 전환 전에 체크포인트의 의무 전체를 원래 작업·권위 있는 결과물과 대조하고 복원 뒤 다시 확인한다.
부정, 예외, 승인, 미해결 결정, 동작 상태를 명시적으로 시험한다. “요약이 완전해 보임”만으로는 부족하다.
승인 없는 대화 기록을 만들지 말고 해당 절차의 기존 보관 규칙 안에서 소스 근거를 보존한다.
쓰기 완료 여부를 확정하지 못하면 그에 의존하는 동작을 멈추고 기존 복구 계약을 따른다.

## 결정적 검사와 채택 기록

파일·참조 존재, 메타데이터 유효성, 출력 파싱, 그래프 ID·간선,
알려진 원문 리터럴, 범위를 제한한 diff, 잠금 상태, 스크립트 종료는 정확한 검사로 확인한다.
의미, 자연스러움, 다이어그램 가독성, 완전성, 참조 적용 여부는 모델·사람이 검토한다.
토큰 수, 문자열 존재, 출력 길이로 실제 완료 여부를 대체하지 않는다.

변경한 동작에 대해서만 기존 회귀 검사를 확장한다.

| 대상 | 기존 회귀 검사 위치 |
|---|---|
| 프롬프트 표현, 실행기, 보고서 처리 | `skills/skill-builder/tests/test_evaluation.py`, `test_model_runner.py`, `test_viewer.py`, `test_benchmark.py` |
| 패키징 검증 책임과 스키마 참조 | `skills/skill-builder/tests/test_package_skill.py`, `test_schema_single_source.py`, `test_sibling_references.py` |
| 지침 라우팅과 미러 | `tests/test_session_context.py`, `test_instruction_duplication.py`, `test_planning_contract.py`, `test_korean_mirrors.py` |
| 콘텐츠 변환과 다이어그램 도구 | `skills/document-to-confluence/tests/` |
| 토론 상태와 진행 출력 | `skills/tiki-taka/tests/` |
| 지도 잠금과 갱신 생명주기 | `skills/decision-navigator/tests/test_local_lock.py`, `tests/test_session_lifecycle.py`, `tests/test_orca_plugin_refresh.py` |

테스트 수정 시 `instructions/testing.md`를 따른다. 의미상 문장 중복을 정규식 판정으로 바꾸지 않는다.
릴리스 준비를 마치기 전에 [README 개발 검사](../../README.md#development-checks)를 모두 수행한다.

후보마다 `adopt`, `reject`, `unverified` 중 하나와 구·신 해시, 실제 모델·사고 강도,
사례별 근거, 반복 실행 총비용, 한계를 기록한다. 거부한 후보는 실행 기본값에 넣지 않는다.
채택 뒤에는 입력, 도구, 요구사항, 모델 변경이 기존 근거를 무효화할 때만 다시 비교한다.
