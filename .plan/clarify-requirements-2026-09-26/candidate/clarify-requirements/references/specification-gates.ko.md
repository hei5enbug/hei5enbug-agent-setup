# 엄격한 명세 종료 조건

> 영어 원본: [specification-gates.md](specification-gates.md)
> 이 문서는 사람이 읽기 위한 비권위 한국어 미러다. 실행 지침으로 사용하지 않는다.

엄격한 인터뷰나 실행 가능한 명세를 만들 때 공통 명확화 반복 절차 안에서 이 제어를 적용한다.
일반 결정이 지도를 사용한다는 이유만으로 적용하지 않는다. 지도 안의 명세에서는 평가할 범위를 먼저
명시하고 티켓 준비 완료와 전체 목적지 준비 완료를 구분한다.

## 구성요소 초기화와 확인

첫 평가 전에 `scoring-and-state.md`를 읽는다. 불확실성 기준은 `0.01`이며 사용자가 더 엄격한 값을
명시하면 따른다. 느슨한 값은 `0.01`로 제한하고 출처나 제한 사실을 기록한다. 첫 질문 전에
`Deep Interview threshold: <percent> (source: <source>)`를 출력한다. 호환성을 위해 이 표기를 유지한다.
greenfield/brownfield를 구분하고 기존 작업이면 관련된 최소 원본 범위를 조사한다.

독립적으로 성공·실패할 수 있는 상위 구성요소를 1–6개 정한다. 구현 세부 사항은 결과 아래로 묶는다.
추가·삭제·병합·분리·보류 여부를 사용자에게 확인한다. 이것은 Round 0이며 점수를 매기지 않는다.
활성·보류 구성요소, 근거, 이유를 기록한다. 모든 활성 구성요소의 해당 명확성 차원을 다룬다.
하나를 깊이 다뤘다고 다른 구성요소의 빈틈이 상쇄되지 않는다.

## 평가로 다음 질문 선택

`../SKILL.md`의 공통 절차를 사용하고 두 번째 인터뷰 절차를 시작하지 않는다. 점수가 가장 낮은
활성 구성요소·차원을 선택하고 비슷하게 약한 구성요소를 순환한다. 핵심 개체·관계, 목표, 제약,
수용 기준, 필요한 기존 맥락 순으로 우선한다. 질문 하나는 결정 하나만 다룬다.
접속사나 중첩 목록으로 여러 질문을 숨기지 않는다.

질문·확인마다 `ask-ui.md`를 적용하고 해당 호스트의 지원 도구·모드를 쓴다.
`Round <n> | Component: <name> | Targeting: <dimension> | Why now: <reason> | Ambiguity: <score>%`를 포함한다.
선택지가 유용하면 서로 다른 선택지를 근거 있는 추천 순서로 제시하고 짧은 트레이드오프와 자유 입력을
허용한다. 선택지가 정보를 줄이면 열린 질문을 쓴다. 모든 질문은 주 세션에서 한다.

실질적인 자유 입력 후에는 결정, 이유, 사용자 제약, 사용자 비목표, 확인된 맥락을 추출한다.
의미를 잃었을 수 있으면 평가 전에 해석을 확인하고, 명시하지 않은 요구를 추가하지 않는다.
선택을 명시적으로 위임하면 `auto-answer-uncertain.md`를 사용한다. 결과는 가정으로 유지하고
`scoring-and-state.md`의 확신 상한과 확인 규칙을 적용한다.

상태가 바뀔 때 점수 계약을 다시 적용한다. 모든 활성 구성요소를 평가하고 사실·개체 관계를 갱신한다.
차원 점수·빈틈, 이전·현재 불확실성, 모순·불일치·회피·범위 확장, 다음 대상, 활성·보류 범위를 보고한다.
내부 정밀도는 유지하고 표시 반올림으로 준비 여부를 판단하지 않는다. 라운드가 지났다는 이유로 점수를 낮추지 않는다.

답변이 기존 사실과 충돌하면 두 버전을 보존하고 다툼을 표시하며 관련 점수를 낮추고 충돌을 다음 대상으로 삼는다.
확장된 범위를 추적하기 전에 구성요소를 갱신한다. 독립 조사로 도움이 되는 greenfield 질문에는
`auto-research-greenfield.md`를 사용한다. 이 기능은 선택적이며 사용자의 결정을 대체하지 않는다.

## 검토와 라운드 제어

불확실성 단계 구간을 어느 방향으로든 넘거나 에이전트 가정을 제안할 때 `lateral-review-panel.md`를 적용한다.
연구자·반대자·단순화자·설계자 관점을 유지한다. 가능하면 원하는 결론을 알리지 않은 독립 읽기 전용
컨텍스트를 사용하고, 불가능하면 같은 관점을 순차 적용한다. 검토자는 근거를 제공하며 사용자 질문,
승인, 범위 변경을 하지 않는다. 검증된 가장 중요한 발견을 다음 질문 하나에 반영한다.

에이전트가 세 번 연속 결정을 해결하면 다음 결정은 사용자에게 직접 묻는다.
10라운드에서는 다음 질문 전에 계속·중단을 확인한다. 20라운드에서는 질문을 멈추고 위험 표시 명세를 만든다.
조기 종료나 질문 생략 요청에서는 미해결 빈틈과 위험 표시 초안을 남기고 불확실성 기준 통과를 암시하지 않는다.
정확한 범위의 실행 권한을 아직 받지 않았다면 별도로 승인받는다.

## 종료

불확실성이 기준에 도달하면 다음 순서로 확인한다.

1. 모든 활성 구성요소의 목표·제약·수용 기준·해당 기존 맥락을 감사한다.
2. 미해결 모순·불확실한 외부 의존성·미검증 가정을 나열한다.
3. 전체 목표를 한 문장으로 다시 말하고 명시적인 목표 확인을 받는다.
4. `spec-template.md`로 명세를 만들고 합의를 정확히 담았는지 명시적으로 확인받는다.
5. 저장·계획·실행·인계·중단을 별도로 정한다. 기존 명시적 권한은 승인된 정확한 범위에만 적용한다.
   명세 승인에서 실행을 암묵적으로 선택하지 않는다. 저장은 승인된 경로에만 한다.

확인과 다음 행동 선택에도 `ask-ui.md`를 사용한다. 수치 기준과 모든 종료 조건을 통과해야 `passed`다.
조기 종료·한도 도달은 `risk-accepted` 또는 `pending`으로 남긴다. 지도에서 미해결 사람 결정은 열린 상태다.
위험 표시 초안은 해결된 티켓이 아니다.

## 완료 확인

구성요소 확인과 개별 범위 충족, 질문 하나에 결정 하나, 질문 전 조사, 증가할 수 있는 근거 기반 점수,
준비 기준을 넘기 전 가정 확인, 필수 검토·라운드 제한, 목표·명세의 명시적 확인, 별도로 허용된 다음 행동,
UI·작업 에이전트·병렬·저장 부재 시 정직한 대체 절차를 확인한다. 실패한 필수 항목은 드러내어 남긴다.
