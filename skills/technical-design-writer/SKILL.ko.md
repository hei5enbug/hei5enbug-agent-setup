# 기술 설계 문서 작성

> 영어 원본: [SKILL.md](SKILL.md)
> 이 문서는 사람을 위한 비권위 한국어 번역본이다. 에이전트 실행 시 읽거나 사용하지 않는다.

독자가 추측하지 않고 설계를 구현, 검증, 운영하거나 승인할 수 있는 문서를 만든다.

## 적용 범위

사용자가 기술 설계 문서, 아키텍처 제안서, RFC, 시스템 설계, 데이터 설계, API 설계 또는 설계 개요를 명시적으로
요청하거나 이 스킬을 직접 호출했을 때 사용한다. 번역, 일반 문장 교정, 구현 계획, 사용자 가이드, 릴리스 노트,
일반 구현, 진단, 요약 또는 명시적인 설계 의도가 없는 코드 리뷰에는 사용하지 않는다.

## 기준과 자료

실행 지침은 `SKILL.md`와 그 파일이 명시적으로 요구하는 참조 파일이다.

한국어 결과물을 작성하거나 검토할 때는 `references/korean-writing.md`를 먼저 읽는다.

새 문서와 개선 작업에서는 초안을 쓰기 전에 `references/design-documents.md`를 읽는다. 이 참조는 목표 설계 경계,
설계 문서 절차, 템플릿을 관리한다. 세션 지침은 독립 모델 검증 규칙의 단일 기준을 제공한다. 필수 참조를 사용할 수
없다면 누락된 항목을 알리고 해당 작업을 중단한다. 규칙을 임의로 재구성하지 않는다.

`references/korean-writing.md`는 형제 스킬 파일 하나를 읽는다. 이 스킬 폴더를 기준으로 한
`../humanize-korean/references/patterns.md`가 번역투 신호 표를 제공한다. 그 파일이 없으면
`korean-writing.md`의 나머지 규칙만 적용하고 신호 목록을 참조하지 못했다고 보고한다.
이 스킬은 다른 스킬을 호출하지 않고 다른 스킬의 스크립트에 의존하지 않는다.

이 스킬은 상위 지시를 따른 뒤 기술 설계 작업에만 적용한다. 사용자 요구사항, 저장소 규칙,
제공된 템플릿, 확립된 프로젝트 규칙이 이 스킬보다 우선한다.

## 작업 유형

| 유형 | 필수 결과 |
|---|---|
| 새 문서 | 확인된 요구사항과 근거로 완전한 설계 문서를 작성한다. |
| 개선 | 근거가 있는 의도와 계약을 보존하면서 누락, 모호함, 중복, 구조를 고친다. |
| 검토 | 요청이 없으면 파일을 수정하지 않는다. 위치, 영향, 교정안을 포함한 지적을 반환한다. |

## 설계 범위

적용되는 항목을 각각 한 곳에서 완전하게 다룬다.
한 섹션에서 명확하게 설명할 수 있으면 항목을 합친다.

| 항목 | 문서가 답해야 하는 질문 |
|---|---|
| 맥락 | 어떤 문제, 독자 결과, 목표, 비목표, 제약, 가정이 설계를 한정하는가? |
| 결정 | 무엇을 선택했고 왜 선택했으며, 어떤 대안과 절충안을 왜 제외했는가? |
| 경계 | 어떤 행위자, 시스템, 소유자, 의존성, 신뢰 경계, 책임이 범위에 있는가? |
| 계약 | 어떤 입력, 출력, 스키마, 불변 조건, 호환성, 데이터 수명 주기가 적용되는가? |
| 동작 | 정상 흐름, 순서, 상태 변화, 동시성, 멱등성, 대체 동작은 무엇인가? |
| 실패 | 잘못된 입력, 부분 실패, 시간 초과, 재시도, 중복, 복구를 어떻게 처리하는가? |
| 안전 | 인증, 인가, 개인정보, 무결성, 악용, 규정 준수 통제는 무엇인가? |
| 운영 | 용량, 관측, 소유권, 지원, 비용 요구사항은 무엇인가? |
| 변경 | 출시, 마이그레이션, 하위 호환성, 롤백, 정리를 어떻게 수행하는가? |
| 입증 | 어떤 테스트, 측정, 승인 기준, 미결 결정이 완료를 입증하거나 막는가? |

## 근거 없는 내용

근거 없는 주장이라도 그것이 없으면 독자가 구현, 검증, 운영, 승인을 다르게 할 수 있으면 중요한 내용이다.
중요한 내용은 모두 남기고 나머지만 지운다.

| 처리 | 대상 |
|---|---|
| 가정으로 남김 | 설계가 의존하지만 확인할 수 있는 출처가 아직 없는 중요한 주장 |
| 미해결 사항으로 남김 | 아직 정해지지 않은 중요한 결정 |
| 삭제 | 평가 문구, 중복 요약, 초안 메모, 현재 설계로 대체된 서술 |

남긴 항목은 `가정과 미해결 사항` 섹션 한 곳에 모으고 주장, 근거 상태, 확정 방법을 함께 적는다.
본문에는 라벨, 변경 표시, 이 처리에 관한 설명을 넣지 않는다. 기록은 그 섹션이 담당한다.
이 섹션이 "맥락" 항목의 가정과 "입증" 항목의 미결 결정을 담는 유일한 자리이므로 다른 곳에서 되풀이하지 않는다.

지운 항목은 문서 옆에 `<문서명>.removed.md` 파일을 만들어 원래 위치와 삭제 사유와 함께 기록한다.
실제로 지운 내용이 있을 때만 만들고, 커밋하지 않는 파일임을 표시하며, 사용자가 요청하기 전에 지우지 않는다.

## 정확성

정보를 빼면 구현, 검증, 운영, 결정, 해석이 실질적으로 달라질 때 그 정보를 포함한다.
각 규칙을 만족하지만 결과가 다른 두 사례를 만들어 본다.
그런 사례가 있으면 두 결과를 구분하는 정보만 더한다.

| 검사 | 요구사항 |
|---|---|
| 주체 | 알맞은 추상화 수준의 행위자나 대상을 쓰고 식별자나 표현으로 대신하지 않는다. |
| 동작 | 동작, 영향받는 대상, 결과를 쓴다. 필요하면 조건과 순서를 더한다. |
| 규칙 | 입력, 평가 순서나 우선순위, 출력, 대체 결과나 예외 결과를 쓴다. |
| 상태 | 유효 상태, 전이 조건, 보호 조건, 종료 상태, 잘못된 전이의 동작을 정의한다. |
| 근거 | 수치에는 단위와 측정 기준을, 중요한 정성적 주장에는 기준이나 출처를 붙인다. |
| 참조 | 문장, 셀, 목록 도입문 안에서 해결되지 않으면 안정적인 이름을 다시 쓴다. |
| 구조 | 표 셀은 머리글과 함께 명제 하나를, 목록 항목은 도입문과 함께 명제 하나를 이룬다. |

행위는 행위자에게만 준다. 다른 주어에는 상태나 변화를 나타내는 서술어를 쓴다.
한 문장에는 주장 하나, 한 문단에는 중심 생각 하나를 둔다.
근거로 셀 수 있으면 정확한 수를 쓴다.
요구사항, 현재 사실, 가정, 제안, 미결 질문을 구분한다.

## 용어

용어 결정은 변경이 닿는 범위 전체에 적용하며 파일 하나에 한정하지 않는다.
문서가 같은 대상을 다루는 문서 집합에 속하면, 그 집합에 이미 자리 잡은 용어가 새로 고른 용어보다 앞선다.

다음 순서로 용어를 결정한다.

1. 사용자가 정했거나 프로젝트에 있는 용어집
2. 구현, 인터페이스, 스키마, 계약에 있는 정확한 이름
3. 공식 제품명이나 확립된 분야 용어
4. 대상 언어에서 확립된 쉬운 표현
5. 남은 선택이 같은 수준으로 정확할 때만 기존 문서에서 가장 흔한 표현

뜻마다 정식 용어 하나를 쓰고 용어마다 뜻 하나를 준다.
낯선 용어는 그 용어에 의존하는 첫 문장보다 먼저 정의한다.
반복 사용이나 검색에 도움이 될 때만 약어를 한 번 정의하고 이후 한 형태로 통일한다.
정확한 기술 용어를 쉽지만 뜻이 다른 말로 바꾸지 않는다.

일관성은 선언이 아니라 검사로 확보한다.
완료 조건을 걸기 전에 문서가 이름 붙인 반복 개념을 뽑고, 개념마다 문서가 실제로 쓴 표기를 모두 모은다.
한 개념을 두 표기가 가리키면 위 순서가 고르는 표기만 남기고 나머지를 바꾼다.
한 표기가 두 개념을 가리키면 그중 하나의 이름을 바꾼다.

## 구조

- 한 페이지에는 독자 목표 하나를, 한 섹션에는 책임 하나를 둔다.
  목표가 다르거나 4단계 제목이 필요하면 나눈다. 파일을 줄이기 위해서만 나누지 않는다.
- 제목 바로 아래에 짧은 결정 요약을 둔다. 역사와 상세보다 가치와 결과를 먼저 쓴다.
- 선행 조건, 결정, 동작, 실패 처리, 변경, 입증 순으로 배치한다.
- 제목은 문장부호 없는 명사구로 쓴다.
  정확한 식별자나 수식어를 잃지 않는 한 한국어 제목을 30자 안으로 쓴다.
- 제목은 3단계까지만 쓴다. 직접 작성한 Markdown 파일은 500줄 안으로 둔다.
  제공된 템플릿이나 생성된 계약은 나누면 산출물이 달라질 때만 제외한다.
- Markdown 산문 원본 줄은 120자 안으로 쓴다. 표 행, URL, 코드, 정확한 문자열은 제외한다.
  완전한 문장 뒤에서만 나누고 의도한 Markdown 문단 렌더링을 보존한다.

## 표와 다이어그램

비교할 항목이나 차원이 셋 이상이고 공통 필드가 안정적이면 표를 쓴다.
작은 비교는 산문으로 쓴다.
머리글과 셀의 의미 구조를 맞추고 여러 문단이 필요한 상세는 본문으로 옮긴다.

복잡한 분기, 상태 변화, 상호작용, 소유 경계, 의존성, 데이터 관계를 그림이 더 잘 설명하면
다이어그램을 쓴다.
동작에는 흐름도나 상태도, 상호작용에는 시퀀스 다이어그램,
경계에는 구성 요소 다이어그램, 데이터에는 개체 관계 다이어그램을 쓴다.

인접 산문을 그림으로 반복하지 않는다.
행위자와 상태는 노드로, 조건과 전달 데이터는 간선 라벨로 쓴다.
노드 하나만 묶지 않고 경계를 넘는 화살표의 연결점을 모호하게 두지 않는다.
모든 다이어그램을 렌더링해 라벨, 잘림, 겹침, 경로, 균형을 확인한다.
렌더링할 수 없으면 그 사실을 밝히고 문법만 검증한다.

규칙을 그림이나 표로 요약한 뒤에는 분기 수와 판정 순서를 원본 규칙과 대조한다.
요약에서 단계가 빠져도 문서에는 오류로 드러나지 않는다.
개체 관계 다이어그램에서는 관계선의 카디널리티를 참조 컬럼의 빈값 허용 여부와 대조한다.
비울 수 있는 참조는 0 또는 1로 그리고 항상 1로 그리지 않는다.

## Markdown과 참조

- 문단은 빈 줄 하나로 나눈다. 제목, 표, 코드 블록, 목록 앞뒤에는 빈 줄을 둔다.
- 순서나 우선순위가 있을 때만 번호 목록을 쓴다. 같은 수준의 항목은 의미와 문법 구조를 맞춘다.
- 정확한 식별자, 경로, 명령어, 값, 코드는 백틱으로 표시한다.
  링크 텍스트는 대상을 설명해야 한다.
- 보이는 줄바꿈은 문단, 목록 항목, 표 행으로 만든다. 줄 끝 공백으로 줄바꿈을 만들지 않는다.
- 주제마다 상세 원본을 하나만 둔다. 다른 곳에서는 조건을 잃지 않고 요약한 뒤 링크한다.
- 여러 문서가 같은 종류의 목록을 각자 가지면, 어느 하나가 바뀔 때마다 항목을 상호 대조한다.
- 섹션 번호, 위치, 특수 참조 기호 대신 문서 경로와 제목으로 참조한다.
  실제 제목과 맞는지 검사한다.
- 계약을 옮겨 적으면 기준 원본과 함께 바꿔야 할 모든 산출물을 밝힌다.
- 주석과 docstring을 포함한 코드에서는 문서를 참조하지 않는다.

## 도구 범위

기계 도구는 정확히 판정할 수 있는 조건에만 쓴다.
검색 결과만으로 의미 품질을 결정하지 않는다.
가능하면 다이어그램을 렌더링하고 예제를 실행한다.
보고한 모든 실패가 실제 위반이고 지원 범위의 모든 위반을 실패시킬 때만 검증기를 만든다.
문맥에 따른 정확성, 문체, 적용 여부는 모델이나 사람이 판단한다.

## 완료 조건

- [ ] 작업 순서를 지켰고 결과가 새 문서, 개선, 검토 중 요청한 유형과 맞는다.
- [ ] 적용되는 설계 항목마다 완전한 자리가 하나 있고, 빠진 항목은 실제로 적용되지 않는다.
- [ ] 요구사항, 사실, 가정, 제안, 미결 질문을 구분할 수 있다.
- [ ] 규칙, 상태 전이, 계약, 실패 경로, 마이그레이션 단계, 승인 기준이 모호하지 않다.
- [ ] 주장, 수치, 예제, 명령어, 링크, 옮긴 계약, 다이어그램에 충분한 근거나
      명확한 제한이 있다.
- [ ] 용어, 어조, 숫자, 단위, 제목, 목록, 표, 다이어그램, 참조가 일관된다.
- [ ] 대상 언어 참조를 통과했고 정확한 문자열, 인과관계, 부정, 가능성, 범위를 보존했다.
- [ ] 모든 완료 기준과 검증 항목은 이 문서가 밝히거나 명시적으로 인용한 규칙에만 기댄다.
- [ ] 중요한 근거 없는 주장을 모두 `가정과 미해결 사항` 섹션에 두었고, 본문에는 처리 표시가 없으며,
      지운 내용은 기록 파일에 남기고 사용자에게 알렸다.
- [ ] 불필요한 내용, 중복 원본, 미해결 자리 표시자, 기록하지 않은 근거 없는 주장이 남지 않았다.
- [ ] 새 문서와 개선 작업은 `references/design-documents.md`와 세션 수준의 독립 모델 검증 규칙을 모두 지켰다.
