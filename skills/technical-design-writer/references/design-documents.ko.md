# 설계 문서 워크플로

> 영어 원본: [design-documents.md](design-documents.md)
>
> 이 문서는 사람을 위한 비권위 한국어 번역본이다. 에이전트는 실행 중 이 문서를 읽거나 사용하지 않는다.

`SKILL.md`가 지시한 뒤 Create 및 Improve 모드에서만 이 문서를 사용한다. 이 문서는 설계 문서의 범위와 출력
템플릿을 정의한다. 세션 수준의 독립 모델 검증 지침은 검토자 선택, 모델 설정, 검토 항목, 확정 방법을 정의한다.

## 목표 설계 경계

설계 문서는 선택한 목표 설계를 공유한다. 계약, 제약, 동작, 대안, 트레이드오프를 중심으로 작성한다. 기존 설계의
문제는 목표 결정을 설명하는 데 필요한 만큼만 다룬다. 사용자가 실행 가능한 계획을 명시적으로 요구하지 않았다면
RFC는 설계 문서로 분류한다.

설계 문서를 구현 계획으로 바꾸지 않는다. 사용자가 요구했거나 순서가 실현 가능성, 마이그레이션 안전성, 호환성을
입증하는 데 필요할 때만 실행 단위나 작업 순서를 포함한다. 요청하지 않은 구현 세부사항, 추측성 확장 지점, 관련 없는
리팩터링을 추가하지 않는다.

구현 계획과 설계 문서로 모두 해석할 수 있고 선택에 따라 내용, 구조, 범위 또는 인수 조건이 달라진다면 대안을 설명하고
작성 전에 사용자에게 확인한다. 사용자 용어, 저장소 템플릿 또는 기존 프로젝트 계약이 유형을 결정하면 그 근거를
적용한다.

## 작업 순서

1. 설계 승인에 영향을 주는 설계 목표, 범위, 목표가 아닌 항목, 제약, 보호해야 할 계약, 독자, 승인 기준, 근거 출처를
   확정한다. 기존 문서라면 근거 없는 주장, 빠진 설계 범위, 규칙 위반도 찾는다.
2. `SKILL.md`의 설계 범위로 내부 점검표를 만든다. 각 항목이 적용되는지 이유와 함께 판단한다. 본문을 쓰기 전에
   2단계 제목을 확정하고, 문서에는 독자 목표 하나를, 섹션에는 책임 하나를 둔다. 반복 요약을 지우고 선행 조건을
   종속 결정 앞에 배치한 뒤 모든 적용 항목에 자리를 하나씩 준다.
3. 원본 계약과 근거를 수집한다. 설명문보다 요구사항, 코드, 스키마, 설정, 측정값, 공식 인터페이스를 우선한다.
   도입부부터 쓴 뒤 목표 설계, 경계, 동작, 계약, 실패 처리, 제약, 대안, 절충안을 대상 언어로 설명한다.
   `SKILL.md`의 정확성, 구조, 표, 다이어그램, 언어 규칙을 적용한다.
4. 변경 범위 전체의 용어를 한 번에 정리한다. 참조와 인용한 제목도 함께 갱신한다. 구현 식별자나 외부 계약명을
   바꾸기 전에 사용자에게 묻는다. 앞선 결정을 뒤집는다면 그 결정을 기록한 모든 문서를 갱신하고 원래 근거가 더 이상
   성립하지 않는 이유를 적는다.
5. 옮겨 적은 계약, 예제, 명령어, 링크, 계산, 다이어그램을 가능한 가장 강한 방법으로 검증한다. `SKILL.md`에 따라
   근거 없는 내용을 분류하고, 초안 메모와 불필요한 내용을 지우고, 실제로 지운 항목을 기록한 뒤 완료 조건을 검사한다.
6. 세션 지침이 제공한 독립 모델 검증을 적용한다. 검토자 선택, 모델 설정, 검토 항목, 실패 처리, 확정, 결과 보고는
   공통 검증 지침에서 관리한다.

## 출력 템플릿

같은 계약을 유지할 수 있다면 저장소의 기존 템플릿에 맞게 제목을 바꾼다. 선택 항목은 자리 표시자로 채우지 않고
생략한다.

```markdown
# <목표 설계 제목>

<결정 요약과 독자가 얻을 결과>

## 목표와 범위

<목표, 목표가 아닌 항목, 제약, 가정, 보호해야 할 계약>

## 목표 설계

<경계, 동작, 데이터, 인터페이스, 불변 조건, 실패 처리>

## 대안과 트레이드오프

<결정에 영향을 주는 대안과 선택한 설계의 근거>

## 변경과 입증

<해당할 때 마이그레이션 또는 호환성, 인수 조건, 검증>

## 가정과 미해결 사항

<중요한 미입증 주장과 미결 결정만 기록하며, 없으면 생략>
```

## 완료 검사

- 모든 섹션은 목표 설계 또는 승인에 필요한 결정에 기여한다.
- 현재 상태 설명은 목표 결정의 근거가 되는 내용으로 제한한다.
- 계약, 제약, 대안, 주요 트레이드오프가 빠짐없이 정확하게 설명되어 있다.
- 실행 순서는 사용자가 요청했거나 실현 가능성, 안전성 또는 호환성을 입증하는 데 필요할 때만 포함한다.
- 추측성 확장, 관련 없는 리팩터링, 요청하지 않은 낮은 수준의 세부사항이 남아 있지 않다.
- 공통 독립 검증 규칙을 모두 지켰다.
