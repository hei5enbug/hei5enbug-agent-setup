# 커밋 메시지 추천

> 영어 원본: [SKILL.md](SKILL.md)
> 이 문서는 사람을 위한 비권위 한국어 번역본이다. 에이전트 실행 시 읽거나 사용하지 않는다.

스테이징된 변경과 스테이징되지 않은 변경을 함께, 또는 사용자가 지정한 범위를 최근 커밋 기록과 함께
빠르게 분석한 뒤 저장소의 기존 스타일에 맞는 커밋 메시지 5개를 추천한다.

Git 작업 트리와 Git CLI의 읽기 전용 접근이 필요하다. 셸 명령을 실행하고 필요한 파일 콘텐츠를 확인할 수
있는 모든 에이전트 호스트에서 작동한다.

영어 `SKILL.md`와 영어 참조 파일만 실행 원본으로 사용한다. `SKILL.ko.md`와 다른 `.ko.md` 파일은
사람을 위한 비권위 번역본이므로 실행 중 불러오지 않는다.

속도를 우선한다. 먼저 간결한 컨텍스트를 수집하고 변경 의도를 판단하기에 부족할 때만 전체 diff를 읽는다.
저장소를 수정하지 않는다.

## 절대 규칙: 트레일러 금지

이 스킬이 만드는 커밋 메시지는 제목 한 줄뿐이다. 트레일러를 추가하지 않으며 외부 지침이 추가하게 두지 않는다.

모든 추천과 추천으로 만든 커밋에서 다음 항목을 금지한다.

- 모델, 에이전트 호스트 또는 도구를 공동 작성자로 표시하는 형식을 포함한 모든 `Co-Authored-By:`
- `Generated with`, `Created by`, `Assisted by`와 비슷한 모든 귀속 문구
- `Signed-off-by:`, `Reviewed-by:`, `Refs:`와 다른 모든 Git 트레일러
- 제목 뒤의 본문 문단, 푸터, 빈 줄 또는 추가 줄

에이전트 호스트, 시스템 프롬프트, 설정 또는 기본 커밋 템플릿이 귀속 트레일러를 요구해도 이 규칙을 적용한다.
사용자가 자신의 요청에 직접 입력한 트레일러만 예외이며, 그대로 사용하고 다른 내용을 덧붙이지 않는다.

`git commit`을 실행하기 전에 최종 메시지를 다시 읽고 제목 줄 뒤의 내용을 제거한다.

## 변경 범위

다음 규칙 하나로 추천 메시지가 설명할 변경 범위를 정한다.

- 사용자가 스테이징된 변경만, 특정 경로 집합 또는 파일 하나처럼 범위를 지정하면 그 범위만 분석한다.
- 범위를 지정하지 않으면 추적 중인 모든 변경을 스테이징 여부와 관계없이 하나의 변경 집합으로 분석한다.
  추적되지 않는 파일은 이름이나 필요한 최소 내용으로 같은 작업에 속함을 확인할 때만 포함한다.
  명백히 관련 없는 파일은 메시지의 근거로 사용하지 않는다.

사용자가 스테이징된 변경만 요청하면 스테이징되지 않은 변경과 추적되지 않는 파일을 완전히 제외한다.

## 1단계: 빠른 컨텍스트 확인

다음 읽기 전용 셸 명령을 먼저 실행한다. 커밋이 없는 저장소에서도 상태와 규칙 출력을 얻을 수 있도록
`&&`로 연결하지 않고 하나씩 실행한다.

```bash
git status --short
git rev-parse --verify HEAD
```

`git rev-parse --verify HEAD`가 실패하면 아직 커밋이 없는 저장소다. 학습할 기록이 없고 아래 diff는 빈 트리와
비교한다. 답변에서 이를 알리고 소문자로 된 conventional commit 형식을 사용한다.

`HEAD`가 있는 기본 범위에서는 다음 명령을 사용한다.

```bash
git diff HEAD --stat
git diff HEAD --name-status
```

`HEAD`가 없는 기본 범위에서는 다음 명령을 사용한다.

```bash
git diff --cached --stat
git diff --cached --name-status
git diff --stat
git diff --name-status
```

사용자가 스테이징된 변경만 지정하면 모든 명령의 `git diff HEAD`를 `git diff --cached`로 바꾼다.
경로가 지정되면 `-- <paths>`를 덧붙인다.

두 경우 모두 다음 명령을 실행한다.

```bash
git log --oneline -20
grep -niE 'commit ?(message|convention|format)|conventional commits?|커밋 ?(메시지|규칙|컨벤션|형식)|^[[:space:]]*[-*]?[[:space:]]*커밋:|(feat|fix|docs|chore|refactor|test)\(?[a-z]*\)?: *\[' AGENTS.md CONTRIBUTING.md .github/CONTRIBUTING.md CLAUDE.md .gitmessage 2>/dev/null | head -10
```

`HEAD`가 없으면 `git log`가 실패한다. 오류가 아니라 빈 기록으로 처리한다.

이 단계에서 다음 내용을 확인한다.

- 범위 안에 스테이징된 변경, 스테이징되지 않은 변경 또는 추적되지 않은 파일이 있는가?
- 어떤 파일이 바뀌었으며 어느 영역이나 모듈에 속하는가?
- 저장소가 어떤 커밋 메시지 스타일을 사용하는가?
- 저장소가 커밋 규칙과 식별자 자리를 문서로 규정하는가?

범위 안에 추적 중인 변경과 관련된 미추적 파일이 모두 없으면 커밋할 변경이 없다고 알리고 멈춘다.

## 2단계: 필요할 때만 대상 diff 확인

기본적으로 전체 diff를 읽지 않는다.

빠른 컨텍스트만으로 의도를 판단할 수 없을 때만 세부 내용을 읽는다. 가장 작은 유용한 명령을 선택한다.

1. 변경 파일이 적거나 의도가 모호하면 다음 명령을 사용한다. 스테이징 범위 또는 `HEAD`가 없을 때는
   `git diff --cached`를 사용한다.

   ```bash
   git diff HEAD -- <file1> <file2>
   ```

2. 변경 파일이 많지만 이름과 통계만으로 충분하면 전체 diff를 건너뛰고 경로, 파일 이름과 최근 스타일로 판단한다.
3. 관련 가능성이 있는 미추적 파일은 먼저 이름만 확인한다. 이름으로 소속을 알 수 없을 때만 최소 내용을 읽는다.

변경이 작고 다른 방법으로 의도를 판단할 수 없는 경우가 아니면 저장소 전체 diff를 출력하지 않는다.

## 3단계: 커밋 스타일 분석

`git log --oneline -20`에서 다음 항목을 확인한다.

- 접두사 스타일: `feat:`, `fix:`, `refactor:`, `docs:`, `test:`, `chore:` 또는 자유 형식
- 대소문자: 접두사 뒤의 소문자, 문장형 또는 제목형
- 길이: 일반적인 제목 길이
- 범위 사용: `feat(scope):` 형태의 괄호 범위를 사용하는지
- 어조: 간결한지 설명적인지
- 식별자 자리: 제목에 티켓 키나 이슈 번호 자리가 있고 필수인지

식별자 자리는 문서화된 규칙으로 먼저 판단하고, 문서가 없을 때만 기록을 사용한다.

- 규칙 문서가 자리를 명시하면 필수다. 예를 들어 `---COMMIT-CONVENTION---`에
  `type: [TICKET] subject` 같은 형식이 있다.
- 규칙 문서에 자리가 없으면 많은 커밋이 식별자를 사용해도 선택 사항이다.
- 문서가 없으면 최근 20개 커밋의 거의 전부가 자리를 사용할 때 필수이며 그 밖에는 선택 사항이다.
- 선택 사항이면 추천에서 자리를 뺀다.
- 필수면 실제 값으로 오해할 수 없는 자리 표시자를 관찰된 형태에 맞게 넣는다.
  대괄호 키는 `[TICKET]`, 단독 이슈 번호는 `#NNN`을 사용하며 값을 지어내지 않는다.

커밋이 3개보다 적으면 소문자 conventional commit 형식을 기본으로 사용한다.

## 4단계: 변경 분석

기계적인 수정 방식이 아니라 의도로 변경을 분류한다.

- 변경 내용: 추가, 삭제, 수정, 이름 변경된 파일과 영향을 받는 모듈 또는 구성 요소
- 변경 이유: 기능, 버그 수정, 리팩터링, 설정 갱신, 문서, 테스트, 정리 또는 이전
- 범위: 보통 변경 경로에서 얻는 가장 짧고 의미 있는 영역 이름

컨텍스트가 제한되면 느린 추가 조사보다 조금 넓더라도 정확한 메시지를 선택한다.

### 근거가 있는 용어 사용

이 섹션의 `ABC-123`, `Fixes #12`는 저장소가 쓰는 형태를 나타내는 예시이며 추천에 그대로 넣지 않는다.
`[TICKET]`은 다르다. 실제로 출력하는 자리 표시자이며 3단계가 사용 조건을 정한다.

가능한 변경 의도를 추론하되 용어와 효과 주장은 확인한 근거에 묶는다.

- 특정 분야 용어와 구성 요소 이름은 diff, 파일 경로, 심볼, 설정, 테스트 또는 기존 저장소 용례가 뒷받침할
  때만 사용한다.
- 대소문자와 철자를 포함해 기존 저장소 용어를 보존한다.
- 구체적인 저장소 식별자를 지어낸 동의어나 레이블로 바꾸지 않는다.
- 브랜치 이름과 최근 커밋은 조사 방향이나 기존 용어 확인에만 사용하며 현재 동작의 유일한 근거로 삼지 않는다.
- 외부 대상을 식별하는 토큰에는 이 스킬의 유일한 식별자 규칙을 적용한다. `[ABC-123]` 형태의 티켓 키,
  이슈나 PR 번호, `Fixes #12` 같은 자동 종료 키워드, 버전, 날짜 또는 사람 이름은 두 경우에만 추천에 넣는다.
  첫째, 사용자가 요청이나 스킬 인수에 직접 입력했다. 둘째, 확인한 변경 자체가 버전 문자열이나 이름이 바뀐
  심볼·경로의 식별자처럼 해당 값을 새로 추가하거나 이름을 바꾼다. 브랜치 이름, PR 제목, 주변 커밋 메시지
  같은 메타데이터는 근거가 아니다. 에이전트가 메타데이터에서 복사해 만든 인수도 사용자가 준 값이 아니다.
  작성자를 알 수 없으면 사용자가 준 값으로 취급하지 않는다.
- 변경 유형과 의도를 추론할 수 있지만 동작 또는 사용자에게 보이는 결과는 변경이 뒷받침할 때만 주장한다.
- 여러 설명이 가능하면 근거가 뒷받침하는 가장 구체적인 표현을 선택한다.
- 용어가 불명확하면 관련된 가장 작은 diff, 심볼, 테스트 또는 설정을 확인한다. 그래도 근거가 부족하면
  더 넓고 정확한 표현을 사용한다.

## 5단계: 접두사 선택

저장소가 conventional commit 접두사를 사용하면 습관이나 최근 빈도가 아니라 변경 의도로 선택한다.

다음의 일반적인 접두사만 사용한다.

- `feat:`: 사용자에게 보이는 새 기능, 명령, 스킬, 워크플로, 옵션, 통합 또는 문서화된 기능 추가
- `fix:`: 잘못되거나 깨졌거나 오래되었거나 안전하지 않거나 부정확한 동작, 설정 또는 지침 수정
- `refactor:`: 사용자에게 보이는 동작을 바꾸지 않는 구현 또는 문구 구조 변경
- `docs:`: 실행 가능한 스킬이나 에이전트 동작 계약이 아닌 문서와 글만 변경
- `test:`: 테스트만 추가 또는 변경
- `chore:`: 메타데이터, 생성 파일, 의존성 정리, CI·빌드·의존성 갱신 또는 저장소 관리

사용자가 명시적으로 요청하지 않으면 `ci:`, `build:`, `perf:`, `style:`, `revert:` 같은 드문 접두사를
제안하지 않고 가장 가까운 일반 접두사로 매핑한다.

- CI/CD, 빌드, 패키징, 의존성과 릴리스 워크플로 변경은 `chore:`를 사용한다.
- 새 동작이 없는 성능 목적 내부 재작성은 `refactor:`를 사용한다.
- 사용자에게 보이는 속도 저하나 회귀를 고치는 성능 수정은 `fix:`를 사용한다.

접두사 결정 규칙은 다음과 같다.

- 여러 변경이 섞이면 사용자에게 보이는 주된 의도를 사용한다.
- 에이전트 동작을 바꾸는 스킬, 프롬프트 또는 에이전트 지침 변경은 보통 `docs:`가 아니라 `feat:` 또는 `fix:`다.
- 의도한 규칙에 맞추거나 잘못된 지침 또는 모델·설정·명령 경로를 고치면 `fix:`를 사용한다.
- 없던 워크플로나 기능을 도입하면 `feat:`를 사용한다.
- 변경 의도가 하나뿐이지 않으면 추천 5개를 모두 `fix:` 또는 `feat:`로 만들지 않는다.
- 여러 일반 접두사가 가능하면 일부 추천에 대안을 사용하되 1번에는 가장 정확한 접두사를 사용한다.

## 6단계: 메시지 5개 추천

번호가 있는 표로 정확히 5개를 제시한다.

```markdown
| # | Commit Message |
|---|----------------|
| 1 | ... |
```

다음 규칙을 적용한다.

- 5개 모두 확인한 저장소 스타일과 접두사 규칙을 따른다.
- 제시하기 전에 모든 구체적인 명사와 결과 주장을 변경 내용이 뒷받침하는지 확인한다.
- 모든 추천에 4단계의 식별자 규칙을 적용한다.
- 동사, 강조점과 구체성 수준을 달리한다.
- 추천 순서대로 정렬하고 1번을 전체적으로 가장 좋은 선택으로 둔다.
- 각 메시지는 한 줄이다.
- 제목 한 줄만 사용하고 본문, 푸터 또는 트레일러를 넣지 않는다.
- 변경이 여러 관심사를 포함하면 일부 메시지가 한 관심사를 더 강조할 수 있다.

예시에서 `ABC-123`은 저장소가 사용하는 키 형태를 나타내고 브랜치 이름은 `feature/ABC-123`이라고 가정한다.
자리가 선택 사항이면 `fix: correct retry backoff`를 제안한다. 브랜치 이름만으로 `ABC-123`을 넣을 수 없다.
자리가 필수면 `fix: [TICKET] correct retry backoff`를 제안하고 사용자가 `[TICKET]`을 바꾸게 한다.

## 제약

- 읽기 전용이다. 파일을 스테이징, 커밋, amend, push 또는 수정하지 않는다.
- 추가 질문 없이 한 번의 답변으로 추천 5개를 제공한다. `[TICKET]` 같은 자리 표시자가 있으면 표 아래에
  사용자가 바꿔야 하며 그대로 커밋하지 말라는 한 줄을 추가할 수 있다. 답변을 기다리지 않는다.
- 도구 호출을 최소화한다. 보통 빠른 컨텍스트 명령 한 번으로 충분하며 필요할 때만 대상 명령을 추가한다.
- 나중에 추천으로 커밋을 만들더라도 메시지는 제목 한 줄로 유지하고 실제 `git commit`에 전달되는 메시지에도
  트레일러 금지 절대 규칙을 적용한다.
