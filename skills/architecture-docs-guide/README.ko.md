# 개발 설계 문서 작성 가이드

이 가이드는 특정 프로젝트의 문서 템플릿이 아니라, **개발 설계 문서를 어떻게 사고하고 작성할지**를 정하는 방법론이다. 문서의 중심은 파일명, 로컬 경로, 이슈 번호, 도구 명령, 플랫폼별 서식이 아니라 **의도, 제약, 결정, 대안, 트레이드오프, 검증 기준**이다.

## 1. 목적

개발 설계 문서는 시스템을 설명하는 모든 정보를 담는 문서가 아니다. 설계 문서는 독자가 다음 질문에 답할 수 있도록 돕는다.

- 왜 이 설계가 필요한가?
- 어떤 제약과 품질 목표가 설계를 밀어붙였는가?
- 어떤 구조와 책임 경계를 선택했는가?
- 어떤 대안을 버렸고, 그 이유는 무엇인가?
- 이 선택의 비용, 위험, 되돌릴 수 있는 조건은 무엇인가?
- 구현 또는 리뷰 전에 어떤 근거가 더 필요한가?

따라서 설계 문서에는 **결정에 영향을 주는 정보**만 남긴다. 실행 절차, 임시 운영값, 도구 사용법, 특정 환경의 우발적 세부사항은 별도 문서로 분리한다.

## 2. 독자 계약

문서를 쓰기 전에 독자 계약을 먼저 정한다. 독자 계약은 “이 문서를 읽은 사람이 무엇을 이해하거나 결정할 수 있어야 하는가”에 대한 합의다.

| 독자 의도 | 문서가 제공해야 하는 것 |
|:---|:---|
| 방향을 이해한다 | 배경, 문제 정의, 제약, 핵심 결정 |
| 설계를 리뷰한다 | 대안, 트레이드오프, 품질 목표, 위험 |
| 구현을 시작한다 | 책임 경계, 상호작용, 검증 기준 |
| 나중에 변경한다 | 결정 이유, 보존해야 할 제약, 재검토 조건 |

독자 계약이 정해지지 않은 문서는 쉽게 구현 메모, 회의록, 튜토리얼, 운영 절차가 섞인다. 설계 문서는 주로 **설명(explanation)**과 **참조(reference)**의 결합으로 유지한다. 문서 유형 분류는 섹션을 강제하는 계획표가 아니라, 독자의 의도와 맞지 않는 내용을 걷어내는 판단 도구로 쓴다.

## 3. 포함 기준

설계 문서에 넣을 내용은 “흥미로운 정보”가 아니라 “설계 판단을 바꾸는 정보”다. 다음 중 하나에 해당하면 본문에 포함한다.

- 구조, 책임 경계, 데이터 흐름, 배포 경계를 바꾼다.
- 성능, 보안, 신뢰성, 운영성, 접근성 같은 품질 목표를 결정한다.
- 외부 의존성, 인터페이스, 조직적 제약을 만든다.
- 기술 선택 또는 마이그레이션 방향을 제한한다.
- 미래 변경자가 반드시 보존해야 하는 의도를 설명한다.

반대로 다음 내용은 본문에서 줄이거나 분리한다.

- 특정 로컬 환경, 임시 식별자, 특정 작업 번호 같은 일회성 정보.
- 그대로 따라 하면 되는 운영 절차나 배포 절차.
- 전체 구현 코드처럼 설계 판단보다 구현 노이즈가 큰 예시.
- 플랫폼별 꾸밈, 도구별 메뉴 이름, 서식 세부 규칙.
- 같은 정의를 여러 곳에 반복하는 설명.

## 4. 권장 구조

기본 구조는 다음 순서를 따른다. 단, 문서의 독자 계약이 다르면 순서를 조정한다.

1. **맥락** — 문제, 배경, 범위, 비범위, 독자 가정.
2. **제약과 설계 동인** — 품질 목표, 외부 제약, 변경할 수 없는 조건.
3. **제안 설계** — 경계, 책임, 상호작용, 핵심 추상화.
4. **결정과 대안** — 선택한 안, 버린 안, 트레이드오프.
5. **위험과 검증** — 남은 불확실성, 실패 가능성, 확인해야 할 근거.
6. **열린 질문** — 아직 결정되지 않은 항목과 결정 주체.

각 섹션은 독립적으로 읽혀야 하지만, 같은 정의를 반복하지 않는다. 반복이 필요하면 개념을 한 번만 정의하고 나머지 위치에서는 그 의미를 참조한다.

## 5. 디테일 수준 결정

디테일 수준은 문서 길이가 아니라 **독자가 판단할 수 있는 정도**로 결정한다.

| 수준 | 목적 | 포함하는 정보 |
|:---|:---|:---|
| 낮음 | 방향 공유 | 문제, 핵심 선택, 주요 이유 |
| 중간 | 설계 리뷰 | 제약, 대안, 트레이드오프, 위험 |
| 높음 | 구현 착수 | 책임 경계, 상호작용, 검증 기준, 재검토 조건 |

기본값은 낮은 수준의 짧은 설계 노트다. 빠른 합의와 의사결정에 필요한 문제, 핵심 선택, 주요 이유를 먼저 남긴다. 독자가 구현을 시작하지 못하거나 리뷰자가 위험을 판단하지 못하면 중간 또는 높은 수준으로 깊이를 높인다. 반대로 문서가 실행 절차나 구현 세부사항으로 흐르면 깊이가 아니라 범위를 줄인다.

## 6. 결정 중심 작성법

중요한 설계 선택은 다음 형식으로 정리한다.

| 항목 | 질문 |
|:---|:---|
| Context | 어떤 문제나 제약 때문에 결정이 필요한가? |
| Decision | 무엇을 선택했는가? |
| Alternatives | 어떤 대안을 검토했는가? |
| Consequences | 어떤 장점, 비용, 위험을 받아들였는가? |
| Review trigger | 어떤 신호가 오면 결정을 다시 봐야 하는가? |

결정 기록은 미래 독자를 위한 것이다. “무엇을 했는가”보다 “왜 그 선택이 합리적이었는가”를 남긴다. 되돌릴 수 있는 결정과 되돌리기 어려운 결정은 구분한다. 작은 설계 문서에서는 별도 ADR을 만들지 않고 이 섹션 안에 결정 맥락과 결과를 함께 기록한다.

## 7. 품질 목표 작성법

품질 목표는 설계 선택을 이끄는 기준이다. 좋은 품질 목표는 다음 조건을 만족한다.

- 독자가 어떤 품질 속성이 중요한지 알 수 있다.
- 설계 대안 사이의 우선순위를 정하는 데 사용된다.
- 가능한 경우 관찰 가능한 기준으로 표현된다.
- 너무 많지 않다. 모든 것이 중요하면 아무것도 중요하지 않다.

품질 목표는 “빠르게”, “안정적으로”, “확장 가능하게” 같은 형용사로 끝나면 약하다. 어떤 상황에서 어떤 반응을 기대하는지까지 설명해야 설계 판단에 쓸 수 있다.

## 8. 다이어그램과 표

다이어그램과 표는 장식이 아니라 사고 도구다. 다이어그램은 항상 넣는 형식 요건이 아니라, 글만으로 관계·흐름·경계·비교를 따라가기 어려울 때 사용하는 압축 도구다. 다음 중 하나에 해당하면 산문만으로 설명하지 말고 다이어그램을 우선한다.

- 구성 요소가 3개 이상이고 경계나 책임이 서로 맞물린다.
- 요청, 데이터, 이벤트, 결정 흐름이 2단계 이상 이어진다.
- 외부 행위자, 외부 시스템, 내부 구성 요소의 관계가 오해될 수 있다.
- 대안이나 트레이드오프를 산문으로만 설명하면 비교 기준이 흩어진다.
- 같은 설명을 여러 문단으로 반복해야 해서 그림이 리뷰 시간을 줄인다.

다이어그램은 하나의 추상화 수준만 다룬다. 시스템 맥락과 실행 단위만으로 충분하면 더 깊은 그림을 만들지 않는다. 내부 구성 요소나 코드 수준 그림은 책임 경계나 변경 위험을 설명하는 데 실제로 도움이 될 때만 추가한다. 표는 비교 가능한 항목이 있을 때 사용하고, 단일 개념 설명은 산문으로 둔다.

## 9. 대칭성 점검

새 개념을 기존 개념과 나란히 도입할 때는 같은 차원을 비교한다.

| 차원 | 점검 질문 |
|:---|:---|
| 생명주기 | 생성, 활성, 종료, 실패 상태가 대응되는가? |
| 책임 | 누가 소유하고 변경하는가? |
| 관측성 | 성공과 실패를 어떻게 알 수 있는가? |
| 권한 | 누가 읽고 쓰고 실행할 수 있는가? |
| 호환성 | 기존 방식과 어떻게 공존하거나 전환되는가? |
| 되돌림 | 끄거나 되돌리는 조건이 있는가? |

대칭성 점검은 빠진 설계 차원을 찾기 위한 방법이다. 모든 차원을 억지로 채우라는 뜻은 아니다. 의도적으로 제외한다면 제외 이유와 재검토 조건을 남긴다.

## 10. 검증 질문

완성된 문서는 다음 질문에 답할 수 있어야 한다.

- 이 문서가 다루는 문제와 다루지 않는 문제는 무엇인가?
- 이 설계의 핵심 제약은 무엇인가?
- 가장 중요한 결정은 무엇이고, 왜 그렇게 결정했는가?
- 어떤 대안을 버렸고, 그 결과 어떤 비용을 받아들였는가?
- 어떤 위험이 남아 있으며, 무엇을 확인하면 위험이 줄어드는가?
- 미래 변경자는 어떤 의도를 보존해야 하는가?

답이 본문에 없으면 내용을 추가한다. 답은 있지만 특정 구현 세부사항을 알아야만 이해된다면 추상화 수준을 조정한다. 답이 여러 곳에 흩어져 있으면 구조를 다시 잡는다.

## 11. 참고 방법론

- Diátaxis: 독자 의도에 따라 문서 유형을 분리한다.
- arc42: 아키텍처 문서에서 품질 목표, 제약, 결정, 횡단 관심사를 구조화한다.
- C4 Model: 시스템을 맥락, 실행 단위, 구성 요소, 코드 수준으로 나누어 설명한다.
- ADR: 중요한 결정의 맥락, 선택, 결과를 보존한다.
- 기술 문서 스타일 가이드: 독자가 오해하지 않도록 명확하고 일관된 표현을 사용한다.

이 가이드는 위 방법론을 그대로 복제하지 않는다. 개발 설계 문서를 쓸 때 반복해서 적용할 수 있는 판단 규칙만 남긴다.
