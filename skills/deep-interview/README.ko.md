# Deep Interview (심층 인터뷰)

> 이 문서는 `SKILL.md`를 한국어로 옮긴 참고 문서입니다. 에이전트가 실행할 때 사용하는
> 기준 문서는 영어 `SKILL.md`입니다. 두 문서의 내용이 다르면 `SKILL.md`를 기준으로 합니다.

불확실한 아이디어를 실행 가능한 사양서로 바꿉니다. 한 번에 하나씩 영향력이 큰 질문을 하고, 질문하기 전에 확인할 수 있는 사실을 먼저 검증하며, 사용자가 최종 범위를 승인하기 전에는 구현하지 않습니다.

다음 자료는 해당 단계에 도달했을 때만 읽습니다.

- [`references/ask-ui.md`](references/ask-ui.md): 사용자에게 질문하기 전
- [`references/scoring-and-state.md`](references/scoring-and-state.md): 처음 점수를 매길 때와 점수나 상태가 바뀔 때
- [`references/spec-template.md`](references/spec-template.md): 최종 사양서를 만들 때
- [`references/auto-research-greenfield.md`](references/auto-research-greenfield.md): 그린필드 질문에 선택적 독립 조사가 도움이 될 때
- [`references/auto-answer-uncertain.md`](references/auto-answer-uncertain.md): 사용자가 결정을 명시적으로 위임했을 때
- [`references/lateral-review-panel.md`](references/lateral-review-panel.md): 모호성 단계가 바뀌거나 에이전트가 제시한 가정을 받아들이기 전

## 반드시 지켜야 하는 계약

- 라운드마다 질문은 정확히 하나만 합니다.
- 사용자에게 하는 모든 질문은 메인 대화에서 진행합니다. 지원 에이전트는 근거를 반환할 수 있지만 사용자에게 질문해서는 안 됩니다.
- 탐색 중에는 읽기 전용으로 유지합니다. 허용되는 쓰기는 사용자가 승인한 경로에 최종 사양서나 재개 가능한 상태 파일을 쓰는 것뿐입니다.
- 사용자의 언어에 맞춥니다. 코드 식별자, 경로, 명령어, 스키마 키, 고정 상태 토큰은 유지합니다.
- 사실과 결정을 분리합니다. 확인할 수 있는 사실은 근거에서 찾고, 선호·트레이드오프·범위·의도한 동작은 사용자에게 묻습니다.
- 브라운필드 근거는 경로, 기호, 명령어 또는 관찰된 동작으로 인용합니다.
- 모호성은 단조롭게 줄어들지 않는 것으로 다룹니다. 모순, 회피성 답변, 범위 확장은 모호성을 높일 수 있습니다.
- 사양서를 실행 흐름에 넘기기 전 사용자의 명시적 승인을 받습니다.
- 특정 공급업체, 도구 이름, 모델 또는 서브에이전트 구현을 필수로 요구하지 않습니다.

## 기능 라우팅

시작할 때 제품 이름을 미리 가정하지 말고 사용할 수 있는 기능을 확인합니다.

1. **구조화된 질문**: 가능하면 호스트의 네이티브 단일 질문 UI를 사용합니다. 일반 텍스트 폴백을 사용하기 전 `references/ask-ui.md`의 호스트별 모드나 설정 관문을 따릅니다. 관문에서 사용자 행동을 요구하면 이를 설명하고, 지원되는 모드로 사용자가 다시 시작할 때까지 턴을 끝냅니다.
2. **읽기 전용 탐색**: 저장소 검색·읽기 도구를 사용합니다. 사용할 수 없으면 관찰할 수 없는 사실만 묻습니다.
3. **독립적 추론**: 가능하면 격리된 읽기 전용 서브에이전트를 사용하고, 그렇지 않으면 메인 문맥에서 같은 관점 검토를 순서대로 수행합니다.
4. **병렬 처리**: 지원되면 독립적인 근거 수집을 병렬화합니다. 순차 실행을 하더라도 논리적 결과는 같아야 합니다.
5. **지속성**: 기본적으로 대화 안에 상태를 보관합니다. 사용자가 재개 가능성을 요청하고 경로를 승인했을 때만 상태를 씁니다.

기능이 없으면 효율만 달라질 뿐 인터뷰 계약은 달라지지 않습니다.

## Phase 0: 실행 설정

1. 아이디어, 명시적 제약, 원하는 깊이, 요청한 결과를 파싱합니다.
2. 모호성 임계값을 정합니다.
   - 사용자가 임계값을 말했더라도 모호성 1% 이상으로 더 엄격할 때만 따릅니다.
   - 더 느슨한 값은 `0.01`로 제한하고 값이 제한되었다고 기록합니다.
   - 그 외에는 `0.01`을 사용합니다.
3. 첫 질문 전에 임계값과 출처를 출력합니다.

```text
Deep Interview threshold: <percent> (source: <source>)
```

4. 작업을 분류합니다.
   - **브라운필드**: 기존 산출물을 변경하는 경우
   - **그린필드**: 관련 기존 구현이 아이디어를 제한하지 않는 경우
5. 브라운필드 작업이라면 질문하기 전에 가장 관련 있는 작은 소스 범위를 살핍니다. 오래 유지될 사실과 아직 남은 간격만 요약합니다.
6. 매우 큰 입력은 의도, 제약, 결정, 근거, 비목표를 보존하는 프롬프트용 요약으로 정규화합니다.
7. `references/scoring-and-state.md`에 정의된 상태를 초기화합니다.

## Round 0: 토폴로지 고정

성공하거나 실패하는 단위가 서로 독립적인 최상위 구성 요소를 1~6개 열거합니다. 모든 작업을 구성 요소로 취급하지 말고 구현 세부 사항을 결과 아래에 묶습니다.

구성 요소를 추가·삭제·통합·분리·보류해야 하는지 사용자에게 확인합니다. 이 라운드에서는 점수를 매기지 않습니다. 활성 구성 요소와 보류 구성 요소를 근거 및 보류 이유와 함께 저장합니다.

한 구성 요소를 깊이 다룬다고 다른 구성 요소의 모호성을 가리지 않게 합니다. 모든 활성 구성 요소는 적용되는 모든 명확성 차원을 결국 충족해야 합니다.

## 인터뷰 루프

임계값에 도달하거나 사용자가 조기 종료하거나 라운드 제한에 도달할 때까지 반복합니다.

### 1. 다음 간격 선택

점수가 가장 낮은 활성 구성 요소와 명확성 차원을 고릅니다. 비슷하게 약한 구성 요소 사이를 번갈아 다루어 하나의 작업 흐름이 인터뷰를 독점하지 않게 합니다.

가능한 경우 다음 순서로 질문을 우선합니다.

1. 온톨로지: 핵심 엔터티와 관계가 실제로 무엇인지
2. 목표: 어떤 관찰 가능한 결과가 발생해야 하는지
3. 제약: 경계, 호환성, 위험, 비목표, 되돌릴 수 없는 선택
4. 수용 기준: 성공을 증명하는 근거나 테스트
5. 맥락: 브라운필드 동작과 소유권을 어떻게 보존해야 하는지

한 번에 하나의 결정만 묻습니다. 접속사나 중첩된 글머리표로 여러 질문을 감추지 않습니다.

### 2. 먼저 근거 수집

확인할 수 있을 가능성이 있는 사실을 묻기 전에는 다음을 수행합니다.

- 관련 소스, 설정, 이력, 문서 또는 실행 출력을 검색합니다.
- 관찰한 근거를 밝히고 해석에만 확인이 필요할 때 질문합니다.
- 근거가 충돌하면 조용히 하나를 선택하지 말고 충돌을 제시합니다.
- 현재 외부 사실은 가능하면 신뢰할 수 있는 조사를 사용하고, 출처가 있는 사실과 추론을 구분합니다.

### 3. 질문 작성

`references/ask-ui.md`를 읽습니다. 다음 형식을 포함합니다.

```text
Round <n> | Component: <name> | Targeting: <dimension> | Why now: <reason> | Ambiguity: <score>%
```

구조화된 선택지가 유용하면 서로 구별되는 선택지 2~4개를 제시합니다. 근거가 가장 강한 추천을 첫 번째에 두고 트레이드오프를 설명하며, 항상 자유 입력도 허용합니다. 열린 질문이 더 나은 정보를 얻을 수 있다면 선택을 강요하지 않습니다.

### 4. 답변 정규화

실질적인 자유 답변은 다음 항목으로 중요한 내용만 다시 정리합니다.

- 결정
- 추론
- 사용자가 말한 제약
- 사용자가 말한 비목표
- 확인된 맥락

해석에서 의미가 사라졌을 가능성이 있으면 점수를 매기기 전에 사용자에게 해석을 확인합니다. 말하지 않은 요구사항을 추가하지 않습니다.

사용자가 선택을 위임하면 `references/auto-answer-uncertain.md`를 사용합니다. 결과를 명시적인 가정으로 전달하고 점수 자료에 설명된 대로 확신에서 비롯된 명확성을 제한하며, 그 가정이 최종 임계값을 넘기 전에 사용자의 확인을 받습니다.

### 5. 점수 계산과 보고

`references/scoring-and-state.md`를 읽습니다. 모든 활성 구성 요소에 점수를 매기고, 확정된 사실과 온톨로지를 갱신한 뒤 다음을 보고합니다.

- 차원별 점수와 남은 간격
- 이전 모호성과 새 모호성
- 모순, 불일치, 회피성 또는 범위 확장 신호
- 다음에 다룰 구성 요소와 차원
- 활성 구성 요소와 보류 구성 요소의 적용 범위

라운드가 한 번 진행되었다는 이유만으로 모호성을 낮추지 않습니다.

### 6. 라운드 제어 적용

- 에이전트가 3회 연속 결정을 해결하면 다음 결정은 사용자에게 직접 전달합니다.
- 10라운드에는 계속할지 멈출지 간단히 확인합니다.
- 20라운드에는 질문을 멈추고 위험을 표시한 사양서를 만듭니다.
- 사용자가 조기 종료하면 해결되지 않은 간격을 보존하고 모호성 관문을 실패로 표시합니다.

## 독립 검토

모호성이 단계 구간을 넘거나 에이전트가 제시한 가정을 받아들이기 전에 `references/lateral-review-panel.md`의 측면 검토를 실행합니다.

호스트가 지원하면 독립된 문맥을 사용합니다. 검토자 프롬프트에 의도한 결론을 흘리지 않습니다. 격리나 서브에이전트를 사용할 수 없으면 researcher, contrarian, simplifier, architecture 관점을 순서대로 수행합니다.

검증된 가장 영향력이 큰 결과만 다음 단일 질문에 반영합니다. 검토자는 범위를 바꾸거나 가정을 승인하거나 완료를 선언할 수 없습니다.

## 종료 관문

모호성이 임계값에 도달하면 다음을 수행합니다.

1. **범위 적용 감사**: 모든 활성 구성 요소에 명확한 목표, 제약, 수용 기준, 해당하는 경우 브라운필드 맥락이 있는지 확인합니다.
2. **모순 감사**: 해결되지 않은 충돌, 불확실한 외부 의존성, 확인되지 않은 가정을 열거합니다.
3. **목표 재진술**: 의도한 전체 결과를 한 문장으로 다시 쓰고 명시적 확인을 요청합니다.
4. **사양서 승인**: `references/spec-template.md`를 사용해 사양서를 작성하고 합의 내용을 정확히 담았는지 묻습니다.
5. **실행 연결**: 저장, 계획, 실행, 인계 또는 중단 중 다음 단계를 별도로 묻습니다. 실행 선택은 암묵적으로 포함되지 않습니다.

수치 임계값과 모든 종료 관문을 통과했을 때만 모호성 관문을 `passed`로 표시합니다. 조기 종료와 하드 캡 결과는 `risk-accepted` 또는 `pending`으로 남깁니다.

## 실패 처리

- 도구나 서브에이전트가 실패하면 동등한 현재 문맥 경로로 계속하고 기능 저하를 내부적으로 기록합니다.
- 근거를 사용할 수 없으면 항목을 `unverified`로 표시하고 사실을 만들어 내지 않습니다.
- 사용자가 확정된 사실과 모순되면 두 버전을 모두 보존하고 사실을 분쟁 상태로 표시하며 해당 점수를 낮추고 다음에 충돌을 다룹니다.
- 범위가 늘어나면 깊이 있는 질문을 계속하기 전에 토폴로지를 갱신합니다.
- 사용자가 질문을 건너뛰라고 하면 위험을 표시한 초안 사양서를 만들고 실행 승인은 별도로 요청합니다.

## 완료 점검표

- 토폴로지를 명시적으로 확인했습니다.
- 모든 활성 구성 요소를 독립적으로 다뤘습니다.
- 모든 질문이 하나의 결정을 다뤘습니다.
- 확인할 수 있는 사실을 질문하기 전에 조사했습니다.
- 점수가 답변이나 근거의 변화에 근거합니다.
- 모순과 범위 확장이 모호성을 높일 수 있습니다.
- 에이전트가 제시한 가정이 조용히 임계값을 넘지 않았습니다.
- 최종 목표와 사양서를 명시적으로 확인했습니다.
- 실행을 분리하고 승인을 요구했습니다.
- 구조화된 UI, 병렬 처리, 서브에이전트, 지속성이 없어도 흐름이 작동합니다.
