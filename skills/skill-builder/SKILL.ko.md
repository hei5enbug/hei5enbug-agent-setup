# 스킬 빌더

> 영어 원본: [SKILL.md](SKILL.md)
> 이 문서는 사람을 위한 비권위 한국어 번역본이다. 에이전트 실행 시 읽거나 사용하지 않는다.

여러 AI 에이전트 호스트에서 스킬을 생성, 수정, 검증하고 평가한다. 새 스킬 작성, 기존 스킬 개선,
기준 버전과의 동작 비교, 품질·분산 벤치마크, 패키징 또는 설명의 호출 정확도 개선에 사용한다.
이식 가능한 `SKILL.md` 묶음과 호스트 전용 스킬 패키지를 모두 다루며 대상 호스트의 메타데이터와 규칙을 보존한다.

핵심 작성 작업은 모든 호스트에서 가능하다. 포함된 스크립트에는 Python과 파일 시스템이 필요하다.
모델 기반 설명 최적화는 stdin으로 프롬프트를 읽고 stdout으로 응답만 쓰는 명령을 받을 수 있다.

영어 `SKILL.md`와 영어 참조 파일만 실행 원본으로 사용한다. 한국어 `.ko.md` 파일은 사람용 번역본이다.

초안, 테스트, 검토, 개선 순환으로 스킬을 만들고 개선한다.

## 이식성 계약

제품 이름이 아니라 기능에 맞춰 모든 호스트에서 같은 핵심 절차를 유지한다.

1. 작업자, 파일 시스템, subprocess, 브라우저·화면, 연결된 조사 도구와 아티팩트 표시 기능을 먼저 확인한다.
2. 기능이 없어도 의도 확인, 초안, 테스트, 검토, 개선, 패키징 또는 인계 단계를 유지한다.
3. 이식 가능한 지침에는 agent, host, worker, model runner 같은 중립 용어를 쓴다.
   특정 제품은 실제 대상이 요구하거나 범위가 명확한 adapter에서만 언급한다.
4. 숨은 환경 변수, 비공개 도구명, 설치 경로 또는 CLI 문법을 가정하지 않고 확인하거나 설정으로 받는다.
5. 호스트 간 출력과 스키마를 일관되게 유지한다. 없는 지표는 `null`이나 생략으로 나타내고 지어내지 않는다.
6. 설치된 스킬을 고칠 때 호스트별 매니페스트와 메타데이터를 보존한다.
   공통 동작은 `SKILL.md`, 피할 수 없는 호스트 차이는 작은 adapter나 명확한 참조에 둔다.
7. 사용자가 대상을 정하지 않았으면 현재 호스트에서 설치 위치, 매니페스트 또는 패키지 구조를 추론하지 않는다.
8. 기본적으로 각 스킬을 독립적으로 만든다. 내용이 길어 복사본이 달라질 위험이 있을 때만 형제 스킬의
   `../<skill>/references/<file>.md`를 읽을 수 있다. 형제 스킬을 호출하거나 스크립트에 의존하지 않는다.
   참조 목적과 누락 시 동작을 밝히고 절대 설치 경로를 쓰지 않는다. 안전·정확성 핵심 규칙은 자체 포함한다.
9. 호스트마다 같은 문구가 아니라 같은 품질 계약을 목표로 한다. 공통 평가 조건으로 판단하고 한 호스트의
   부족함 때문에 공통 규칙을 약하게 만들지 않는다.

| 기능 | 우선 경로 | 대체 경로 |
|---|---|---|
| 독립 작업자 | 스킬 적용·기준 사례를 병렬 실행 | 순서대로 실행하고 독립성 저하를 알린다. |
| 파일 시스템 | 반복 작업 공간과 포함 스크립트 | 프롬프트, 출력, 평가와 의견을 답변에 표시한다. |
| 브라우저·화면 | 생성된 검토 페이지 열기 | 정적 HTML을 만들거나 답변에서 검토한다. |
| 모델 subprocess | 반복 시험에 설정된 runner 사용 | 같은 rubric으로 직접 실행하고 격리 저하를 알린다. |
| 시간·토큰 지표 | 호스트가 제공한 값을 즉시 기록 | `null` 또는 선택 필드 생략 |
| 아티팩트 표시 | 호스트의 네이티브 방식 | 정확한 파일 경로 반환 |

## 핵심 순환

- 스킬의 동작, 호출 조건과 성공 기준을 정한다.
- 스킬과 포함 자료를 초안 작성하거나 검사한다.
- 실제적인 프롬프트를 만들고 가능하면 스킬 적용과 기준 실행을 모두 수행한다.
- 객관적 조건과 품질 판단으로 출력을 평가한다.
- 사용자가 예시를 볼 수 있도록 검토 화면을 일찍 만든다.
- 개별 사례에 과적합하지 않고 의견과 벤치마크 패턴으로 수정한다.
- 의견이 해결되거나 더 의미 있는 개선이 없을 때까지 반복한다.
- 환경이 지원하면 최종 스킬을 검증하고 패키징한다.

사용자가 순환의 어느 지점에 있는지 판단해 이어서 진행한다. 가벼운 검토를 원하면 결과를 보존하며 깊이를 줄인다.
작고 동작을 보존하는 수정은 직접 적용하고 동작 변경에는 관련 이전·새 사례를 실행한다.
작업자나 model runner를 시작하기 전에 `references/execution-methods.md`의 Evaluation model adapters만 읽고
현재 호스트의 모델·사고 강도 규칙을 적용한다. 실행 방식이나 반복 비용을 비교할 때만 전체 참조를 따른다.
필수 검사가 통과하고 추가 반복을 정당화하는 미해결 지적이 없으면 멈춘다.

## 사용자와 소통

사용자의 기술 수준에 맞춘다. evaluation, benchmark는 보통 그대로 쓸 수 있지만 JSON, assertion 같은 형식과
개념은 필요하면 설명한다. 결정과 결과를 먼저 말하고 기능 부족이 엄밀성을 낮춘 경우를 포함해 중요한 선택의
이유를 설명한다. 사용자의 출력 계약이 기본 보고보다 우선하며 아티팩트나 정확한 형식만 요청하면 그것만 출력한다.

## 스킬 생성 또는 수정

### 의도 확인

대화와 기존 파일에서 답을 먼저 찾는다.

1. 스킬이 가능하게 할 일
2. 실제 표현과 상황을 포함한 호출 조건
3. 만들어야 할 출력이나 부작용
4. 제약, 의존성, 경계 사례와 안전 경계
5. 테스트 가치와 객관적·주관적 검증 방식
6. 지원 호스트와 실제 호스트 차이
7. 유지하거나 줄일 품질, 시간과 반복 토큰 비용

기존 스킬은 사용자가 명시적으로 이름 변경을 요청하지 않으면 디렉터리 이름과 `name`을 보존한다.
수정 전에 원본 snapshot을 만들어 기준으로 사용한다.

### 인터뷰와 조사

구현을 실질적으로 바꾸는 공백만 질문한다. 연결 도구, 로컬 참조, 예시와 비교 스킬을 필요할 때 조사한다.
가능하면 독립 조사를 병렬로 하고 아니면 직접 순서대로 처리한다.

### `SKILL.md` 작성

- `name`: 안정적인 식별자
- `description`: 동작과 호출 조건을 담는 주요 호출 신호
- `compatibility`: 관련 도구, 의존성과 지원 환경
- 본문: 실행 절차, 제약, 참조와 출력 계약

설명은 실제 의도에 맞게 호출될 만큼 구체적이어야 하지만 키워드 목록이 되어서는 안 된다.
한 모델 계열의 라우팅 습관에 맞추지 않는다.

```text
skill-name/
├── SKILL.md
├── scripts/
├── references/
├── assets/
└── adapters/
```

필요한 호스트별 매니페스트는 보존한다. 현재 호스트가 지원한다는 이유만으로 새 제품별 매니페스트를 만들지 않는다.

### 여러 호스트

공통 스킬 본문 하나를 기준 원본으로 유지하고 호스트별 복사본을 만들지 않는다.

- 동작, 품질, 용어, 출력 계약과 체크리스트를 공통 본문에 둔다.
- 호출·검색 메타데이터, 도구명, 스크립트 호출, 호스트 필수 메타데이터와 호스트 전용 기능만 adapter에 둔다.
- 같은 eval corpus와 완료 조건으로 모든 호스트를 평가한다.
- 모든 호스트가 실패하면 공통 규칙을 고친다. 한 호스트만 실패하면 공통 규칙의 모호함을 먼저 고치고,
  그래도 실패할 때만 adapter 규칙을 추가한다. 변경 뒤 모든 호스트를 다시 실행한다.
- 한 호스트를 맞추려고 공통 품질을 낮추지 않는다.

### 번역본

한국어 `.ko.md`는 영어 기준 원본의 사람용 비권위 번역본이다. 원본을 수정하면 같은 작업에서 번역본도
갱신하고, 변경·삭제·이름 변경을 함께 처리한다. 번역본은 원본과 같은 의미를 유지하고 원본 링크와 비실행
표시를 포함한다. 실행 중 번역본을 읽지 않는다. 한국어 자체가 입력·출력 데이터인 사례는 영어 지침 안에
유지할 수 있다.

### 자동화 경계

| 작업 | 기본 방식 | 경계 |
|---|---|---|
| 의미, 의도, 모호함, 출력 품질 | 모델 판단 | 문맥 신호를 결정적 판정으로 만들지 않는다. |
| 계산, 스키마 검사, 파일 변환 | 기존 기능이나 터미널 도구 | 지원되는 parser나 validator를 우선한다. |
| 반복 모델 평가와 결과 수집 | 필요할 때 모델과 실행 스크립트 | 모델이 판단하고 스크립트는 실행·기록·집계한다. |

기존 도구와 단순 조합을 먼저 사용한다. 새 스크립트는 명확한 입출력 계약과 유지비를 정당화할 이점이
있을 때만 추가한다. 결정적 실행은 규칙의 정확성을 증명하지 않는다. validator는 선언된 입력에서 모든
지적이 실제 위반이고 지원되는 모든 위반을 찾을 수 있는 정확한 조건에만 사용한다. 주관적 판단은 모델이나
사용자에게 남기고 지원되지 않는 입력을 명시한다. 유효·무효·경계·미지원 입력을 시험한다.

paired comparison, 스크립트 추가 또는 실행 측정 주장을 할 때 `references/execution-methods.md`를 읽는다.
작은 미측정 제안에는 반복 비용 규칙을 적용하되 나중 비교를 위해 기준을 유지한다.

### 반복 실행 비용

모든 개선에서 지침·참조 로딩, 반복 읽기, 도구 출력, 모델 호출, 작업자 시작, 재시도와 불필요한 단계를
검사한다. 조건, 예외, 근거와 품질을 보존하면서 피할 수 있는 비용을 제거한다. 특정 모드의 긴 내용은
명시적인 읽기 조건과 함께 참조로 옮긴다.

선택한 방식과 전환 조건을 대상 스킬에 쓴다. 입력이 바뀌지 않으면 근거를 재사용하고 필요한 자료만 읽으며,
관련 상태가 바뀌면 다시 확인한다. 품질을 희생해 최신성 검사를 생략하지 않는다. 측정 근거 없이 비용이
줄었다고 주장하지 않고 정확성 문제가 없는 기준을 유지한다. 정상 실행마다 Skill Builder나 자체 수정,
새 벤치마크를 요구하지 않는다.

### 점진적 공개

1. 라우터가 항상 보는 이름과 설명
2. 선택되면 읽는 `SKILL.md`
3. 필요할 때만 읽거나 실행하는 포함 자료

가능하면 `SKILL.md`를 약 500줄 이하로 유지한다. 긴 세부 사항은 읽기 조건이 있는 참조로 옮기고
300줄보다 긴 참조에는 목차를 둔다. 여러 분야는 `references/aws.md`, `gcp.md`, `azure.md`처럼 분리하고
현재 변형만 읽게 한다.

### 안전과 예상 가능성

사용자가 밝힌 의도에 맞춘다. 악성, exploit, 은밀한 데이터 접근, 오해를 유도하는 동작 또는 예상하지 못한
외부 부작용을 만들지 않는다. 중요한 쓰기와 외부 동작을 지침에서 보이게 한다.

### 작성 패턴

명령형을 사용하고 중요한 제약의 이유를 설명한다. 반복되는 강한 금지보다 적응 가능한 원칙을 선호한다.
형식을 제한하는 규칙은 적용되는 모든 표면을 이름으로 밝힌다. 정확한 출력 계약에는 템플릿을 제공하고
모호함을 해소할 때 예시를 사용한다.

## 테스트 사례

첫 반복에는 실제적인 프롬프트 2개에서 3개를 만든다. 실제 입력 형태를 다양하게 하고 올바른 동작이 최소
수정이나 무수정인 사례를 하나 이상 둔다. 사용자 판단이 필요하면 공유하고, 기대 동작이 명확하고 실행이
승인됐으면 진행한 뒤 선택한 사례를 보고한다. 파일 시스템이 있으면 `evals/evals.json`에 다음 형태로 저장한다.

```json
{
  "skill_name": "example-skill",
  "evals": [{"id": 1, "prompt": "a realistic task", "expected_output": "success", "files": []}]
}
```

assertion이나 benchmark 아티팩트가 필요하면 `references/schemas.md`를 읽는다.

## 실행과 평가

### 1. 작업 공간과 기준

스킬 옆에 `<skill-name>-workspace/iteration-N/<eval-name>/`을 만들고 기존 스킬은 수정 전 snapshot을 기준으로
사용한다. 새 스킬은 스킬 없는 실행을 기준으로 한다. 두 실행의 프롬프트, 입력, 모델과 출력 요구를 같게 한다.
각 eval 디렉터리에 `eval_id`, `eval_name`, `prompt`, `assertions`를 가진 `eval_metadata.json`을 둔다.

### 2. 적용·기준 실행

호스트 한도와 파일·자원 충돌이 없으면 쌍을 병렬 실행한다. 적용 출력은 `with_skill/outputs/`, 기존 기준은
`old_skill/outputs/`, 새 스킬 기준은 `without_skill/outputs/`에 저장한다. 작업자를 사용할 수 없으면 같은 쌍을
순서대로 실행하고 독립성 저하를 기록한다. 파일 출력도 불가능하면 답변에서 간단히 검토한다.

### 3. assertion

실행 중 기계로 확인할 수 있는 요구사항만 정확한 조건과 범위가 있는 assertion으로 만든다.
주관적인 품질을 억지로 수치화하지 않는다. `eval_metadata.json`과 `evals/evals.json`을 함께 갱신한다.

### 4. 지표

호스트가 제공하는 시간과 토큰을 각 실행의 `timing.json`에 즉시 저장한다. 없는 값은 `null`이나 생략한다.
부모·작업자 호출, 읽기, 도구, 재시도를 중복 없이 포함하고 개발·평가 비용과 반복 실행 비용을 구분한다.

### 5. 평가와 집계

`agents/grader.md`로 각 실행을 평가하고 `grading.json`에 저장한다. 기대 항목은 `text`, `passed`, `evidence`를
사용한다. 기계 assertion은 자동화 경계를 만족할 때만 스크립트로 확인한다. 다음 명령으로 집계한다.

```bash
python <skill-builder-path>/scripts/aggregate_benchmark.py <workspace>/iteration-N --skill-name <name>
확인한 값을 `agents/grader.md`, `agents/comparator.md` 또는 `agents/analyzer.md`의 사후 분석 모드를
호출할 때 `skill_builder_path`로 전달하세요.
```

토큰은 `timing.json` 값만 사용하고 문자 수로 대신하지 않는다. 유효한 `grading.json`이 없는 실행은
`incomplete`이며 평균과 delta에서 제외한다. 두 설정이 모두 끝낸 eval만 delta에 포함한다.
적용 설정을 기준보다 먼저 놓고 `agents/analyzer.md`로 무차별 assertion, 큰 분산, 평균에 가려진 회귀와
시간·토큰 장단점을 확인한다.

### 6. 검토 화면

사용자 지정 HTML 대신 포함된 generator를 사용한다.

```bash
python <skill-builder-path>/eval-viewer/generate_review.py \
  <workspace>/iteration-N --skill-name "my-skill" \
  --benchmark <workspace>/iteration-N/benchmark.json
```

두 번째 반복부터 `--previous-workspace`를 추가한다. 브라우저가 있으면 열고, headless면 `--static`으로
공유하며 파일 표시가 불가능하면 프롬프트, 출력, 평가와 요약을 답변에 보여 준다. 주관적 수정 전에 만든다.

### 7. 의견

`feedback.json`이 있으면 `status`를 먼저 본다. `complete`일 때만 빈 의견을 승인으로 본다.
`in_progress`이거나 파일이 없으면 완료로 추정하지 않고 질문한다. 구체적인 지적을 우선하고 임시 서버를 닫는다.

## 스킬 개선

개별 사례가 아니라 새 사례에도 적용할 결정 절차를 고친다. 조건과 예외를 보존하며 불필요한 내용을 줄이고
명확성이 손상되면 삭제 대신 참조로 옮긴다. 중요한 제약의 이유를 설명한다. 반복하는 helper는 기존 기능과
단순 조합을 먼저 비교한 뒤 자동화 경계를 만족할 때만 스크립트로 만든다. 반복되는 문맥 판단은 스크립트가
아니라 판단 절차를 개선한다. 공통 동작과 호스트 adapter를 분리한다.

수정 뒤 영향을 받은 사례를 새 반복에서 다시 실행하고 원본이나 이전 버전과 비교한다. 작은 검토는 답변에,
큰 검토는 이전 반복과 연결한 검토 화면에 제시한다. 미해결 지적이 있는 동안만 반복하고 불확실한 결과를 밝힌다.

엄격한 A/B에는 `agents/comparator.md`, `agents/analyzer.md`를 읽고 설정 이름을 숨긴 독립 평가를 사용한다.
평가자는 `TIE`를 반환할 수 있다. 독립 작업자가 없으면 건너뛰고 제한을 알린다.

동작이 안정된 뒤 설명을 개선하거나 호출 평가를 실행할 때
`references/description-optimization.md`를 읽는다.

## 패키징

먼저 검증한다.

```bash
python <skill-builder-path>/scripts/quick_validate.py <path-to-skill-folder>
```

PyYAML이 필요하며 빈 이름·설명을 거부한다. `scripts/check_*.py`는 60초를 넘으면 실패한다.

```bash
python <skill-builder-path>/scripts/package_skill.py <path-to-skill-folder> [output-directory] [--check-installed]
```

출력 디렉터리는 스킬 밖이어야 한다. 패키지는 `.env`, `.git`, 이전 `.skill`, `evals/`,
`*-workspace/`, symbolic link를 제외한다. 임시 ZIP을 만들고 검증한 뒤 최종 파일을 교체하며 실패하면 기존
아티팩트를 보존한다. `--check-installed`는 사용자가 설치본 비교를 원할 때만 사용한다.

형제 참조는 개별 패키지에 포함되지 않으므로 디렉터리 구조를 함께 배포하거나 규칙을 자체 포함해야 한다.
호스트의 아티팩트 표시 기능을 사용하고 아니면 정확한 경로를 반환한다. 설치본이 읽기 전용이면 쓰기 가능한
임시 위치에 같은 이름으로 복사해 수정하고 패키징한다.

## 참조 파일

- `agents/grader.md`: assertion 기반 출력 평가
- `agents/comparator.md`: blind A/B 비교
- `agents/analyzer.md`: benchmark와 분산 분석
- `references/schemas.md`: eval, grading, timing, benchmark 스키마
- `references/execution-methods.md`: 실행 방식, 비교 모델, 반복과 비용 결정
- `references/description-optimization.md`: 호출 설명 최적화

## 완료 체크리스트

- 의도, 호출, 출력과 제약이 명확하다.
- 공통 지침은 기능 중심이며 우발적인 제품 결합이 없다.
- 좋은·나쁜 예시는 자체 규칙으로 평가됐다.
- 호스트 차이가 분리됐고 모든 호스트가 같은 corpus와 조건으로 평가됐다.
- 번역본이 원본의 변경, 삭제와 이름 변경을 반영한다.
- 형제 참조의 목적과 누락 동작을 밝히고 형제 스킬이나 스크립트를 호출하지 않는다.
- 스크립트의 입출력 계약과 미지원 입력이 명확하고 validator가 선언 범위에서 정확하다.
- 기존 도구를 비교했고 성능 주장은 실제 측정으로 뒷받침한다.
- 작업자·runner가 현재 호스트의 모델 규칙을 지키며 없는 지표를 지어내지 않았다.
- 반복 실행 비용을 품질 저하 없이 검토했고 대상 스킬에 방식 전환 조건이 있다.
- 실제 적용·기준 사례를 실행했거나 기능 제한을 밝혔다.
- assertion과 지표에 근거가 있으며 사용자가 검토 결과를 볼 수 있다.
