# 스킬 빌더

> 영어 원본: [SKILL.md](SKILL.md)
> 이 문서는 사람을 위한 비권위 한국어 번역본이다. 에이전트 실행 시 읽거나 사용하지 않는다.

여러 AI 에이전트 호스트에서 스킬을 생성, 수정, 검증하고 평가한다. 새 스킬을 처음부터 만들거나, 기존 스킬을
개선하거나, 기준 버전과 동작을 비교하거나, 품질과 분산을 benchmark하거나, 스킬을 패키징하거나, 호출이
안정적으로 일어나도록 설명을 최적화할 때 사용한다. 이식 가능한 `SKILL.md` 지침 묶음과 호스트 전용 스킬
패키지에 모두 적용하며, 대상 호스트가 요구하는 메타데이터와 규칙은 보존한다.

핵심 작성 작업은 모든 에이전트 호스트에서 가능하다. 포함된 스크립트에는 Python과 파일 시스템 접근이
필요하다. 모델 기반 설명 최적화는 stdin으로 프롬프트를 읽고 stdout으로 응답을 쓰는 명령이면 무엇이든
받는다.

영어 `SKILL.md`와 영어 참조 파일만 실행 원본으로 사용한다. `SKILL.ko.md`를 비롯한 `.ko.md` 파일은 비권위
인간용 번역본이며 실행 중에는 절대 불러오지 않는다.

초안 → 테스트 → 검토 → 개선의 반복 순환으로 스킬을 만들고 개선한다.

## 이식성 계약

제품 이름이 아니라 기능에 맞춰 적응해서 모든 에이전트 제품에서 같은 절차를 유지한다.

1. 방식을 고르기 전에 현재 호스트를 확인한다.
   독립 작업자, 파일 시스템 접근, subprocess 실행, 브라우저·화면 접근, 연결된 조사 도구, 아티팩트 표시
   기능이 있는지 본다.
2. 기능이 없어도 핵심 단계를 유지한다. 의도 파악, 초안, 테스트, 검토, 개선, 패키징 또는 인계가 그것이다.
3. 이식 가능한 지침에는 **agent**, **host**, **worker**, **model runner** 같은 중립 용어를 쓴다.
   특정 제품은 범위가 명확히 한정된 adapter 안에서만, 또는 사용자의 대상이 요구할 때만 언급한다.
4. 숨은 환경 변수, 비공개 도구 이름, 설치 디렉터리, CLI 문법을 가정하지 않는다. 확인하거나 설정으로 받는다.
5. 출력과 스키마는 호스트가 달라도 일관되게 유지한다. 지표를 쓸 수 없으면 `null`을 쓰거나 선택 필드를
   생략한다. 데이터를 지어내지 않는다.
6. 설치된 스킬을 고칠 때는 호스트별 매니페스트와 메타데이터를 보존한다.
   공통 동작은 `SKILL.md`에 두고, 피할 수 없는 호스트 통합은 작은 adapter나 이름이 분명한 참조 파일에
   격리한다.
7. 사용자가 대상을 정하지 않았다면 현재 작성 호스트에서 설치 루트, 매니페스트 형식, 패키지 구조를
   추론하지 않는다.
   초안에는 작업 범위 안의 쓰기 가능한 경로를 쓰고, 결과가 실질적으로 달라지면 목적지를 묻는다.
8. 모든 스킬은 기본적으로 자기완결이어야 한다. 공유 규칙이 길어서 복사본이 어긋날 위험이 있을 때만 형제
   스킬의 참조 파일을 읽을 수 있고, 형제 스킬을 호출하거나 그 스크립트에 의존해서는 안 된다.
   그 파일은 불러온 `SKILL.md`가 있는 디렉터리를 기준으로 `../<skill-name>/references/<file>.md` 형태로
   지정한다. 절대 경로나 호스트 설치 루트를 쓰지 않는다.
   읽는 형제 파일마다 무엇을 제공하는지와 파일이 없을 때 어떻게 하는지 선언한다.
   파일이 없으면 그 규칙 없이 진행하고 그 사실을 밝힌다. 요약본은 대체 수단이 아니다.
   정확성이나 안전에 필요한 규칙은 스킬 안에 둔다.
   공유할 내용이 몇 줄뿐이면 참조 대신 규칙을 복사한다.
9. 호스트마다 같은 출력이 아니라 같은 품질 계약을 목표로 한다.
   호스트마다 공통 완료 조건으로 판단한다. 같은 조건을 만족하는 표현 차이는 결함이 아니며, 문장 단위
   일치를 좇으면 스킬이 과도하게 복잡해진다.

다음 기능 대응표를 사용한다.

| 기능 | 우선 경로 | 대체 경로 |
|---|---|---|
| 독립 작업자 | 스킬 적용 사례와 기준 사례를 병렬로 실행 | 순서대로 실행하고 독립성이 낮아졌음을 밝힌다 |
| 파일 시스템 | 반복 작업 공간과 포함된 스크립트를 사용 | 프롬프트, 출력, 채점, 의견을 대화 안에 제시한다 |
| 브라우저·화면 | 생성된 검토 페이지를 연다 | 정적 HTML을 만들고, 파일을 제시할 수 없으면 대화 안에서 검토한다 |
| 모델 subprocess | 필요하면 설정된 runner로 반복 시험을 수행 | 같은 rubric으로 직접 프롬프트를 실행하고 격리가 낮아졌음을 밝힌다 |
| 시간·토큰 지표 | 호스트가 보고한 값을 즉시 기록 | `null`을 저장하거나 선택 값을 생략한다 |
| 아티팩트 표시 | 호스트의 네이티브 방식으로 패키지를 제시하거나 첨부 | 정확한 파일 경로를 반환한다 |

## 핵심 순환

- 스킬이 무엇을 해야 하고, 언제 호출되어야 하며, 성공이 무엇인지 정한다.
- 스킬과 포함 자료를 초안으로 쓰거나 검사한다.
- 실제적인 테스트 프롬프트를 만들고, 가능하면 스킬 적용 실행과 기준 실행을 모두 수행한다.
- 출력을 질적으로 평가하고, 적절한 곳에서는 객관적 assertion으로 평가한다.
- 사용자가 예시를 확인할 수 있도록 검토 화면을 일찍 만든다.
- 개별 프롬프트에 과적합하지 않으면서 의견과 benchmark pattern을 반영해 수정한다.
- 의견이 해소되거나 더 이상 의미 있는 변경이 없을 때까지 반복한다.
- 환경이 지원하면 최종 스킬을 검증하고 패키징한다.

사용자가 이 순환의 어디에 있는지 파악해 그 지점에서 이어 간다. 사용자가 정식 평가 대신 가벼운 확인을
원하면 요청한 결과는 유지하면서 깊이를 조절한다.

동작을 바꾸지 않는 작은 수정은 직접 고치고 확인한다. 동작이 바뀌면 관련된 이전·이후 사례를 실행한다.
작업자나 model runner를 시작하기 전에 `references/execution-methods.md`의 "Evaluation model adapters"만
읽고 현재 호스트가 요구하는 모델과 사고 강도를 적용한다.
실행 방식이나 반복 비용을 비교할 때는 `references/execution-methods.md`를 따른다. 측정하지 않은 변경을
거절하려는 목적만으로 그 파일을 불러오지 않는다.
필수 검사가 통과하고 다음 반복을 정당화하는 미해결 지적이 없으면 멈춘다.

## 사용자와 소통

사용자의 기술 수준에 맞춘다.
"평가", "benchmark" 같은 용어는 대개 그대로 써도 되지만, JSON 같은 형식과 assertion 같은 개념은 익숙하지
않을 만한 맥락이면 설명한다.

결정과 결과를 먼저 말한다. 어떤 테스트나 구조 선택이 왜 중요한지 설명한다. 특히 호스트 기능이 없어 엄밀성이
낮아질 때 그렇게 한다.
사용자의 출력 계약이 기본 보고 방식보다 우선한다.
아티팩트나 정확한 형식만 요청하면 그것만 출력하고 머리말, 설명, 인용, 상태 보고를 붙이지 않는다.

## 스킬 생성 또는 수정

### 의도 파악

사용자가 이미 제공한 정보를 다시 묻기 전에 대화와 기존 파일에서 답을 찾는다.

1. 이 스킬은 에이전트가 무엇을 할 수 있게 하는가?
2. 언제 호출되어야 하는가? 사용자가 쓸 법한 표현과 상황을 포함한다.
3. 어떤 출력이나 부수 효과를 만들어야 하는가?
4. 어떤 제약, 의존성, 경계 사례, 안전 경계가 있는가?
5. 테스트가 가치를 더하는가? 객관적으로 검증할 수 있는 작업은 대개 테스트가 도움이 되고, 주관적인 작업은
   사람의 검토에 더 기대게 된다.
6. 어떤 호스트를 지원해야 하고, 어느 부분이 정말로 호스트별 통합을 필요로 하는가?
7. 개선이 유지하거나 줄여야 할 품질 기준, 실행 시간 한도, 반복 토큰 비용은 무엇인가?

기존 스킬을 수정할 때는 사용자가 명시적으로 이름 변경을 요청하지 않는 한 원래 디렉터리 이름과 `name`
필드를 보존한다.
수정 전에 원본을 snapshot으로 남겨 기준으로 쓸 수 있게 한다.

### 인터뷰와 조사

구현을 실질적으로 바꾸는 공백만 질문한다. 필요하면 연결된 도구, 로컬 참조, 예시, 비슷한 스킬을 조사한다.
호스트가 지원하면 독립 조사를 병렬로 실행하고, 아니면 대화 안에서 조사한다.

### `SKILL.md` 작성

다음을 포함한다.

- **name**: 안정적인 스킬 식별자
- **description**: 스킬이 무엇을 하고 언제 쓰는지. 이것이 주된 호출 신호다
- **compatibility**: 관련이 있으면 필요한 도구, 의존성, 지원 환경
- **본문**: 실행 절차, 제약, 참조, 출력 계약

설명은 실제 의도에 반응할 만큼 구체적이되 키워드 나열이 되지 않게 한다. 한 모델 계열의 라우팅 습관에
맞추지 않는다.

### 이식 가능한 스킬의 구조

```text
skill-name/
├── SKILL.md            # 필수: 메타데이터와 핵심 절차
├── scripts/            # 선택: 입력과 출력 계약이 완결된 도구
├── references/         # 선택: 필요할 때 읽는 문서
├── assets/             # 선택: 템플릿과 출력 자료
└── adapters/           # 선택: 호스트별 통합 경계
```

대상이 요구하는 호스트별 매니페스트는 유지한다. 핵심 절차를 adapter마다 복제하지 않는다.
현재 에이전트 호스트가 지원한다는 이유만으로 제품 전용 매니페스트를 만들지 않는다. 요청받은 대상에만
추가하고, 기존 패키지를 수정할 때는 있는 것을 보존한다.

### 여러 대상 호스트

스킬이 둘 이상의 호스트에서 실행되어야 하면 기준이 되는 스킬 본문 하나를 유일한 원본으로 유지한다.
호스트별 복사본을 만들어 따로 관리하지 않는다. 복사본은 거의 즉시 어긋난다.

- 동작 규칙, 품질 기준, 용어, 출력 계약, 검토 체크리스트는 공통 본문에 둔다.
- adapter에는 실제 호스트 차이만 둔다. 호출·검색 메타데이터, 도구 이름, 스크립트 호출 방식, 호스트가
  요구하는 메타데이터, 호스트 전용 기능을 쓰는 절차가 여기에 해당한다.
- 모든 대상 호스트를 같은 eval corpus와 완료 조건으로 평가해 결과를 비교할 수 있게 한다.
- 수정 전에 실패의 원인을 귀속한다. 모든 호스트가 한 사례에서 실패하면 공통 규칙을 고친다. 한 호스트만
  실패하면 공통 규칙이 모호한지 먼저 확인해 명확히 한다. 명확해진 공통 규칙으로도 그 호스트가 실패할
  때만 adapter 규칙을 추가한다. 두 경우 모두 변경 후 모든 호스트에서 corpus를 다시 실행한다.
- 한 호스트가 규칙을 잘 따르지 못한다고 해서 공통 규칙을 최저 수준으로 약하게 만들거나 늘리지 않는다.
  그 호스트의 격차는 해당 adapter 안에 가둔다.

### 번역본

영어를 기준 실행 언어로 유지한다. 사람이 읽는 영어 Markdown 지침과 문서마다 의미가 같은 한국어 `.ko.md`
번역본을 같은 위치에 둔다. 코드, 스키마, eval 자료, 생성 아티팩트, 이미 다른 언어로 쓰인 문서는 복제하지
않는다.

번역본은 원본과 같은 변경에 속한다. 권위 있는 파일을 고칠 때마다 같은 작업에서 번역본도 고친다. 갱신을
미루거나, 원본에 더 이상 없는 규칙을 설명하는 번역본을 남기지 않는다.

에이전트가 읽지 않더라도 오래된 번역본은 결함이다. 독자는 그 문서로 스킬의 동작을 익히므로, 낡은 번역본은
스킬이 따르지 않는 규칙을 가르친다.

번역본마다 원본을 링크하고 비권위 인간용 문서임을 밝힌다. `SKILL.md`는 실행 중에 번역본을 읽지 말라고
에이전트에게 지시해야 한다. 규칙이 뒤집히면 번역본이 옛 규칙 옆에 문장을 덧붙인 것이 아니라 새 규칙을
말하는지 확인한다. 원본 파일을 삭제하거나 이름을 바꾸면 같은 작업에서 번역본도 삭제하거나 이름을 바꾼다.

### 자동화 경계

모델 크기나 도구 우선이라는 고정된 순서가 아니라 작업의 요구 사항으로 결정한다.

| 작업 | 기본 방식 | 경계 |
|---|---|---|
| 의미, 의도, 모호성, 출력 품질 | 프롬프트에 대한 모델 판단 | 맥락 신호를 결정적 판정으로 바꾸지 않는다. |
| 계산, 스키마 검사, 파일 변환 | 기존 호스트 기능이나 터미널 도구 | 직접 만든 코드보다 지원되는 parser나 validator를 우선한다. |
| 반복 모델 평가와 결과 수집 | 필요하면 모델과 실행 스크립트 | 판단은 모델이 하고, 스크립트는 일정, 기록, 집계를 맡는다. |

정확한 기계 작업은 스크립트를 포함하기 전에 기존 도구와 단순한 조합을 먼저 시도한다.
새 스크립트는 충족되지 않은 입출력 계약이 있어야 하고, 작성·테스트·의존성·유지보수 비용을 정당화하는 이득이
있어야 한다.
작고 한 번뿐인 작업이면 스크립트가 있어도 직접 프롬프트 실행이 여전히 선택지다.

결정적으로 실행된다는 사실이 규칙의 정확성을 증명하지는 않는다.
검증기는 선언된 입력에 대한 정확한 술어일 때만 포함한다. 보고하는 실패는 모두 실제 위반이어야 하고,
지원 범위 안의 위반은 모두 실패로 잡혀야 한다.
지원하지 않는 입력은 명시적으로 보고한다.
의미적, 주관적, 확률적, 맥락적 판단은 모델이나 사용자에게 남긴다.
기존 heuristic 분석기는 근거를 제공할 수 있을 뿐 단독 판정 근거가 될 수 없다. 새 heuristic 검사기를 만들지
않는다.
스크립트가 모델을 호출할 수는 있으나 그 출력의 불확실성을 보존해야 한다.
포함한 검증기는 유효 입력, 무효 입력, 경계 입력, 지원하지 않는 입력을 모두 시험한다. 예시만으로는 완전성이
증명되지 않는다.

짝지은 비교를 계획하거나 실행할 때, 스크립트를 추가할 때, 실행 측정으로 주장을 뒷받침할 때는
[실행 방식](references/execution-methods.md)을 읽는다.
측정하지 않은 작은 제안에는 그 참조를 불러오지 말고 아래 반복 비용 규칙만 적용하며, 이후 비교가 후보를
입증할 때까지 기준을 유지한다.

### 반복 실행 비용

이 규칙은 스킬 빌더 자신과 스킬 빌더가 만들거나 개선하는 모든 스킬에 적용한다.
개선할 때마다 평상시 사용 비용을 점검한다. 불러오는 지침과 참조, 반복 읽기, 도구 출력, 모델 호출, 작업자
시작, 재시도, 불필요한 단계가 대상이다.
조건, 예외, 근거, 출력 품질을 유지하면서 피할 수 있는 작업을 없앤다.
분량이 큰 모드별 지침은 읽기 조건을 명시해 참조로 옮긴다.

선택한 방식과 전환 조건을 대상 스킬 자체에 기록한다.
평상시 사용에서는 필요한 자료만 불러오고, 아직 유효한 근거는 재사용하며, 해당하는 검사를 실행한다.
입력이나 관련 상태가 바뀌면 다시 읽는다. 토큰을 아끼려고 최신성 확인을 건너뛰지 않는다.
"한 번만 읽는다"거나 "다시 읽지 않는다"는 무조건적 규칙을 만들지 않는다. 재사용은 변하지 않은 입력으로
범위를 한정한다.
실행 비용 근거가 없으면 제안된 절감을 미검증으로 표시하고 기준을 기본값으로 유지한다.
기준에 정확성 결함이 없으면 측정하지 않은 문구 최적화를 이유로 다시 쓰지 않는다.
사용자가 후보 문구를 요청하지 않는 한, 측정하지 않은 최적화에는 기준을 유지한다는 점, 미검증 상태, 재고에
필요한 측정만 간결히 답한다. 추측에 기반한 대안을 만들지 않는다.
평상시 호출마다 스킬 빌더 의존, 자기 편집, 새 benchmark를 추가하지 않는다.
개선 과정에서 바뀐 실행 동작을 비교하고, 요구 사항, 입력, 도구, 모델 동작이 실질적으로 달라질 때까지 검증된
선택을 재사용한다.
뒷받침되는 개선이 없으면 기존 동작을 그대로 둔다.

### 점진적 공개

세 단계를 사용한다.

1. **메타데이터** — 이름과 설명. 라우터가 항상 볼 수 있다
2. **`SKILL.md` 본문** — 스킬이 선택될 때 불러온다
3. **포함 자료** — 필요할 때만 읽거나 실행한다

가능하면 `SKILL.md`를 500줄 안팎으로 유지한다. 깊은 내용은 링크가 분명한 참조로 옮기고, 300줄이 넘는 참조
파일에는 목차를 붙인다.

여러 영역을 다루는 스킬은 변형별로 구성한다.

```text
cloud-deploy/
├── SKILL.md
└── references/
    ├── aws.md
    ├── gcp.md
    └── azure.md
```

모든 변형을 불러오지 않도록 어떤 참조를 골라야 하는지 에이전트에게 알려 준다.

### 안전과 예상 가능성

스킬은 사용자가 밝힌 의도와 일치해야 한다. 악성 코드, 취약점 공격 절차, 은밀한 데이터 접근, 오도하는 동작,
예상하지 못한 외부 부수 효과를 만들지 않는다.
실질적인 쓰기와 외부 작업은 지침에서 드러나게 한다.

### 작성 pattern

명령형으로 쓰고 중요한 제약에는 이유를 설명한다. 대문자 강조를 반복하기보다 적응 가능한 원칙을 쓴다.

형식을 제약하는 규칙은 그 규칙이 다스리는 모든 표면을 명시하거나, 표면과 무관하게 서술해야 한다.

정확한 출력 계약에는 템플릿을 제공한다.

```markdown
## Report structure
Use this exact structure:
# [Title]
## Executive summary
## Key findings
## Recommendations
```

모호함을 없앨 때는 예시를 사용한다.

```markdown
## Commit message format
Input: Added user authentication with JWT tokens
Output: feat(auth): implement JWT-based authentication
```

## 테스트 사례

첫 반복에는 실제적인 프롬프트를 2~3개 만든다.
같은 형태를 반복해서 시험하지 말고 스킬이 실제로 만나게 될 입력 유형을 다양하게 한다.
사례가 늘어나면 올바른 동작이 최소한의 변경이거나 변경하지 않는 것인 사례를 최소 하나 포함한다. 지나치게
공격적인 스킬은 받아들일 만한 입력까지 고쳐 이 사례에서 실패한다.
사용자의 판단이 필요하면 사례를 공유해 확인받는다. 사용자가 이미 실행을 승인했고 기대 동작이 분명하면
그대로 진행하고 선택한 사례를 보고한다.

파일 시스템을 쓸 수 있으면 사례를 `evals/evals.json`에 저장한다.

```json
{
  "skill_name": "example-skill",
  "evals": [
    {
      "id": 1,
      "prompt": "A realistic user task",
      "expected_output": "A concise description of success",
      "files": []
    }
  ]
}
```

assertion이나 benchmark 아티팩트가 필요하면 `references/schemas.md`를 읽는다.

## 테스트 사례 실행과 평가

이 과정을 하나의 연속 절차로 다룬다. 가능하면 호스트의 네이티브 작업자를 쓰고, 제품 전용 테스트 명령에
의존하지 않는다.

이 파일의 모든 명령은 `<skill-builder-path>`를 사용한다. 이는 불러온 이 `SKILL.md`가 들어 있는 디렉터리의
절대 경로다.
그 값을 한 번 확정하고 절대 경로로 스크립트를 실행한다. 스크립트를 실행하려고 사용자의 작업 디렉터리를
바꾸지 않는다.
`agents/grader.md`, `agents/comparator.md` 또는 `agents/analyzer.md`의 사후 분석 모드를 호출할 때마다 확정한
값을 `skill_builder_path`로 전달한다.
포함된 스크립트에는 PyYAML이 설치된 Python 3.12 이상이 필요하다. PyYAML이 없으면 설치 안내와 종료 코드 2로
멈춘다.

### 1단계: 작업 공간과 기준 준비

파일 시스템을 쓸 수 있으면 스킬 옆에 `<skill-name>-workspace/`를 만든다. 결과는
`iteration-N/<descriptive-eval-name>/` 형태로 정리한다.

새 스킬에서는 기준 실행에 스킬을 주지 않는다. 기존 스킬에서는 수정 전 원본을 snapshot으로 남겨 그것을
기준으로 쓴다.
적용 실행과 기준 실행의 프롬프트, 입력, 모델 설정, 요구 출력을 동일하게 유지한다.

각 eval 디렉터리에 `eval_metadata.json`을 쓴다.

```json
{
  "eval_id": 0,
  "eval_name": "descriptive-name",
  "prompt": "The user's task prompt",
  "assertions": []
}
```

### 2단계: 스킬 적용 실행과 기준 실행 시작

독립적인 쌍은 호스트 한도 안에서, 그리고 파일이나 자원 경합이 없을 때만 동시에 실행한다.
`references/execution-methods.md`를 사용해 모델 설정과 측정 조건을 비교 가능하게 유지한다.

스킬 적용 작업 템플릿:

```text
Execute this task.
- Skill path: <path-to-skill>
- Task: <eval prompt>
- Input files: <paths or none>
- Save outputs to: <workspace>/iteration-N/<eval-name>/with_skill/outputs/
- Outputs to save: <artifacts the user cares about>
```

새 스킬의 기준에는 `without_skill/outputs/`를, 기존 스킬의 기준에는 `old_skill/outputs/`를 사용한다.

독립 작업자를 쓸 수 없으면 같은 쌍을 순서대로 실행한다.
호스트가 허용하는 한 기준 지침을 수정된 스킬과 격리하고, 비교의 독립성이 낮다는 사실을 기록한다.
순차 실행이나 출력 저장조차 불가능하면 대화 안에서 초점을 좁힌 확인을 수행하고, 사용자에게 예시를 직접
판단해 달라고 요청한다.

### 3단계: 실행 중에 assertion 작성

기계로 검증할 수 있는 요구 사항에는 객관적이고 서술적인 assertion을 만든다.
기계 assertion은 "자동화 경계"에 따라 정확한 술어와 범위를 정의해야 한다. 그렇지 않으면 질적으로 채점한다.
주관적인 품질에 억지로 정량 assertion을 씌우지 않는다.
`eval_metadata.json`과 `evals/evals.json`을 함께 갱신하고, 그 assertion이 무엇을 측정하는지 설명한다.

### 4단계: 가능한 지표 수집

호스트가 보고한 시간과 토큰 데이터를 각 실행의 `timing.json`에 즉시 저장한다. `references/schemas.md`를
따른다. 호스트가 값을 제공하지 않으면 `null`을 쓰거나 선택 필드를 생략한다.

비용 비교에는 부모와 작업자 호출, 읽기, 도구 실행, 재시도를 중복 없이 포함한다.
반복 실행 비용을 개발·채점 부담과 분리한다. 기준은 `references/execution-methods.md`에 있다.

### 5단계: 채점과 집계

1. `agents/grader.md`를 읽고 각 실행을 채점한다. 가능하면 독립 작업자를 쓰고, 아니면 대화 안에서 채점한다.
   `grading.json`을 저장한다.
   기대 객체는 `text`, `passed`, `evidence`를 사용해야 한다.
2. 결정적 스크립트는 "자동화 경계"를 만족하는 assertion에만 사용한다.
   결정적으로 실행된다고 해서 proxy나 heuristic assertion이 유효해지지는 않는다.
3. 반복을 집계한다.

   ```bash
   python <skill-builder-path>/scripts/aggregate_benchmark.py <workspace>/iteration-N --skill-name <name>
   ```

   `tokens`는 오직 `timing.json`에서만 온다. 호스트가 보고하지 않았으면 `null`로 남고 뷰어에는 N/A로
   표시된다. 문자 수는 단위가 다르므로 절대 대신 쓰지 않는다.
   읽을 수 있고 스키마에 맞는 `grading.json`이 없는 실행은 `incomplete`로 표시되며 모든 평균과 차이
   계산에서 제외된다. 차이는 두 설정이 모두 완료한 eval ID만 다룬다.

4. 스킬 적용 설정을 각각의 기준 설정 앞에 둔다.
5. `agents/analyzer.md`의 해당 절을 읽고 변별력 없는 assertion, 큰 변동, 평균에 가려진 회귀, 시간·토큰
   교환 관계를 살핀다.

### 6단계: 검토 화면 생성

직접 검토 HTML을 만들지 말고 포함된 생성기를 사용한다.

```bash
python <skill-builder-path>/eval-viewer/generate_review.py \
  <workspace>/iteration-N \
  --skill-name "my-skill" \
  --benchmark <workspace>/iteration-N/benchmark.json
```

두 번째 이후 반복에는 `--previous-workspace <workspace>/iteration-(N-1)`을 덧붙인다.

- 브라우저를 쓸 수 있으면 생성된 검토 페이지를 연다.
- headless 호스트에서는 `--static <output-path>`를 더하고 HTML 아티팩트를 제시한다.
- 파일을 제시할 수 없으면 프롬프트, 출력, 채점, benchmark 요약을 대화 안에 보여 주고 의견을 대화로 받는다.

출력을 어떻게 검토하는지, 정량 결과가 어디에 나오는지 사용자에게 알려 준다. 주관적인 수정을 하기 전에 검토
화면을 만들어 사용자가 근거를 일찍 볼 수 있게 한다.

### 7단계: 의견 읽기

파일 기반 의견을 쓸 수 있으면 `feedback.json`을 읽는다. `status`를 먼저 확인한다. 값이 `complete`일 때만
비어 있는 의견 항목이 출력을 받아들였다는 뜻이다. `in_progress`이거나 파일이 없으면 검토가 끝나지 않은
것이므로, 침묵을 승인으로 보지 말고 사용자에게 묻는다. 구체적인 불만을 우선한다. 검토가 끝나면 임시 뷰어
서버를 종료한다.

## 스킬 개선

1. 시험한 예시만 고치지 말고 의견에서 일반화한다.
   사례가 아니라 판단 절차를 쓴다. 스킬이 본 적 없는 사례에도 적용할 수 있는 기준을 쓰고, 전체 목록이
   아니라 예시임을 밝힌 두세 쌍을 덧붙인다.
2. 프롬프트를 간결하게 유지하고 반복적이고 비생산적인 작업을 만드는 지침은 없애되, 의미가 살아남는 곳에서만
   압축한다.
   모든 제약, 임계값, 범위를 보존하고, 다른 맥락이 없는 코딩 에이전트에게도 각 규칙이 명확하게 만든다.
   잘라내면 명확성이 떨어지는 내용은 삭제하지 말고 참조로 옮긴다.
3. 제약이 왜 중요한지 설명해 성능이 좋은 모델이 새로운 사례에 적응할 수 있게 한다.
4. 여러 실행이 같은 보조 로직을 다시 만들면 먼저 호스트 기능, 검증된 도구, 단순한 도구 조합을 비교한다.
   "자동화 경계"를 만족하고 정확성, 유지보수 또는 성능에서 측정 가능한 이득이 있을 때만 스크립트를 포함한다.
5. 여러 실행이 같은 맥락적 판단을 되풀이하면, 그 판단을 스크립트로 바꾸지 말고 스킬의 판단 절차와 예시를
   개선한다.
6. 이식 가능한 동작은 핵심에 두고 호스트별 방식은 adapter에 격리한다.
   여러 호스트를 지원하는 스킬에서는 "여러 대상 호스트"의 실패 귀속 규칙으로 수정 위치를 정한다.

동작을 수정한 뒤에는 영향을 받는 사례를 새 반복에서 다시 실행한다.
사용자의 결정에 따라 원본이나 이전 버전과 비교한다.
작은 검토에서는 비교를 대화 안에 제시하고, 그 밖에는 검토 화면을 이전 반복과 연결한다.
시험 예산 안에서 미해결 지적에 대해서만 반복한다. 결론이 나지 않은 비교는 솔직하게 보고한다.

## 심화: blind 비교

엄밀한 A/B 비교에는 `agents/comparator.md`와 `agents/analyzer.md`를 읽는다. 어느 설정이 만든 출력인지 밝히지
않고 독립 심사자에게 출력을 준다.
비교자는 `TIE`를 반환할 수 있다. 분석기는 `A`, `B`, `TIE`를 모두 받고, TIE에서는 승자를 지어내지 않고 두
스킬을 함께 분석한다.
독립 작업자가 없으면 blind 비교를 건너뛰고 그 한계를 밝힌다.

## 설명 최적화

스킬 동작이 안정된 뒤 frontmatter 설명을 조정하거나 호출 평가를 실행할 때
[설명 최적화](references/description-optimization.md)를 읽는다.
작업량과 실행 방식 비교 규칙에 따라 직접 프롬프트와 model runner 중에서 고른다.

## 패키징과 제시

먼저 검증한다.

```bash
python <skill-builder-path>/scripts/quick_validate.py <path-to-skill-folder>
```

검증에는 PyYAML이 필요하며 `name`이나 `description`이 비어 있으면 거부한다. 포함된 `scripts/check_*.py`
검사기마다 60초가 주어진다. 더 오래 걸리면 `TIMEOUT`으로 보고되고 검사에 실패한다.

Python과 파일 시스템을 쓸 수 있으면 다음으로 패키징한다.

```bash
python <skill-builder-path>/scripts/package_skill.py <path-to-skill-folder> [output-directory] [--check-installed]
```

출력 디렉터리는 스킬 폴더 밖이어야 한다. 패키지에는 `.env` 파일, `.git`, 이전 `.skill` 파일, `evals/`,
`*-workspace/` 디렉터리, 심볼릭 링크가 들어가지 않는다. 건너뛴 링크는 각각 보고한다.
패키징 도구는 목적지 옆에 임시 ZIP을 만들어 검증한 뒤 최종 `.skill` 파일로 교체한다. 빌드가 실패하면 임시
파일을 지우고 기존 패키지를 그대로 둔다.
설치된 다른 복사본과 파일 단위로 비교하고 싶을 때만 `--check-installed`를 전달한다. 이 옵션이 없으면 패키징
도구는 사용자의 홈 디렉터리를 읽지 않는다.

한 스킬을 패키징하면 형제 스킬의 파일은 제외된다. 형제 디렉터리 구조를 유지한 채 번들을 배포하거나, 참조한
규칙을 스킬 안으로 복사하고 참조를 고친 뒤 단독으로 패키징한다.

호스트의 네이티브 아티팩트 제시 방식이 있으면 그것을 쓰고, 없으면 정확한 출력 경로를 알려 준다.
설치된 원본이 읽기 전용이면 쓰기 가능한 임시 위치로 복사하고 원래 이름을 유지한 채 복사본을 수정·패키징한
뒤 결과를 반환한다.

## 완료 체크리스트

- 의도, 호출 조건, 출력, 제약이 명시되어 있다.
- 핵심 지침이 기능 기반 표현을 쓰고 의도치 않은 특정 제품 결합이 없다.
- 모든 예시를 스킬 자신의 규칙으로 채점했다. 좋은 예시는 규칙을 모두 만족하고, 나쁜 예시는 그것이 보여 주는
  규칙을 위반한다.
- 꼭 필요한 호스트별 동작이 격리되고 문서화되어 있다.
- 여러 호스트를 지원하는 스킬이라면 모든 호스트를 같은 eval corpus로 평가했고, adapter 규칙마다 공통 규칙을
  명확히 해도 해결되지 않는 호스트 차이가 근거로 있다.
- 스킬 안의 모든 번역본이 현재 원본과 일치한다. 뒤집힌 규칙, 삭제, 이름 변경도 반영되어 있다.
- 형제 참조마다 상대 경로, 목적, 파일이 없을 때의 동작을 선언했다. 스킬은 형제 스킬을 호출하지 않고 형제
  스크립트에 의존하지 않는다.
- 포함된 스크립트마다 입력과 출력 계약이 완결되어 있고 지원하지 않는 입력을 명시적으로 보고한다.
- 포함된 검증기마다 선언한 범위 안에서 건전하고 완전하다. 맥락적 판단은 모델이나 사용자에게 남아 있다.
- 직접 만든 코드를 추가하기 전에 기존 호스트 기능과 검증된 도구를 비교했다.
- 성능 주장은 대표적인 입력에서 측정한 것이며 구현 언어에서 추론하지 않았다.
- 시작한 모든 작업자와 model runner가 현재 호스트가 요구하는 모델과 사고 강도를 사용했고 호스트 간 대체가
  없었다. 실행할 수 없었던 경우는 미검증으로 표시했다.
- 불확실하거나 바뀐 방식은 실제 출력으로 비교했거나 명시적으로 미검증으로 표시했다. 얻을 수 없는 지표를
  지어내지 않았다.
- 스킬 빌더와 대상 스킬의 반복 실행 비용을 품질을 낮추지 않고 점검했다.
- 대상 스킬이 사용할 때마다 benchmark를 요구하지 않고 자신의 방식과 전환 조건을 기록한다.
- 시간·토큰 교환은 품질 기준과 사용자 한도를 따르며, 개발과 평가 비용은 분리되어 있다.
- 실제적인 스킬 적용 테스트와 기준 테스트를 실행했거나 기능 한계를 밝혔다.
- assertion과 지표에 근거가 있다.
- 사용자가 검토 화면이나 그에 준하는 대화 내 검토를 받았다.
- 최종 스킬이 검증을 통과하고 요청한 형태로 패키징되었거나 인계되었다.
